5000 亿 token 让 AI agent 团队反编译一款 FPS：4 个 agent 跑三个月，最后败在「语义正确」上

Maurice Heumann 10 月 9 日发布了这次反编译项目的完整复盘：目标不是做出一个能跑的原型，而是把一款第一人称射击游戏准确、稳定、功能完整地还原成可编译的 C++ 源码，同时借这个过程搞清楚「怎么在几个月的时间尺度上编排自主 agent」。他同时开着 Claude Max（20x）与 Codex Pro 两个订阅，模型以 Sonnet 5 为主，也用 Opus 5.5 / Luna / Sol / Terra，agent 跑在 Claude Code CLI 与 Codex CLI 里，反汇编通过 Hex-Rays 的官方 ida-mcp 完成。进度用 GitHub issue 跟踪（一个翻译单元 = 一个 issue），所有 agent 共用一个 Discord 频道，既能 agent 对 agent 沟通也能让人插话，GitHub webhook 还会把 CI 失败推进频道。第一个月 4 个 agent（3 个 worker + 1 个 reviewer）就把约 80% 反编译完，游戏能启动、主菜单能渲染、地图能加载。他们做了两项关键调优：把 compaction 阈值从默认的上下文填充 90% 降到 42%（反编译中间产物是大量易失信息，早点压缩才能把「垃圾」清出上下文），以及用每小时一次的 cron 让 agent 重读目标与工作规范文档——因为长上下文里 agent 会走神、会在看完 CI 之前就关掉 issue。但代码可读并不等于正确：函数签名、类型、struct 布局写错，凭空发明或删掉逻辑，甚至把原来的全局变量常量读取改成了查表（代价高了好几个数量级）。作者归因于没有客观验收标准，reviewer 无从判断对错，worker 在 commit 里的自述理由反而像一次无意的 prompt injection，让 reviewer 接受了偏差。最终的解法是给 agent 一个 oracle：改用原版编译器做 byte-matching 反编译，用脚本把重建的 OBJ 与游戏 EXE/PDB 逐字节比对，并排除重定位字节、只校验符号与偏移，agent 拿到 PASS/FAIL 后自己返工。

🔎 新闻要点：发布 2026-10-09，历时 3 个月；同时订阅 Claude Max（20x）与 Codex Pro，模型以 Sonnet 5 为主兼用 Opus 5.5 / Luna / Sol / Terra，harness 为 Claude Code CLI + Codex CLI；反汇编用 Hex-Rays 官方 ida-mcp；协作面为 GitHub issue（一个翻译单元一个）+ 共用 Discord 频道（含 CI 失败 webhook）。第一个月 4 个 agent（3 worker + 1 reviewer）完成约 80%；调优手段为 compaction 阈值 90%→42% 与每小时 cron 重注入指令文档；失败模式为语义错误（签名/类型/struct 布局错、逻辑凭空增删、全局变量改查表）；根因为缺少客观验收标准、reviewer 被 worker 的 commit 自述说服；最终用 byte-matching 反编译（同编译器 + OBJ/EXE/PDB 逐字节比对、排除重定位）作为验收 oracle。

K8s 上跑 AI，工程师真正卡在哪一层：一份来自 discuss 论坛的问题清单

Kubezilla 团队 10 月 9 日发布了一份技术深潜：他们去 Kubernetes Discuss 论坛里检索 GPU、NVIDIA、DRA、Kueue、Kubeflow、LLM、推理、MCP 与 AI agent 相关的问题，想看看工程师真要做这件事时卡在哪里。结论有点反直觉——几乎没有人问「怎么跑 vLLM」或「怎么部署一个 LLM」，问题都低一层：为什么 Kubernetes 看不到我的 GPU、为什么两个 Pod 落到了同一张卡上、怎么按显存而不是按卡数调度、怎么在一个团队内公平共享一小池 GPU。文章按工程师实际踩坑的顺序逐条展开，并把每一类问题映射到 v1.37 现有的原生能力上：用 DRA 按模型真正需要的属性（显存、互连拓扑、算力代次）调度，用 Kueue 做队列与配额公平共享，用 gang scheduling 支撑分布式训练与多节点推理，服务层则要从普通 Deployment 换到推理网关。最后一节把 agent 拆成两类场景分别讨论：让 agent 去运维 Kubernetes，以及让 agent 跑在 Kubernetes 上。

🔎 新闻要点：文章发布 2026-10-09，基于对 discuss.kubernetes.io 论坛 GPU / NVIDIA / DRA / Kueue / Kubeflow / LLM / 推理 / MCP / agent 帖子的梳理，以 Kubernetes v1.37 为当时最新版本。核心结论：缺失的问法（如何部署 vLLM/LLM）极少，真实问题集中在「GPU 不可见」（如 0/1 nodes are available）、两个 Pod 落到同一张卡、按显存调度、团队内公平共享小 GPU 池。给出的对口能力为 DRA 属性调度、Kueue 队列与公平共享、gang scheduling、推理网关替代普通负载均衡，以及「agent 运维集群 / agent 运行在集群上」两类 agent 场景。

利用 AI 代码智能体优化软件架构的五种方法

InfoQ 译介（2026-10-11，原作者 Pierre Pureur、Kurt Bittner、Todd Miller，全文约 3600 字）：AI 编码智能体提升了开发速度，但不会自动保证架构合理，需要显式输入可衡量的质量属性需求（QAR）并配针对性测试验证；同时要主动建模遗留服务的行为以弥补文档缺失，避免逻辑误判引发集成风险。文章给出五种做法，强调 QAR 必须前置定义并贯穿「生成—验证」闭环，实践经验要结构化沉淀而不是靠试错。

能做什么
给出五条可操作做法：用编码 agent 梳理并记录遗留服务的系统设计与数据流（甚至顺手重构）、把可衡量的质量属性需求（QAR）前置定义并让生成的代码接受对应测试验证、把生成-验证做成闭环，等等。
解决什么痛点
只给模型功能需求时，它会「自动」补上一堆架构决策；遗留服务文档缺失导致调用方误判其逻辑与数据，问题往往到系统测试甚至上线后才暴露。
值不值得
这套「先写 QAR 再让 agent 写代码」的思路对做平台与业务接入都有直接价值——尤其把质量属性写成可测试的验收条件，正是长周期 agent 项目最缺的东西；文章是经验总结而非实验数据，建议只取方法框架，具体指标按自己系统定。

Opera: A Verbal Critic Framework for Long-horizon Coding Agents

论文提出 Opera，一个面向长程编码 agent 的「口头评论家」框架：现有 critic 只关注评估轨迹与生成反馈，很少跟踪反馈交付之后发生了什么，而反馈若误判正在进行的正确工作、或没戳中根本问题，反而有害。Opera 把每条纠正当作一条持久笔记来跟踪，从而判断反馈是否被采纳、是否解决了底层问题。

能做什么
把每次给 agent 的纠正记录成可持续跟踪的条目，据此判断反馈是否被吸收、任务是否真的回到正轨，而不是只生成一句评价就结束。
解决什么痛点
长程编码 agent 需要及时纠偏，但反馈本身会失效：reviewer 误判正确的工作、或只治标不治本，反而把 agent 带偏（与本月那篇 5000 亿 token 反编译复盘的现象互相印证）。
值不值得

The Lattice of Transition Laws

论文研究扩散模型与自回归模型的混合：以往每个混合方案都按设计固定自己的解码调度，作者转而追问「一个模型的解码调度表现能否被预测、以及能否被迁移」，并用 transition law 的格结构刻画这一关系，从而在扩散与 AR 之间做解码调度的选择。

能做什么

Pallas 内核怎么调优？Google 给出的答案是“少信模型，多看寄存器”

InfoQ（2026-10-10，原作者 Claudio Masolo）报道 Google 为 XProf（面向 TPU 工作负载的开源性能分析器）加入内核级性能分析套件：开发者能看到自定义 Pallas 内核的周期级细节，此前这些内核在 trace 里只是一个不透明块。在 TPU v7（Ironwood）上 XProf 会在运行时采样硬件性能计数器；一个分块矩阵乘法示例中 Google 发现内存停顿问题，加上三重缓冲后内核执行时间从 125.5µs 降到 88µs（约 30%）。原因是 Pallas/Mosaic/Triton 创建的内核会跳过标准 XLA Pass，使编译期静态成本模型失真，「optimal FLOPs」等指标可能不准，静态工具会把实际在等 HBM 的 MXU 标成已充分利用。

能做什么
XProf 新增内核级采样与诊断：在 TPU v7 上运行时采样硬件计数器，给出周期级机器指令视图（MXU / 标量与向量 ALU / 加载 / 溢出 / 存储等），并可通过编译器标志启用 MLIR 级自定义调用追踪，用来核对算子是否按预期融合、内存分块是否符合设计。
解决什么痛点
自定义内核在传统 trace 里是黑盒，编译期静态成本模型跳过 XLA Pass 后会严重失真——把明明在等 HBM 的单元报成满载，性能问题只能靠猜。
值不值得
如果你关心 GPU/加速器侧的内核调优，这篇的价值在于「先量后改」的实例（30% 来自消除内存停顿）；但整套工具面向 TPU/Pallas，N 卡栈需找对应替代（nsight/compute-sanitizer 一类），思路可迁移、工具不可直接照搬。
