🔥 今日重点

Kubernetes 官方实测节点 swap：Local SSD 支撑下 agent 沙盒 pod 密度最高提升 3 倍

Kubernetes 官方博客给出在节点上启用 swap 的基准方法：节点 swap 支持已在 v1.34 GA，配合高速 NVMe Local SSD，内核可把休眠内存换出，从而在同一台机器上跑更多 pod。文章测了三类负载——Linux 内核 CI/CD 构建、无头 Chrome 沙盒（Kata / gVisor）、隔离 Python 沙盒（gVisor）。结果：内核构建把内存上限从 600MB 压到 300MB（-50%），Kata 下并发 pod 从 40 升到 50（+25%），gVisor 下 Chrome 从 80 升到 160（+100%），Python 沙盒从 80 升到 240（+200%，约 3×），多数场景延迟无明显代价。

要点：① swap 支持在 v1.34 GA，能成立的关键前提是 cgroup v2 对 swap 独立记账、以及 NVMe SSD 消除换页延迟（旧版 cgroup v1 把内存与 swap 合并计量，导致用量不可预测）；② 动机正是 agentic 负载「启动吃大内存、之后长时间 idle 但内存仍需常驻」的形态，文中点名 agent-sandbox 框架；③ 密度收益：内核构建内存 -50%、Chrome Kata +25%、Chrome gVisor +100%、Python 沙盒 +200%。
🔥 今日重点

DeepSeek 披露 Agent 沙盒平台 DSec：单套分片日服务约 300 万沙盒，资源超卖超 50 倍

DeepSeek 公开其 Agent 沙盒平台 DSec 的工程细节：一套扩展分片约 160 台服务器、3 万 CPU 核心、250TB 内存，每天服务约 300 万个沙盒，峰值约 38 万个沙盒同时在线，承载 V3.2 到 V4.1 的 Agent 训练、评测与数据预处理负载。它把环境拆成 base image（OS/基础软件）、workspace（任务代码依赖）、toolkit（如 DeepSeek Harness）三层各自版本化、创建时组合，避免工具一改就整镜像重建；镜像数据放 3FS、本地只留元数据按需读取——8192 容器并发测试从 60 多分钟降到约 35 分钟（1.71×），磁盘写入减少约 57%。资源侧，约 90% 沙盒平均 CPU 使用不足申请量的 5%，生产超卖率超过 50 倍；用 virtio-pmem + DAX 让同宿主机 MicroVM 共享页缓存，峰值内存降 40.2%，再用 DAMON + balloon 回收空闲页，累计内存再降 21.2%。

要点：① 规模——160 台服务器 / 3 万核 / 250TB 内存，日约 300 万沙盒、峰值 38 万并发；② 环境三层拆分（base image / workspace / toolkit）+ 镜像按需加载（Agent 实际只访问镜像的 4.2%–13.3%），EROFS 挂载把工作区准备从 79 分钟压到 45 分钟；③ 资源侧 ~90% 沙盒 CPU 使用 <5%、超卖 >50 倍，virtio-pmem+DAX 与 DAMON+balloon 分别省内存 40.2% / 21.2%；④ 统一 FnCall / Container / MicroVM / Full VM 四种后端，并用 Agent 构建 Agent 的环境。

Leviathan：把数据集变成 agent 可查的排序全文索引，单二进制、每次作答约 450 token

elstongun/leviathan 是一个单文件二进制，把 JSONL/JSON/CSV/TSV/SQLite（或任意数据库 CLI 的导出）建成排序全文索引，agent 用自然语言提问即可拿到带引用的短结果卡。它在 100 万条记录（678MB）上对比「最佳 grep 策略」：中位每问 436 token 对 107,122 token（245×），Top-5 命中相关记录 99.0%、Rank-1 98.5%，中位延迟 33ms 对 92ms，最坏情况 602 token 对 9.7M token。它不持有任何数据库凭据（数据经各库自身 CLI 管道进来），索引就是一个 SQLite 文件，并提供 skills/leviathan 供拷进 ~/.claude/skills/，另有 MCP 模式（search / resolve_group / get / describe 四个只读工具）。

能做什么
单二进制把任意表格/导出/日志建成排序全文索引，自然语言查询返回带引用结果卡（约 450 token）；支持 -g 分组检索、--where / --since / 短语与排除过滤，upsert/delete 增量刷新，可作 CLI+skill 或 MCP 接入 agent。
解决什么痛点
agent 面对大数据集只能 grep 再读原始历史，token 消耗爆炸（实测差 245×）且容易漏掉关键记录；上下文预算全被原始数据吃掉。
值不值得
关注 agent 上下文/成本治理的值得试——无运行时依赖、索引即一个 SQLite 文件、未使用时 0 token 成本；但它是确定性全文索引而非向量库，语义模糊检索能力有限，适合工单/台账/日志这类记录型数据。

AWS：Bedrock 托管 Agent（OpenAI 驱动）公测，并上架 GPT-6.1 Sol 等新模型

AWS 上周宣布 Amazon Bedrock Managed Agents powered by OpenAI 进入公测：基于定制版 OpenAI Agents API，做成 AWS 原生并接入既有的身份、权限与治理控制；执行环境可选自托管算力（已有开发机、容器或计算环境）或 Bedrock AgentCore Runtime（托管运行时 + 你 AWS 账户内可配置存储）。同期 Bedrock 上架多款模型：GPT-6.1 Sol（称接近 GPT-6 Astra 但成本约 1/5）、GPT-6 Astra 的 UltraFast 模式（称 API 推理最高快 6×、约 300 token/秒）、Anthropic Claude Sonnet 5.5、SpaceXAI Grok 4.7（强化混合文档处理与 repo 级编码的规划/错误恢复）。

能做什么
在 Bedrock 上托管运行 OpenAI 模型驱动的 agent：可复用 IAM 身份、权限与治理，执行环境在自托管算力与 AgentCore Runtime 之间可选，并同时把 GPT-6.1 Sol、GPT-6 Astra UltraFast、Claude Sonnet 5.5、Grok 4.7 纳入 Bedrock 模型目录。
解决什么痛点
企业要在合规边界内跑 agent，既不想自建 agent 运行时，又希望沿用云上现有的身份/权限/审计体系；同时模型选择被单一供应商锁定。
值不值得
若你在评估「agent 运行时托管 vs 自建」，这是一条主流公有云的现成路线，值得对照 AgentCore 的能力边界与计费；注意它是 AWS 侧托管（含 OpenAI 模型），与本地/私有化 agent Infra 是两条不同取舍。

The Agency：把成套专业 agent 人格一键装进 Claude Code / Cursor / Codex 等 harness

msitarzewski/agency-agents 是一套按职能划分的 AI agent 人格集合（前端、社区运营、创意、现实校验等），每个 agent 文件包含身份与人格、核心任务与工作流、可交付物定义。它现在提供原生桌面 App（macOS/Linux/Windows，可 brew install --cask msitarzewski/agency-agents/agency-agents），用于浏览整套 roster 并一键安装到 Claude Code、Cursor、Codex、Gemini CLI、OpenCode、Qwen、Osaurus，且自动更新；也支持脚本安装（./scripts/install.sh --tool claude-code）或直接把 markdown 拷进 ~/.claude/agents/。

能做什么
以 markdown 文件组织的 agent 人格库，按职能分目录；桌面 App 可浏览整套 roster 并一键装进多种 harness，脚本方式支持只装某一类；每个 agent 定义人格、任务与工作流、可交付物。
解决什么痛点
各家 harness 的 subagent / 角色配置格式不一，想复用一套按职能划分的角色资产得逐个手工迁移；且角色定义容易停留在空泛 prompt 模板。
值不值得
想快速给编码助手配一套「分工角色」的可以直接装来试，App 化安装降低了门槛；但它偏角色/流程编排而非硬能力，实际收益取决于你的工作流是否真需要多角色分工，值得与已有的 project rules / skill 体系对比后再引入。

接收方条件化潜在通信：多 agent 协作的缓存开销据称降低约 94%

论文针对多 agent 系统中「把大上下文分散到各 agent、靠通信协作」的场景：文本消息紧凑但需解码、且可能丢失接收方真正需要的证据，近期用潜在表示（latent）传递上下文的工作能保留更多信息。作者提出 Receiver-Conditioned Latent Communication，让通信按接收方条件化，据论文标题口径可获得约 94% 的缓存收益（CacheBack）。

能做什么
把多 agent 之间的上下文传递从文本消息改为「接收方条件化」的潜在表示，使接收方能直接复用所需的证据信息，而非先解码文本再补证。
解决什么痛点
多 agent 系统里文本通信要么信息有损、要么因解码与重复传递产生大量缓存/上下文开销，团队难以在「保真」与「省开销」之间取平衡。
值不值得
做多 agent 编排、关心上下文/缓存成本的可以读原文看条件化机制的具体做法；属研究阶段、结论来自论文自测口径，工程可用性还需验证。

Reflection 发布 501B 开源权重模型 Beam：23B 激活稀疏 MoE，RL 用了 1.05 万张 GB300

Reflection 发布其首个开源权重模型 Beam：稀疏 MoE，总参数 501B、激活 23B，面向编码、推理与 agentic 负载。预训练用了 23.8 万亿 token（含自有授权数据集）；并行开展的大算力 RL 在 1.05 万张 NVIDIA GB300 上、4 周训练里产生超过 1 亿次 rollout。公开榜单上 Beam 的 SWE-Bench Verified 80.9、Terminal Bench v2.1 80.1、SWE-Bench Pro v2-Hard 77.2、AIME 2026 97.8、HLE（无工具）36.2，官方称接近 Qwen 3.8-Max，优势在推理时效率。权重、技术报告与模型卡将在本月晚些发布，目前开放早期访问申请。

能做什么
501B 总参 / 23B 激活的稀疏 MoE 开源权重模型，面向编码与 agentic 任务，配合在 1.05 万张 GB300 上、4 周完成、超 1 亿次 rollout 的大规模 RL 训练流程。
解决什么痛点
开源阵营要在编码/agentic 能力上逼近闭源前沿，同时控制推理成本；训练侧则需要能支撑高算力 RL 的环境与基础设施。
值不值得
关注开源模型前沿与「RL 训练基础设施」规模效应的值得留意，尤其 1 万卡级 GB300 的 RL 时长与 rollout 数据；但权重尚未放出、能力为厂商自测口径，真正评估需等模型卡与第三方复现。

Qwen3.8 27B「用文字算加法」：模型能算对和，却给出错误的英文数词

Simon Willison 记录 Colin Frasier 分享的一个实验：用 GPT-4o 让模型「算出和，但用英文单词写出答案」，结果模型能算对数值，却在把数字转成英文数词时出错。文章借此说明「模型内部能算对、只是在特定输出格式上失败」的现象，对评估与提示设计有直接含义。

能做什么
通过「要求用英文数词输出加法结果」的对照实验，暴露模型在数值计算与数字→数词转换之间的能力落差：中间计算正确、最终格式化输出错误。
解决什么痛点

值不值得

FrugalEvo：把「成本」纳入 LLM 引导的程序进化

论文针对 AlphaEvolve 一类 LLM 引导的进化式程序优化（如圆堆积等困难计算优化问题）提出 FrugalEvo：以往方法通常只优化结果，忽略搜索过程的算力/调用成本，FrugalEvo 让搜索对成本敏感，在同等预算下做更划算的探索。

能做什么
在 LLM 引导的程序进化框架中加入成本感知：不只是追求最优解，还把搜索过程中的算力/token 开销纳入决策，使有限预算下的优化更高效。
解决什么痛点
AlphaEvolve 类方法效果好但调用与算力成本高，缺乏「花多少换来多少」的显式权衡，预算受限时容易浪费在低效探索上。
值不值得
关注用 LLM 做自动化算法/程序优化的可留意其成本建模方式；属研究论文，落地价值取决于与你实际优化任务的匹配度。

Felix Rieseberg 谈 Claude Cowork 架构换代：从本地 VM 改为云端沙盒

Simon Willison 收录了 Anthropic 的 Felix Rieseberg 的一段说明：旧版 Cowork 在云端做模型推理，但把工具调用执行在「随桌面端下发的 Anthropic 提供的 VM」里——加这个本地 VM 是为了能力、安全与安全边界，只把用户显式加入会话的数据映射进去。用户喜欢 Claude 能做到的事，但不喜欢本地跑 VM 的磁盘、续航与性能代价，也受不了「合上笔记本工作就停」。新版把模型推理和 VM 都搬到云端，每个会话独占一个沙箱、不与其他会话共享状态；当 VM 需要用户设备上的东西（如某个文件），由桌面 App 负责那次文件访问的工具调用。

能做什么

Kubelet 其实会看 inode，只是要等到「快满」才动手

CNCF 博文剖析一次真实的 inode 告警：节点触发 NodeFilesystemFilesFillingUp，直觉会先看磁盘——83% 已用、剩 22G，再看 inode 才 67% 已用、剩 530 万。作者指出这并不矛盾：该告警基于 predict_linear，报的是增长速度（斜率）而非当前水位，67% 本身没问题，问题是在多快逼近上限；而 kubelet 里唯一会介入的机制是驱逐。文章据此澄清 kubelet 到底看什么：镜像垃圾回收只看字节百分比（imageGCHighThresholdPercent 默认 85，降到 80），从不看文件数；但 Linux 的默认硬驱逐信号里确实包含 nodefs.inodesFree=5% 与 imagefs.inodesFree=5%（Windows 与其他平台的默认文件则没有 inode 阈值）。

能做什么
厘清 kubelet 对 inode 的真实处理路径：image GC 仅按字节百分比（85/80）回收、不看文件数，而 Linux 默认硬驱逐信号包含 nodefs.inodesFree=5% 与 imagefs.inodesFree=5%，并解释 predict_linear 类告警为何按斜率触发。
解决什么痛点
inode 耗尽与磁盘写满是两种不同故障，但运维惯性只盯 df -h 的磁盘百分比，容易漏掉文件数增长这个真正逼近的上限；等 inode 真满时唯一兜底是驱逐 pod。
值不值得
负责集群节点运维的直接有用：把「同时看 df -h 与 df -i」变成例行检查项，并按平台确认默认驱逐信号是否含 inode 阈值（Linux 有、Windows/其他没有）；具体阈值随版本变化，需对照自家 kubelet 版本核对。
