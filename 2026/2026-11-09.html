🔥 今日重点

Kinference：给 vLLM + Kubernetes 补一层 KV-cache 感知的推理控制面

Buoyant 开源 Kinference，定位是 vLLM 之上的推理控制面，而不是又一个推理引擎：客户端把 OpenAI / Anthropic 兼容请求指向它的 HTTP 端点，由它负责 token 速率限制、租户用量与成本核算、推理策略路由。最核心的机制是 KV-cache 感知的负载均衡——按 GPU 队列长度、历史性能以及目标 worker 上已有的 KV cache 内容打分，把请求发给「为这条请求要做的工作最少」的 vLLM worker，而标准 Kubernetes Service / kube-proxy 完全不看缓存。官方基准里，同等 SLO 下共享前缀负载的 goodput 是 kube-proxy 的 7.4 倍、多轮对话 3.5 倍，中位 TTFT 降低 95%，而且 kube-proxy 在测试的任一并发度都没能达到其设定 SLO。策略层用 CRD InferencePolicy 表达，可按租户、模型、GPU 池状态、提示词语义分类路由：低复杂度请求发给便宜模型，本地队列积压时溢出到 Bedrock / Databricks，命中 PII 时禁止出集群（fail closed）。策略是 YAML、可进 git、可 lint、可独立回滚，这是它和硬编码在网关里的路由规则最大的区别。

Kinference 由 Buoyant 发起并开源，底层推理仍交给 vLLM。接入方式仅为把客户端指向其 HTTP endpoint，发送 OpenAI 或 Anthropic 兼容流量。控制面能力：token rate limiting、租户用量与成本追踪、KV-cache 感知负载均衡、InferencePolicy 策略。策略 CRD 为 kinference.buoyant.io/v1alpha1，示例包括按语义复杂度选模型、按队列深度溢出到云 provider、PII 请求 fail-closed。基准数字：共享前缀 goodput 7.4×、多轮 3.5×，中位 TTFT −95%，中位端到端延迟下降 45%（其中一类负载）。
🔥 今日重点

阿里云 CIO 三年复盘：AI 生码率涨了，端到端交付只快 3%–7%

阿里云智能集团副总裁、CIO 蒋林泉复盘三年 AI 实践，给出一个反直觉结论：AI 生码率和代码量持续上涨，但端到端交付一个需求所消耗的人力几乎没变。他把需求全流程拆成六段——需求设计与评审 20%、交互视觉设计 10%、技术方案设计 15%、编码开发 20%、前后端联调集成 15%、测试与 Bugfix 20%。再拆编码这 20%：真正吃时间的是存量核心系统改造、与老系统融合、保证上线稳定的关键非功能性代码，代码量不大却占 65% 以上的编码时间；而 AI 最擅长的 CRUD、前端 UI、测试代码、胶水代码占大部分代码量，却只花不到 35% 的时间。按 20%×35% 计算，即便 AI 把这部分压到零，端到端理论收益上限也只有约 7%，业界实际多在 3%–5%。他进一步指出瓶颈已转移到 Review 与线上责任：能兜底的少数「老司机」被大量 AI 生成代码打爆，绕过 Review 则直接变成技术债。

讲者为阿里云智能集团副总裁、CIO 蒋林泉，内容为其负责的 CIO 线三年 AI 实践复盘。关键数字：需求六阶段耗时占比 20/10/15/20/15/20；存量核心与关键非功能代码占编码时间 65%+ 但代码量占比小；端到端提效理论上限约 7%，业界实测 3%–5%。核心判断：AI Native 是组织问题，token 用量、Vibe Coding、通用智能体的使用量不能证明组织形态发生变化；需要 CIO 与 CPO 联动，工具定义能力边界、组织决定能力能否进入真实工作。

EvoMemState：把 agent 记忆从「独立事实」改成带关系与推理状态

现有 agent 长期记忆多按「抽取事实—存储—检索」组织，事实之间如何互相更新、约束、冲突，以及当前请求该用哪条，都是隐式的。EvoMemState 增加两种状态：Relational State 记录每条事实的有效性、作用域与演化关系，Reasoning State 由强化学习训练的策略按当前请求生成，决定这些事实该如何应用。在长期对话与记忆使用基准上，它的检索完整性与记忆 grounding 的回答准确率都稳定优于现有记忆系统，代码已开源。

能做什么
把记忆建成「持久事实 + 关系状态 + 推理状态」三层：本体引导抽取事实并建关系，RL 把记忆使用经验内化成策略，按请求生成 Reasoning State 再驱动回答。
解决什么痛点
把记忆当互不相干的事实堆着，新事实与旧事实冲突、过期、限定条件不同时无法处理，检索出来的内容也不知道该不该用。
值不值得
做个人 agent / 长期陪伴类产品时，这是一条比「向量库 + 摘要」更结构化的路线，且有开源实现；代价是引入本体与 RL 训练环节，冷启动和调参成本高于纯检索方案。

VisSearch-Bench：多模态 agent 长程视觉搜索，最强系统只完整解出 26.47%

现有搜索基准多是「用图片定位实体，然后转文本检索」，测不到 agent 如何跨图像、对象与搜索步骤串联证据。VisSearch-Bench 提供 204 个人工编写任务、覆盖 7 个主域 25 个子域，分集合式视觉搜索、序列式视觉搜索、宽深混合搜索、竞争性视觉消歧、视觉结构引导搜索五类。每道题给出参考答案、可追溯证据与评分规则，准确率看整题是否解出，Process Score 单独算子问题与中间证据的正确性。16 个多模态模型中最好的系统即使带搜索工具也只完整解出 26.47%。

能做什么
204 题、7 域 25 子域的长程视觉搜索基准，五类任务覆盖跨图证据串联，同时给整题准确率与过程分两套指标。
解决什么痛点
多模态 agent 的视觉能力评估长期停在单图问答或「图片只用来认实体」，无法判断它在多步搜索中能否管理视觉上下文、串联证据。
值不值得
做视觉/浏览器类 agent 评测时可以直接拿来当压力测试集，26.47% 的上限说明这块远未解决；但它偏学术基准，和业务任务的分布差距需要自行校准。

vLLM v0.33.0 起发 LibTorch Stable ABI wheel：升级 PyTorch 不用重编

vLLM 的 C++ 后端大量调用 LibTorch，过去 PyTorch 一升级就要重编重链 vLLM。v0.33.0 起 vLLM 发布 LibTorch ABI Stable 的 CUDA wheel，同一份 vLLM wheel 可跨兼容的 PyTorch 版本使用，换 torch wheel 后直接导入即可。实现依赖 PyTorch 三层 stable ABI（C shim、C++ 包装、headeronly 工具），未覆盖的算子走 torch_call_dispatcher；迁移覆盖 175 个 .cpp/.cu 与 120+ 头文件，按块搬进独立 stable 库，并用 TORCH_TARGET_VERSION 让构建在引入不稳定头文件时直接失败。代价是少量 host 侧类型转换开销，CUDA Graphs 下基本消失。

能做什么
发布 ABI 稳定的 CUDA wheel：把 kernels 迁到 stable C shim / C++ 包装上，未稳定的 API 用 torch_call_dispatcher 兜住，并用构建标志强制约束。
解决什么痛点
PyTorch 版本节奏快于 vLLM 发版节奏，每次升级都要重编整个推理引擎，发行版与用户都被卡在旧 torch 上。
值不值得
自建推理服务、又需要跟进新 torch/CUDA 特性时价值直接：升级路径从「等 vLLM 重编」变成「换 wheel」；但要接受 stable ABI 只覆盖部分算子，且仍有 CUDA 版本与 Python API 的兼容约束。

Cloudflare Auto Router 基准：可靠性 +10 个百分点，成本约三分之一

Cloudflare 在 AI Gateway 推出 Auto Router 公测：模型名设为 cloudflare/auto 后，边缘 GPU 上的多头分类器给请求分配 14 类任务概率，并从复杂性、歧义性、风险程度、上下文依赖四个维度打 1–5 分，再按公开公式「效用 = 预期质量 − 自适应成本惩罚」选模型。官方基准用 97 个任务、每模型采样 3 次、1 万次 bootstrap 重采样，结果是可靠性提升约 10 个百分点、成本约为原来的三分之一。限制也很明确：分类只看最近几轮、文本上限 8 KiB；没有 session ID 时同一对话的请求可能落到不同模型，前缀缓存无法复用；路由权重来自基准测试，新模型要手工加进评分矩阵。

能做什么
两阶段路由：先按格式/凭证/预算过滤候选池，再在边缘用 Workers AI 跑多头分类器（14 类任务 + 四维 1–5 分），按「质量 − 成本惩罚」打分选模型。
解决什么痛点
多模型网关里「该用哪个模型」通常靠人工规则或全量走最贵模型，缺少按请求难度动态降本的可审计机制。
值不值得
做模型网关/多 provider 路由时这份基准与公式值得当参考，尤其它公开了自家路由器落败的对照组；但分类上下文只有 8 KiB 且按最近几轮判风险，长会话里的高风险指令可能被降级，生产要自己补跨轮风险标签。

Muir：门控压成低秩投影，1.34B 外推 1000 万 token 无困惑度漂移

线性注意力把上下文压进固定大小的 KV state，门控 delta 规则要同时做擦除与写入。作者分析发现 state 更新对擦除的敏感度远低于写入（key 能量经激活与归一化后集中在少数通道），于是 Muir 把全部门控融进一个敏感度分配的低秩投影，再用匹配滤波读出给 state 行重新加权，省下的参数投到更宽的 FFN。166M–1.34B 规模上困惑度比 GDN-2 低 1.8%–2.0%、比 Transformer 低 2.5%–3.6%，常识准确率最高 +1.9 分；1.34B 模型从 4K 训练长度外推到 1000 万 token 流无困惑度漂移，100 万 token passkey 接近 100%，吞吐与 GDN-2 持平。

能做什么
按擦除/写入敏感度不对称做低秩门控 + 匹配滤波读出，并设计大 chunk 下数值稳定的并行更新算法。
解决什么痛点
门控线性注意力里慢衰减 state 行范数过大会主导读出、逼出更强的写入擦除，形成干扰；标准 chunkwise 算法在大 chunk 下数值不稳定。
值不值得
跟踪长上下文架构时值得读：它把「门控该多精细」这件事量化了，且给出 10M token 外推的实测；但仍是 1.34B 规模的研究模型，离生产推理栈还有距离。

PACT 跨模型传递被拆穿：部分收益用「无用信号」也能复现

PACT 把大模型的 prompt 表示传给小模型做生成，理论上兼顾能力与成本。作者开源 PLatour 框架（冻结模型 + 零初始化线性桥，支持混合注意力），在生成任务上超过开源基线，并在数学与代码基准上以更小的 sender 超过 Mostik 报告的结果。但受控实验发现：部分任务的收益用无信息 sender 信号、自通信或只训 receiver 也能复现——可训练桥本身是参数高效适配器，未必真用上了 sender 信息。为此作者提出 PACT-Check，量化一个训练好的 PACT 系统里有多少增益真正来自通信。

能做什么
开源的 PACT 框架 + 归因方法：用零初始化线性桥连接冻结的大小模型，再用 PACT-Check 做消融，判断增益来自通信还是桥的适配效应。
解决什么痛点
跨模型 latent 通信的论文普遍只报任务提升，缺少「收益是否真的来自 sender」的对照，容易把参数高效微调的效果误读成模型协作。
值不值得
做小模型+大模型协同推理时，这篇的结论比方法更有价值：先做 PACT-Check 式消融，别把适配器收益算成通信收益；框架本身可直接复用。

Simon Willison：同一 parse_number()，C 扩展 14 KB vs Rust 321 KB

他用 Claude Opus 5.5 把同一个 parse_number()（把 -$1,234.56、12.5% 这类字符串转成数值）分别实现为 C 与 Rust 的 SQLite 可加载扩展。产物大小差距明显：C 扩展 14 KB，Rust 用 rusqlite 是 321 KB、sqlite-loadable-rs 是 298 KB；但最初 Rust 更快，因为 Rust 的 strtod 等价实现约快一倍。随后让模型手写 C 的十进制快速路径后反超：200 万行净耗时混合数据 19 ns/行（Rust 41–46 ns，原 C 67 ns），整数 16 ns、小数 18 ns，8 百万次 fuzz 校验各版本结果一致。

能做什么

解决什么痛点

值不值得
