🔥 今日重点

Sashiko：Google 的 Linux 内核 agent 代码评审上线全部 lkml 提交，在 1000 个 Fixes 补丁里命中约 53% 的 bug

Sashiko 是 Google 内核团队（Roman Gushchin 等）做的 agent 代码评审系统，目标很窄：在补丁进内核之前把新问题拦下来。衡量方式是对 1000 个带 “Fixes:” 标记的近期上游内核问题做一次不过滤的回顾评审，命中约 53%；这套系统已在 Google 内部跑了一段时间，如今公开并对 Linux 内核邮件列表的全部提交做评审，token 与算力由 Google 出。代码用 Rust 写、Apache-2.0，已捐给 Linux Foundation（sashiko-dev/sashiko），支持 Gemini 与其它主流模型，实测以 Gemini 系列调得最多。文章重点不在跑分而在“怎么搭”：评审不是一次性提示，而是带代码笔记与维护者笔记的多轮 agent 循环，把内核的上下文（历史、约定、相关补丁）喂进去再让人看结论。代价也说得直白：每个补丁都要把代码发给所选模型厂商，成本按 token 计，公开实例靠赞助撑住。

🔥 今日重点

外部沙箱（external sandbox）模式：agent 留在沙箱外、只通过 localhost API 调执行环境，已有 v86 / Apple Containers / Quicksand 三套实现

Simon Willison 与 Prime Radiant 合作提出“外部沙箱”模式：agent 本身跑在宿主机上，真正执行代码的那部分放进一个独立沙箱，两者之间只走一个统一的 localhost HTTP API。这样 agent 的推理与工具编排不受沙箱限制，而被 prompt injection 或本地小模型失误引爆的代码只能待在沙箱里。一次放出三套实现：external-sandbox-v86（Node 服务内用 v86 在 WebAssembly 里跑 Alpine Linux）、external-sandbox-container（Python 服务把 Alpine 跑在 Apple Containers 实例里）、external-sandbox-quicksand（用微软 Quicksand 库，把 QEMU 与 Alpine 打包成一个 Python 包）。三者 API 一致，Pi、Claude Code、Codex 都可配置成把执行请求发过去。沙箱还带一个可选 HTTP/HTTPS 允许列表代理，能限定 agent 代码只能访问哪些主机，并做凭据替换——让 agent 发出带认证的请求而拿不到明文密钥；代理在沙箱运行中也能改配置。

研究：模型变强不等于活儿变多——Fable 5 被禁 19 天当作自然实验，7 天 PR 合并率只差 1.4 个百分点且不显著

论文用 2026 年 6 月 12 日美国出口管制导致 Claude Fable 5 停用 19 天做自然实验：人和项目不变，只有模型换了。多数原 Fable 5 用户退到 SWE-Bench Pro 低 11 分的 Opus 4.8，作者跟踪 297 名用户前后的 GitHub PR，并以 8,908 名一直用 Opus 4.8 的开发者作对照。双重差分（开发者与日期固定效应）结果：拿到 Fable 5 只让 7 天 PR 合并率提高 1.4 个百分点（置信区间 -1.4 到 +4.3），不显著；每周合并 PR 数 +2.4%（-4.9% 到 +10.2%）。另外对 2026 年五次模型升级重复同样比较（1,208 名开发者、15,442 个 PR），加权平均 -0.9 个百分点，五个估计全为负。

能做什么
用真实的模型断供窗口做准实验，把“基准分提升”与“实际交付量”分开量化：样本 297 + 对照 8,908 人，外加五次升级的重复验证，全部用 diff-in-diff 控制人与时间。
解决什么痛点
团队做模型选型时，常拿 SWE-Bench 之类的分数当生产力代理，但缺少“分数→交付”的因果证据；这篇给出的估计接近零，说明瓶颈可能在流程、评审与上下文，而不在模型。
值不值得
值得读方法与结论，别只看结论：合并率这种指标受评审流程影响大，未必等于“工作没变多”。做内部 agent 投入决策时，可以作为“先量自己的流水线”的反面提醒。

研究：给冻结的 LLM 一个算力预算和“改写文本”的工具，它会自己长出一套自学算法，且能迁移到新游戏与 3D 导航

论文问的是一个很实际的问题：模型越来越强，还需要人规定“怎么自我改进”吗？实验设定是“自主范式”：只给基础原语、资源和一句笼统的自我改进目标，agent 自己构造基于上下文的自我学习算法。以游戏为测试床，冻结的 LLM agent 拿到算力预算和收集经验、改写文本的工具，在没有外部强加循环、也拿不到真实世界数据的前提下自由实验。结论是足够强的模型确实能自学：涌现出的策略与自我调节学习的经典认知框架、以及自生成课程的机器学习构造对得上；学到的文本产物还能迁移到不同游戏时长、机制与 3D 导航任务。

能做什么
把“自我改进”从人手写的训练循环，变成 agent 在给定算力与工具下自建的上下文优化过程；验证方式是跨游戏时长、机制与 3D 导航的迁移。
解决什么痛点
现在做 agent 自我提升基本靠人设计反思/记忆/课程；这篇给出证据：能力足够的模型能自己发明这一层，人的工作退化为给资源与目标。
值不值得
对 skill/harness 设计有直接启发——别把反思循环写死，留出“让 agent 自己写笔记与课程”的空间；但结论绑定“足够强的模型”，弱模型上未必成立。

Microsoft Agent Framework 的 Durable Task 扩展 GA：把 agent 编排做成可持久化、可恢复的工作流

Durable Task 扩展在 Microsoft Agent Framework 上正式可用，把多 agent 编排落到可持久化的工作流引擎上：长跑步骤、人工审批、失败重试都有检查点，进程重启后从断点继续而不是从头再跑一遍。对多轮、跨小时的 agent 任务，这是把“编排逻辑”和“模型调用”分开的一层。

能做什么

解决什么痛点

OpenCode v2.3.2 修 GPT-6.2 提示缓存：system prompt 放进 instructions 字段不被缓存，改为前置 developer 消息后每步不再重复计费

OpenCode 2.3.2 修了一个直接烧钱的细节：GPT-6.2 不缓存放在 Responses 接口 instructions 字段里的 system prompt，于是每一步都被当成未缓存输入重新计费。改动是把 system prompt 作为前置 developer 消息发送，所有 Responses 路由统一处理，从而命中缓存。配合上一版的“超时命令转后台继续跑”，这一轮更新基本都在压长跑 agent 的隐性成本与中断。

能做什么
统一把 system prompt 走 developer 消息以命中 GPT-6.2 的缓存路由；输出侧延续上一版，超时命令转后台、压缩异步写。
解决什么痛点
长会话里 system prompt 每步重发，未命中缓存时按全价计费，成本随步数线性膨胀且很难在账单上定位。
值不值得
用 OpenCode 跑 GPT-6.2 的必须升；若自己写 harness 直连 Responses 接口，同样要检查 instructions 字段是否被缓存——这是通用坑。

OpenAI 公开 Codex 沙箱实现：macOS 用 Seatbelt、Linux 用 bubblewrap+Landlock、Windows 用 AppContainer，文件与网络边界由用户配置

OpenAI 系统讲了 Codex 如何在你的机器上执行命令同时守住文件系统与网络边界，并跨 macOS、Linux、Windows 三平台各自用系统原生原语：macOS 走 Seatbelt（sandbox-exec 的 SBPL profile），Linux 走 bubblewrap 命名空间加 Landlock LSM，Windows 走 AppContainer/受限令牌这一路线。权限由用户配置的文件系统与网络策略决定，agent 只能在被允许的读写范围内动作。这套设计的关键取舍是“不引入 VM 也能把破坏面收窄”，代价是隔离强度依赖各平台原语自身的成熟度。

能做什么
同一套策略模型映射到三种 OS 原语：Seatbelt profile、bubblewrap+Landlock、AppContainer/受限令牌；限制文件读写与网络出口，策略由用户声明。
解决什么痛点
agent 在本地跑命令是最实用的能力，也是最危险的能力；装 VM 太重，裸跑又不可接受，原生沙箱是唯一的中间档。
值不值得
写自家 agent 执行层可直接照这套映射表选原语；注意 Seatbelt 早已被苹果标记弃用、Windows 侧成熟度最低，真要隔离不可信代码仍应上容器/microVM。

Google PageBreak 用“确定性验证器”把 agent 误报压到接近零：1 月起在自家 Web 应用里找出 500+ XSS

Google 的 AI 安全 agent PageBreak 自今年 1 月全面运行以来，在自家各类 Web 应用里发现了 500 多个 XSS 漏洞。它用 Gemini 自主调查潜在漏洞，但只在确定性验证器于运行中的应用上真实复现成功后才上报：执行 JavaScript 验 XSS、往全局可读位置写数据验路径遍历、触发外发 DNS 请求验 RCE。因此误报率接近零。关键在于验证器是安全工程师写的普通代码、由真实利用载荷驱动，并且位于 agent 循环之外——模型可以随便提假设，只有验证器确认的才算数。未经验证的候选漏洞留在内部作为线索，用于发现验证能力缺口并指导新验证器开发，不下发给产品团队，避免他们被不可信报告拖住。Google 的长期目标是把产品团队的参与缩到“只验证 AI 生成的修复”，正与 CodeMender 集成以自动产出补丁。

能做什么
agent 提出漏洞假设 → 在运行环境用真实 exploit 做确定性复现 → 只有复现成功才上报；验证器是人工编写的普通代码而非模型生成，且在 agent 循环之外；已验证 XSS、路径遍历、RCE 三类。
解决什么痛点
AI 生成的漏洞报告“听起来很有说服力但经常是错的”，团队被迫逐条核查，信任度迅速归零；PageBreak 用可复现性当作报告的准入条件，把噪音挡在门口。
值不值得
这是把“agent 提假设、确定性程序做裁决”落成生产系统的范本，可直接搬到代码评审、配置审计、渗透测试；前提是你有一套能真实复现的运行环境与流量/源码关联能力。

Envoy 往“第 8/9 层”走：按请求体里的 model / tools.call 路由，按 token 预算限流，已经承载 GKE 上的 Agent Substrate 数据面

Google Cloud 把 agent 流量的路由问题拆成两层新协议层：第 8 层是 LLM API、MCP、A2A 这类跑在 JSON-RPC 2.0 / gRPC 上的交互协议，第 9 层是 UCP、AP2、ADK 这类 agent 框架接口。传统 L7 代理在这两层上失效：几乎所有 LLM 流量共用 /v1/chat/completions 这类路径，靠 header 分不出“便宜一问”和“50 万 token 的长提示”，也分不出用的是哪个模型。限流同样失真——每分钟 1 个请求配巨大上下文，消耗的算力可能超过几十个短查询，agent 循环能把预算悄悄烧光。Envoy 的做法是把策略属性（tools/call、tool_name、model 等）从请求体里解出来做路由与配额，并处理多轮推理需要的会话亲和与工具调用边界。这套能力已经用在 Google Cloud 的 Application Load Balancer 与 GKE 上的 Agent Substrate 数据面上。

解决什么痛点
多模型、多租户的 agent 网关如果只按路径和请求数限流，既分不清成本也拦不住单请求烧穿预算；token 维度才是真正需要计量的资源。
值不值得
自建 agent 网关的重点参考：把“按 token 计量 + 按工具/模型路由”放进数据面而不是应用层。注意解析请求体会带来性能与隐私权衡，需评估是否在网关解密。

GKE 支持单栈 IPv6：节点与 Pod 全 IPv6，每节点 /112 给 65,536 个地址，TPU v6e 与 Axion 池已在预览

GKE 上线单栈 IPv6 预览：节点与 Pod 都只跑 IPv6，不再占用私有 IPv4；Cloud TPU v6e（Trillium）与 CPU 节点池（含 Axion）先支持，GKE 版本 1.37.1-gke.3020000。每个节点分到 /112 的 Pod 网段，即 65,536 个地址，地址容量不再是集群规模的上限（单节点 Pod 上限仍受 GKE 限制约束）。与 IPv4 端点互通靠 DNS64（VPC 侧）+ NAT64（区域 Cloud NAT）：Pod 可透明访问只支持 IPv4 的镜像仓库、数据集站点。性能方面官方称 burst 调度、CNI sandbox 建立、节点间 TCP/UDP 时延与多流吞吐、eBPF Service 负载均衡与 NodeLocalDNS 都与 IPv4 持平；每个 Pod 有唯一 IPv6 地址，无需集群内 NAT，便于遥测与网络策略排障。

能做什么
节点与 Pod 只用 IPv6，nodes/pods 不再吃 RFC1918；每节点 /112（65,536 地址）；DNS64/NAT64 打通 IPv4 端点；eBPF Service LB 与 NodeLocalDNS 无额外开销。
解决什么痛点
大 AI 集群真正的瓶颈常在地址：上千加速节点 + 推理副本 + Ray worker + sidecar + 向量库，私有 IPv4 很快耗尽，双栈也顶不住与本地网络/对等 VPC 的地址冲突。

Kyverno 定位 CEL 准入的真实开销：86.8% 分配花在对象转换，改成循环外转换一次后降到 2.9%，1.19.2 已修

Nirmata 对 Kyverno 的 CEL 引擎做 profile，本以为成本在 CEL 表达式求值，结果 86.8% 的内存分配花在 ConvertObjectToUnstructured——把 AdmissionRequest 的原始 JSON 字节转成 CEL 能读的 map。根因是转换写在“遍历匹配策略”的循环里：启用 Pod Security Standards 后，一次典型 Pod 创建约匹配 16 条策略，同一个 Pod 被解析 16 次，复杂度 O(策略数) 而本应是 O(1)。修复把转换提到循环外：先把对象临时置空做一次便宜转换，再把对象拼回去，保证策略看到的语义完全不变；各引擎（Validating/Mutating/Generating）保留各自既有契约，并用等价性测试逐字段比对原实现。效果：转换占比 86.8% → 2.9%；MutatingPolicy 引擎在 64 条策略下分配次数 258,943 → 52,689、耗时 10.59ms → 2.97ms。修复随 Kyverno 1.19.2 发布。

能做什么
把准入对象的 unstructured 转换从 per-policy 循环里提到循环外，一次构建、多策略复用；保持 Validating 与 Mutating 引擎各自原有的对象视图语义，附等价性回归测试。
解决什么痛点
策略数量越多、Pod 越大，准入延迟越线性膨胀，而成本藏在“没人以为贵”的对象转换上；这也是公共基准里 Kyverno 落后的隐藏原因之一。
值不值得
跑 Kyverno 的直接评估 1.19.2；自研 admission webhook 的把“每次请求只解码一次请求体”当硬规则——这类 O(策略数) 的重复解析在准入路径上最容易被忽略。
