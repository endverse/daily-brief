🔥 今日重点

Kubernetes 官方：cgroup v1 已弃用，v1.35 起 kubelet 默认不再在 cgroup v1 节点启动

Kubernetes 官方博文梳理 cgroup v2 迁移：cgroup v1 管理自 v1.31 进入维护模式、现已被弃用，cgroup v2 自 v1.25 起稳定。从 v1.35 起 failCgroupV1 默认为 true，kubelet 默认不会在 cgroup v1 节点上启动；kubeadm 的 SystemVerification 预检在 kubelet ≥v1.35 时会直接报错，中止 init / join / upgrade。文章同时列出 cgroup v2 上才有的能力：Memory QoS（memory.high 限流 + memory.min / memory.low 分层保护，memoryReservationPolicy 取 TieredReservation 时启用，memoryThrottlingFactor 默认 0.9，建议内核 ≥5.9），以及容器级 OOM 处理——cgroup v2 节点上 singleProcessOOMKill 默认 false，kubelet 会写 memory.oom.group 让整个容器一起被杀。还有一条迁移后依然存在的老问题：active_file 在 kubelet 眼里不算可回收内存（kubernetes#43916），I/O 密集负载下大 page cache 会触发内存压力驱逐，官方给的绕法是对这类容器设相等的 request 与 limit。

要点：① v1.31 cgroup v1 进入维护模式、现已弃用，cgroup v2 自 v1.25 稳定；② v1.35 起 failCgroupV1 默认 true，kubelet 不再在 cgroup v1 节点启动，kubeadm 对 v1.35+ 预检直接报错（旧 kubelet 只是告警）；③ cgroup v2 独占：Memory QoS（memory.high 限流 + memory.min / memory.low 分层保护，memoryThrottlingFactor 0.9，建议内核 ≥5.9）与容器级 OOM（singleProcessOOMKill 默认 false → memory.oom.group）；④ active_file 不计入可回收内存的旧问题（k8s#43916）迁移后仍在，I/O 密集容器需设 request=limit。
🔥 今日重点

GKE 为 AI 推理给出两套参考架构：Inference Gateway 按模型路由 + PSC 内网入口 + Model Armor 护栏

Google Cloud 发布两套「AI 推理服务网络」参考架构：一套基于 GKE，一套面向其他所有后端类型。共同组件包括 Private Service Connect 推理端点（把入口锚定在消费方 VPC 内，流量走私有内部 IP，推理调用不出私网）、可选的 Apigee API 管理（通过 Extension Processor 回调做客户端身份校验、限流与配额），以及 Model Armor 作为内联 AI 安全检查点（对 prompt 与 completion 做提示注入与敏感数据泄漏筛查）。GKE 版额外引入 GKE Inference Gateway，以内部应用负载均衡器（gke-l7-rilb）形式部署，解析请求负载、按 HTTPRoute 规则把请求路由到对应模型的 inference pool（同模型副本的逻辑分组）。入口层统一承担 TLS 终止、API 管理扩展与安全策略执行。

要点：① 两套参考架构——GKE 版与「所有其他后端」版，共享 PSC 私网推理端点、可选 Apigee（Extension Processor 回调做身份/限流/配额）与 Model Armor 内联安全筛查；② GKE 版核心是 GKE Inference Gateway，作为内部 ALB（gke-l7-rilb）按 HTTPRoute 规则选 pool，pool 内是同模型副本的逻辑分组；③ 入口同时是策略、安全与业务逻辑的执行点，TLS 终止与 API 管理扩展都收敛在这一层。

MCP Toolbox Java SDK 发布 1.0：把 agent 的数据访问收敛成类型安全的一套 MCP 接口

Google 宣布 MCP Toolbox Java SDK 达到 v1.0（紧随 MCP Toolbox v1.0）。它针对的是「N 个模型 × M 个企业数据源 = N×M 套定制连接」的集成爆炸，把集成收敛到单一的 MCP 协议层：任何 MCP 兼容 agent 都能直接访问 MCP 使能的数据系统，无需为每个模型或数据库重写连接代码。Java 侧提供类型安全的 agent 编排 API，v1.0 标记为稳定且向后兼容，官方称面向高并发、强事务一致性与状态管理的生产场景。

能做什么
以 MCP 作为模型与数据源之间的统一接口，提供 1.0 稳定、向后兼容的 Java 类型安全编排 SDK，让 MCP 兼容 agent 直接访问 MCP 使能的数据系统。
解决什么痛点
N×M 的自定义集成网既难维护，又让敏感企业数据库暴露在分散的访问控制与安全面之下；每接一个模型或数据源都要重写一套连接。
值不值得
团队主力栈是 Java、又要把 agent 接到既有企业数据源的值得评估——1.0 的稳定 API 意味着可以进生产；非 Java 栈收益有限，仍应评估凭据传递与最小权限。

预注册实验：agent 记忆里「选对原始对话轮次」可能不输「先抽取事实」

论文用预注册实验回答一个有争议的问题：对话记忆到底需要 LLM 抽取事实，还是选对原始对话轮次就够了？在 LoCoMo 与 LongMemEval 的留出集上、紧 token 预算条件下，用类型化决策模型 Jev 的一次调用选出的原始轮次，在 LoCoMo 上不劣于基于 LLM 抽取事实的系统（HuggingFace 8 赞）。实验同时检验了「排序是否重要」这一此前结论互相矛盾的关键点。

能做什么
用类型化决策模型 Jev 的一次调用来检索原始对话轮次，替代「LLM 先抽事实、再写入记忆」的流水线，并在紧 token 预算下与抽取式方案对比。
解决什么痛点
抽取式记忆要为每轮对话付一次 LLM 调用、还可能丢掉细节；而「选择式」方案此前的结论互相矛盾，工程上没有取舍依据。
值不值得
正在做多会话 agent 记忆、想砍掉抽取开销的值得读；属预注册研究但规模有限，落地前建议在自己的对话分布上复现一次。

CLIFT：用「保形自验证」给 Web agent 补上稠密监督与测试时扩展

CLIFT 针对 Web agent 用 RL 训练时监督太弱的问题：二元任务成败太稀疏、无法做 credit assignment，而每步都调用前沿模型当裁判又太贵、且部署时无法假定可用。它用保形自验证（conformal self-verification）：训练时让 agent 用自然语言回答验证问题以产生更密的信号，测试时用同一机制做候选筛选与扩展，从而不依赖外部大模型裁判。

能做什么
以保形自验证为底座打通训练与测试时扩展：训练阶段让 agent 自答自然语言验证问题生成稠密奖励，测试阶段用同一机制做候选筛选，不必逐步调用前沿模型裁判。
解决什么痛点
Web agent 的 RL 依赖弱监督——二值成功信号太稀疏难做 credit assignment，前沿模型裁判既贵又不能在部署环境假定可用。
值不值得
做 Web / 浏览器 agent 训练与评测的值得看它的自验证构造；属论文方法，保形保证依赖交换性假设，需在自己的任务分布上验证覆盖率。

T-Search：开放权重的 agentic 检索器，多轮检索只返回带理由的证据块

T-Search 是一个开放权重的 agentic retriever，面向困难的多跳搜索：给定问题与固定语料上的搜索工具，它做有界多轮检索并返回排好序的证据块与简短理由，把答案生成留给下游模型，因此检索后端与生成器可以各自替换而无需重训。模型基于 Qwen3.6-35B-A3B，用对抗式过滤合成的搜索任务做「按轮切片」的 SFT 后再训练，并附带 playground。

能做什么
有界多轮检索后输出排序证据块与理由，检索与生成解耦（可换后端与生成器而不重训）；基于 Qwen3.6-35B-A3B，训练数据是过滤后的合成搜索任务加轮切片 SFT。
解决什么痛点
稠密检索只依赖表层语义相似度，复杂多跳问题不够用；而端到端 agentic RAG 又把检索与生成绑死，换模型就得重训。
值不值得
在自建 RAG / 检索服务上想做多跳检索的可以看它的解耦设计；开放权重但需自备算力，效果依赖合成训练分布与你自有语料是否匹配。

预训练基座其实会推理：把起始 token 固定成「.\n\nOkay」，Olmo-3-7B 的 MATH-500 从 42% 跳到 78%

论文研究训练数据如何在「回答起始 token」与「后续推理行为」之间建立关联：把起点固定为特定线索 token，就能让未做 RL 的基座模型在数学与代码上逼近 RL 训练版本。例如线索 ".\n\nOkay" 把 Olmo-3-7B 的 MATH-500 pass@1 从 42% 提到 78%，"Alright," 则把 Qwen3-14B 的 72% 进一步提升。这提示「基座不会推理」的判断可能只是采样起点不对。

能做什么
通过固定回答起始 token 线索（如 ".\n\nOkay"、"Alright,"）触发基座模型内部的推理行为，在 MATH-500 上把 pass@1 从 42% 提到 78%（Olmo-3-7B）、把 72% 进一步提升（Qwen3-14B），全程不做 RL。
解决什么痛点
基座模型常被判定「不会推理」而必须再走 RL 后训练；若推理能力其实来自训练数据里的起始关联，后训练的必要性与成本评估都要重做。
值不值得
做后训练与评测的值得一看——它说明提示起点会显著改变能力读数，评测基座时需控制这个变量；属论文结论，线索的通用性与跨模型迁移仍需验证。

Sharpen Without Search：把序列级幂分布蒸馏进模型，免去采样搜索也能锐化推理

论文关注一个现象：模型给正确答案的概率可能高于任何单个错误答案，但错误答案合起来概率更大，于是采样时仍常答错。把每个完整答案的概率取大于 1 的幂再归一化（幂分布 / 锐化）能提升推理且不改参数，但需要对每个 query 采样并打分大量候选。作者证明这个幂分布可以被蒸馏进模型本身（Sharpen Without Search），从而免去推理期的多次采样。

能做什么
用「序列级幂分布」蒸馏：把原本需要多次采样打分才能得到的锐化效果直接训练进模型参数，推理时无需额外搜索或采样即可获得同等提升。
解决什么痛点
采样锐化（power distribution）能改善推理，但每个问题要跑多个候选并打分，推理成本与延迟都不可接受。
值不值得
关心推理期成本（test-time compute）与蒸馏的可以读原文；属方法论文，收益在论文自设基准上，需在自己的模型与任务上复现。
