🔥 今日重点

GPT-6.1 Sol 发布：对标 Astra 的智能、五分之一的 API 价格

OpenAI 在 DevDay 2026 发布 GPT-6.1 Sol，标准 API 价维持每百万输入 2 美元、输出 10 美元不变，缓存输入再降 50% 到 0.10 美元（相对标准输入相当于 95% 折扣）；上下文窗口 105 万 token、单次最多输出 12.8 万 token，支持 low/high/xhigh/max 多档推理强度。官方定位是「接近 Astra 的智能、五分之一的成本」：DeepSWE v1.1 与 Astra 持平，AutomationBench 中等推理强度下比 Claude Opus 5.5 高 2.2 个百分点。Terminal-Bench Science 0.1 在最高推理强度下平均每题 5.47 美元，Astra 为 23.80 美元，但 Astra 准确率仍最高（68.1%），官方建议它留给最难的科研任务。同场还发布 Ultrafast 档（token 生成最高 8 倍速、价格 6 倍）与面向敏感数据的 private intelligence 选项。

价格对照：GPT-6 Sol 缓存输入 0.20 美元、GPT-6 Astra 输入 10 美元 / 输出 50 美元；Sol 系列一周前刚整体降价 50%。Simon Willison 的 pelican 实测显示它与 GPT-6 家族的输出没有明显差异——这轮的重点是价格带而不是能力跃迁。
🔥 今日重点

GKE Agent Sandbox 转 GA：沙箱首条命令从 45–85 秒压到 1–9 秒，尾延迟 7.5 分钟降到 10 秒内

Google 把面向 RL 与评测优化的 GKE Agent Sandbox、Agent Sandbox RL 编排 SDK 一起转 GA，并提供主流 RL gym/harness 的原生集成。给出的数字是：time-to-first-command 提升 10–45 倍（1–9 秒，原 45–85 秒），最坏情况沙箱等待从 7.5 分钟降到 10 秒以内，控制面 churn 减少约 3 倍。关键机制是 in-place recycling：每个 RL step 会一次性申请成千上万个沙箱，SDK 复用 Pod 而不是删除重建，Pod 创建量降到三分之一，API server 在高频 churn 下保持稳定。这套东西是 Google 把「用 SWE-bench 等 agentic 评测故意压垮自家集群、再把 etcd 超时和 GPU 空转逐条修掉」的产物。

痛点描述得很具体：agentic RL 是同步批处理，训练要等最慢的沙箱就绪；每个任务往往需要独立 OCI 镜像，他们测试的公开数据集里仅 R2E 就有 4,578 个镜像，按每任务 4 个 rollout 计就是 1.8 万次镜像实例化——标准容器缓存的「少量静态基础镜像」假设在这里完全失效。

01

SkillGym：用自动生成的可验证环境训练「会用 skill」的 agent

SkillGym 针对一个具体缺口：skill 已被广泛用作 agent 完成长程任务的载体，但「如何合成可靠的训练数据、如何训练 agent 用好 skill」缺少系统方法。它的做法是把长程任务自动转换成可自动判定的训练环境，用带验证的奖励训练 agent 选择、组合与执行 skill，而不是只把 skill 文本塞进系统提示。论文对比了不同环境合成质量与验证信号对训练结果的影响，并给出 skill-use 能力在长程任务上的提升。对正在把 skill 体系落到生产 agent 上的团队，这是少见的「skill 训练 + 评测」公开方法论。

能做什么
自动生成可验证环境的 skill 训练框架：把任务转成有确定奖励信号的 gym 式环境，训练 agent 在长程任务中调用并组合 skill，而不是靠 prompt 注入 skill 文档。
解决什么痛点
现在 skill 生态里大量做法是「写技能文档 + 塞进上下文」，效果依赖模型自觉，既无法验证也没有训练闭环；skill 用错或不用时很难定位。
值不值得
如果你在做内部 skill 库，值得看它的环境合成与奖励设计思路（这是把 skill 从文档变成可训练能力的关键）；偏研究方法，工程化仍需自己搭训练与判定链路。

02

MILO：用多 agent 进化自动搜索出更好的 agent harness

MILO 把 harness——包住模型、控制执行与环境交互的那层代码——当作可搜索对象，用编排式多 agent 进化自动发现更优设计，代替人工反复试错。论文的动机很直接：harness 对长程任务表现影响很大，但组合空间巨大，而且每次改动都要人来重复验证。

能做什么
把 harness 设计自动化：多个 agent 并行提出/变异 harness 实现，用任务表现作为进化信号，自动筛选出更优的执行框架配置。
解决什么痛点
harness 的差异（工具 schema、重试策略、上下文裁剪、循环终止条件）对长程任务成功率影响很大，但靠人手逐个实验成本高、结论难复现。
值不值得
适合关注 agent 工程化调优的团队做思路参考；它是研究原型，离「直接在你们生产 harness 上跑」还有距离。

微软把 SQL 迁移做成 agent skills 并转 GA：评估、选型、执行、校验四段可复用

Azure SQL Migration Agent Skills 转 GA：把 SQL Server 到 Azure 的迁移旅程拆成评估、目标选型、迁移执行、迁移后校验四段可复用 skill，交给 AI agent 驱动，而不是固化在某个专用工具里。它们以 MCP/skill 形式交付，可配合用户在用的 coding agent 使用。这类「把成熟运维流程封装成 skill」正在成为云厂商交付专业能力的主流形态——同月 Google 的 Data Agent Kit 走的是同一路子。

能做什么
四段式迁移 skill：评估现有 SQL 负载、选择目标服务、执行迁移、迁移后验证，每段是独立可调用的 skill，agent 可组合编排。
解决什么痛点
数据库迁移是步骤多、判定标准细的流程，以往要么依赖专家手工清单，要么被锁在厂商专用迁移工具里，agent 无法按现场情况灵活调整。
值不值得
如果你在做企业内部流程 skill 化（把 DBA、发布、巡检等成熟流程交出去），这是很好的「流程即 skill」样板；具体可用性取决于你是否用 Azure SQL。

Google 把 gcloud / bq 打包成一个远程 MCP server：让 agent 直接用几百条 CLI 命令管云

Google Cloud 发布 Cloud CLI remote MCP server（预览），把 gcloud 与 bq 的数百条命令收拢成一个托管远程 MCP server，agent 不必为每个 API 写多步编排，直接调用 CLI 层的高层封装。官方给的理由有两条：CLI 已经把多步工作流、参数校验和高层操作打包成单条命令；LLM 在公开 CLI 文档上被大量预训练，调 CLI 比调裸 API 更稳、更易泛化。它补充了 Google 的托管远程 MCP 生态（此前已有各类服务级 server）。

能做什么
把一个 MCP server 同时暴露 gcloud 与 bq 的能力：agent 用 CLI 语义完成创建集群、查 BigQuery、配置 IAM 等操作，走托管服务而非自建网关。
解决什么痛点
让 agent 操作云资源时，逐 API 编排步骤多、易错；而把 CLI 给 agent 又缺统一的鉴权与封装层，凭据与权限粒度难以控制。
值不值得
如果你在给内部 agent 开云操作通道，这是「CLI-as-tool」的托管参考实现；注意它是预览版，权限最小化与出网审计还得自己在 MCP 层补。

05

ADK 图工作流：什么时候用静态图，什么时候让 Python 决定下一步

Google 用退款流程做例子讲清 Agent Development Kit（ADK）的 Workflow 抽象：任务拆成节点、用边连接、由代码/模型/人决定下一步，覆盖 fan-out/fan-in 并行、确定性路由与 agent 路由、human-in-the-loop 暂停、并行 worker 与动态编排。文章重点回答「什么时候把路径声明成静态图、什么时候让 Python 在结果到达时决定下一步」，也就是哪些部分要可测可控、哪些部分要留给运行时判断。对正在给 agent 工作流定结构的团队，这是把「单 agent + 大 prompt」拆成可验证节点的具体做法。

能做什么
ADK Workflow 的图式编排：节点里可以是函数或 agent，边表达顺序与路由，支持并行 fan-out、人工审核暂停、列表批处理，并区分静态图与运行时动态调度两种模式。
解决什么痛点
把整条业务逻辑塞进一个 agent 的 prompt 后，流程不可观测、失败不可归因、策略改动无法评审；纯代码 pipeline 又无法容纳模型判断。
值不值得
值得细读它的「静态 vs 动态」取舍标准，可以直接对照你给业务接入 agent 时的边界划分；ADK 是 Google 系框架，不在 GCP 也能用但要接受它的抽象。

文子的开源小红书 Agent Skills：把账号冷启动拆成 6 个可安装 skill

一套开源的小红书内容运营 skill 包：从账号定位、选题标题、真人化改稿、6–8 页图文结构到发布排期与数据复盘，拆成 6 个 skill 目录，可直接复制到 ~/.claude/skills/ 或 Codex 的 skills 目录使用。设计上不是「文案提示词合集」，而是把运营状态沉淀下来：每轮发布的数据与结论写回账号档案，成为下一轮输入，先由变现代推定位、再规划前 10 条内容。作者说明结果来自真实账号实践，并明确不承诺粉丝量或流量。

能做什么
6 个可安装 skill 组成的完整工作流：账号档案与定位、选题库与标题、人味化改稿、图文结构、发布排期、数据复盘写回档案；在 Claude Code / Codex / WorkBuddy 里自然语言触发。
解决什么痛点
自媒体运营 prompt 往往一次性、无状态，下一轮又从头开始；定位、选题、复盘之间的数据不连通，AI 产出无法累积成账号资产。
值不值得
对做「流程型 skill」（状态沉淀 + 多 skill 组合）的人是最好的现成样本，哪怕不做小红书也能抄它的档案写回机制；内容领域专用，通用性有限。

Anthropic 自建实验室：Claude 自主发现了一个类似 CRISPR 的新型酶系统

Anthropic 公开其生命科学团队与自建实验室的早期结果：在只有高层方向的情况下，Claude 分析 DNA 数据集、定位到一类未被表征的蛋白家族，并发现了一套与成串 DNA 重复序列相关的新酶系统，其特征组合此前只在极少数可编程系统（限制性内切酶、Taq 聚合酶、CRISPR）中出现过。功能尚未确定，但团队已在实验室验证其存在，并把「agent 参与科研每一步」当作目标工作方式。同批还发布了面向生命科学专业人员的验证计划。

能做什么

Claude 文本水印怎么做：不增 token、不插隐藏字符、拿密钥才能判定

Anthropic 解释 Claude 文本水印的机制：在「overcast / grey」这类对语义影响很小的选词处，模型本来就靠随机数决定，水印把随机数的来源换成密钥加上前文几个词，于是词的分布与可读性不变，但持有密钥的人可以检验整段序列是否与该密钥一致，从而给出「这段文本由 Claude 生成」的概率。官方强调不添加隐藏字符、不额外消耗 token、不携带可追溯到个人或组织的信息，且这是为符合 EU AI Act（8 月 2 日起要求标注 AI 生成内容）而做，多家厂商使用同类方案。

能做什么
基于选词随机性的统计水印：用密钥 + 前文决定低风险位置的选词，检测方用同一密钥做一致性检验，输出概率式判定而非硬标记。
解决什么痛点
监管要求标记 AI 生成内容，但插入隐形字符或改标点会破坏文本、可被简单清洗；厂商需要一个不损质量、又能被验证的机制。
值不值得
跟你的场景直接相关的一点：这类水印是可被检测方验证、也可被对手通过改写绕过的统计信号，做内容合规或数据出境审计时需要知道它的能力边界。

InfoQ 拆解 Claude Sonnet 5.5：Terminal-Bench 从 10.3% 跳到 70.6%，但最高推理强度下单任务 7.60 美元

InfoQ 复盘 Claude Sonnet 5.5 的实测数据：Terminal-Bench 4.0 从上一代 10.3% 跃升到 70.6%（超过 Opus 5.5 公布成绩），CursorBench 55.5% 与 Opus 5.5 只差约两个百分点；Lovable 的测试显示完成编程任务所需工具调用减少约三分之一、Shell 执行减半，Base44 的 118 次真实应用构建里平均 3.6 轮迭代完成（Opus 5 需 7.7 轮）。但 Artificial Analysis 测出推理强度拉到 Max 时每任务平均生成约 19.3 万输出 token（约为 GPT-6 Astra Max 的 7 倍），单任务成本 7.60 美元、比 Sonnet 5 高约 50%。

能做什么
实测数据 + 成本结构分析：agentic coding 能力跃迁（Terminal-Bench 4.0 70.6%）、工具调用/Shell 次数下降、迭代轮数减少；同时量化 Max 档下的 token 膨胀与单任务成本。
解决什么痛点

值不值得
如果你把 coding agent 放进 CI 或批量任务，这篇给的成本分层结论比官方口径更有用；注意它的数据来自第三方基准，真实任务集仍需自测。

何恺明团队 NAT-ARC：纯视觉方案做 ARC，单模型 63.4%、集成 70.2%

论文提出 NAT-ARC，用纯视觉方式解 ARC 抽象推理：预训练只用 ImageNet 的自然图像（猫狗花草），完全不使用 ARC 的彩色格子，再把学到的视觉能力迁移到格子推理上。单模型在 ARC-1 上 pass@2 达 63.4%，集成后 70.2%，是纯视觉方案首次逼近专用 LLM 系统的水平。

能做什么
把 ARC 当作视觉任务而非符号/文本推理：ImageNet 预训练 encoder → 迁移到最大 30×30、10 色的格子变换推理，输出规则并应用。
解决什么痛点
主流 ARC 解法都把格子翻译成文本交给 LLM，语言接口未必适合本质是视觉模式的变换推理，且依赖大规模 LLM 推理成本。
值不值得
值得看它「不用 LLM 也能逼近专用系统」的结论——对抽象推理是否必须靠语言这个假设是一个反例；学术性强，短期没有工程落地路径。

「AI 生成网页文本」占比首次量化：2026 年 6 月 27.5%，8 月升到 31.1%

论文用 Pangram 对通过 FineWeb 质量过滤的网页文本做标注，发现 2026 年 6 月的数据里 27.5% 的 token 由 AI 生成，8 月升到 31.1%。作者进一步给出「一个 AI token 值多少」的缩放律，讨论 AI 生成文本混入预训练语料后的边际收益衰减，以及它与有意合成的数据在性质上的差异。

能做什么
对真实网页语料做 AI 生成标注 + 缩放律分析：量化 AI 文本占比随时间上升，并估计这类 token 在继续预训练中的价值衰减。
解决什么痛点
