Gemini 4 Hydrogen 落地：执行型模型 + Antigravity Orchestrator 在会话内按任务换模型

Thinking Machines 开源 Inkling 2 Small：594B/17B MoE、1M 上下文，vLLM 当天支持到 TP4 630 tokens/s

Inkling 2 Small 是文本+视觉 MoE，594B 总参 / 17B 激活，上下文最高 1M，权重里自带 DSpark 推测解码头（5 层、每步草拟 7 token）。vLLM 做到 day-0：TP4 下最高 630 tokens/s/user、接受长度 3.5，同时支持 LoRA。结构上沿用 Inkling 主干（5:1 滑窗/全注意力、GQA 加学习式相对偏置取代 RoPE、每层 4 个短卷积、sigmoid 路由 MoE），新增块注意力残差、逐头门控与 per-token attention sink，图像编码器换成 23 层 ViT；48 层里前 40 层专家用 NVFP4、后 8 层用 MXFP8，NVFP4 采用 Four-Over-Six 双候选块缩放。

能做什么
594B/17B MoE + 1M 上下文 + 原生视觉，day-0 在 vLLM 上以 TP4 跑到 630 TPS/user，带 DSpark 投机解码与 LoRA；专家层做 NVFP4/MXFP8 分层量化。
解决什么痛点
大 MoE 多模态模型常常「发布即等待」——框架适配滞后几周，期间只能跑未优化路径；整模型统一精度又会把显存和带宽吃满。
值不值得
两个可借鉴点：一是「模型厂 + 推理框架同日交付」已成发布标准动作；二是按层混用精度（前 40 层 NVFP4、后 8 层 MXFP8）是可复用的部署手法。限制在门槛——TP4 起跳、1M 上下文对 KV cache 压力大，自建要按显存倒推并发。

按需升精度：权重存 8bit、默认用高 4 位解码，只在输出分布不确定的那一步重算

论文换了个分配方式：权重存 8bit，解码时只用高 4 位，只有当低精度输出分布看起来不确定（熵超阈值或 top-2 边际过小）才把这一步按 8bit 重算。模型是 Qwen3-0.6B，基准 GSM8K，成本按每 token 读取的权重字节计。在 36724 个回放步上，低精度熵预测 argmax 翻转的 AUC 为 0.93；给 15% 升精度预算，熵门控抓到 78% 的翻转、边际门控 94%。150 道实测题里全高精度 64.0%、全低精度 55.3%（McNemar p=0.053）；16% 升精度率的熵门控得 62.7%，权重字节为全高精度的 0.87。作者明说 live 数据尚不能把门控与两端区分开（配对差 p=0.080），随机对照、思考模式阶段规则与第二模型都没跑。

能做什么
把「精度」从全局常量变成逐 token 决策：8bit 存储、4bit 解码、熵/边际门控触发单步升精度，用「每 token 权重字节」统一度量成本收益。
解决什么痛点
本地/边缘小模型固定精度跑全流程：要精度就得全程 8bit（带宽翻倍），要速度就全程 4bit（关键步算错无法挽回）。
值不值得
机制干净、指标诚实（作者把不显著的结果写出来了），适合作为「动态精度」方向的入门读本。但结论仍弱：0.6B 模型 + GSM8K 单基准，实测差异不显著，离能上生产还有距离。

Claude Code 2.1.323 加入实验性 Code Mode：Claude 写 JavaScript 调工具，不再一次一个 tool call

2.1.323 新增实验性 Code Mode：Claude 改为写 JavaScript 来调用它的工具，需在 code.claude.com 显式开启，也可按组织关闭。同版给 plugin.json 加 engines["claude-code"] 版本区间，超出区间的插件不安装、不更新、不加载，安装时自动挑最新可用版本；claude plugin validate 增加对插件 TypeScript hooks 模块的类型检查（--strict 下失败即报错）。另有 30 秒进度心跳，避免 claude -p 与 SDK 会话里长 hook 被宿主判成挂死；Artifact 支持 .docx；并修了一批 Bash 权限绕过（如 rm 在错误目录下判定、Bash 沙箱中途被关）与多账号 sign-in 串号问题。

能做什么
Code Mode 把多步工具调用压成一段程序（循环、分支、中间变量），减少模型往返；插件侧加版本门与 hooks 类型校验，权限判定补了若干绕过。
解决什么痛点
长链路 agent 每调一次工具就要一次往返、把结果塞进上下文，步骤一多延迟与 token 双爆；插件版本不匹配会静默装坏；权限判定错目录会放过危险删除。
值不值得
「用代码调工具」是今年 agent runtime 最明确的方向之一（省 token、可组合、可复用逻辑），值得在自己的 harness 里对照试验。限制：实验特性、要显式开、组织级才能关，Code Mode 下的沙箱与权限模型还没有公开细节。

Agent Sandbox v1.0.11：沙箱路由支持浏览器路径前缀，sandboxd 收紧文件与终端边界

K8s SIG 的 Agent Sandbox 发布 v1.0.11，把沙箱进一步当成「可路由的服务」：sandbox-router 新增浏览器路径前缀路由（/<prefix>/<namespace>/<id>/<port>/，可跑自带 base URL 的 JupyterLab 类应用），并默认重写上游 Set-Cookie 与 Location 到前缀之下（可用 --path-routing-rewrite-responses=false 回退旧行为）；新增 router-tunnel 连接（经 port-forward 把 REST/gRPC 打到 sandboxd）与 X-Sandboxd-Token 头认证，适配会剥掉 Authorization 的代理。sandboxd 侧修三处边界：文件传输以 O_NONBLOCK 打开并拒绝 FIFO 与设备文件、DELETE 只删符号链接本身、PTY stdin 收到 EOF 不再关闭主终端。控制器修了 Pod 正在终止时 Sandbox 仍报 Ready=True（改报 Ready=False/PodTerminating）与 Retain 策略下过期 SandboxClaim 遗留 warm Sandbox。

能做什么
把沙箱变成可前缀路由的 HTTP 服务 + 可隧道接入 + header token 过代理认证；文件/终端接口对 FIFO、设备文件、符号链接做了明确拒绝；warm pool 与 claim 生命周期补漏。
解决什么痛点
多租户 agent 平台里，浏览器型工具（Jupyter、VNC）没法经沙箱路由暴露；代理剥 Authorization 导致认证失败；FIFO 或指向目录的符号链接会让文件接口挂死、甚至误删数据。
值不值得
自建 agent 沙箱平台可直接对标：路径前缀 + tunnel + token 三件套就是「多租户下安全暴露沙箱内 Web 工具」的完整答案。限制：仍在 1.0.x，响应重写默认开启属破坏性变更，升级要评估；Nitro on EKS 示例绑 AWS。

OpenAI 新版 Usage Policies 11 月 20 日生效：模型路由与 AI 网关须先获审批

OpenAI 重写的 Usage Policies 于 2026 年 11 月 20 日生效，影响面最大的是访问层而非内容层：任何让第三方直接使用 OpenAI 模型的服务——模型路由（model router）、AI gateway 之类——必须先取得 OpenAI 的审核与批准；应用把模型用在自己功能内部不在此列。新增 SafetyIDs，用于区分终端用户而不让 OpenAI 获知身份；同时澄清禁止用 OpenAI 模型与输出训练替代模型、禁止抽取受保护的推理过程、高风险自动化必须保留人工复核，并把国家安全与执法用途纳入审批范围。10 月 21 日宣布，11 月 20 日前旧版仍生效。

能做什么
给「模型访问中间商」加了一道准入：router/gateway 类服务需 OpenAI 审核批准并承诺同等防护、配合调查违规、协同执法；同时用 SafetyIDs 做终端用户区分。
解决什么痛点
多模型聚合网关、API 转售、二次分发这类形态此前处在条款灰区；一旦被认定为 router/gateway 而未获批，服务合法性直接受挑战。
值不值得
对自建多用户 agent 平台是硬约束：若你的网关对外提供模型直连（而不是把模型藏在自有功能里），20 日前要判定自己是否落在定义内。共享账号、代充、多租户转发的风控设计也要同步过一遍。

DeepSeek-V4.1-Flash 搬上 Vera Rubin NVL72：单卡 1.7M tokens/s、单用户 387 tokens/s，官方口径 58× GB300

Kueue v0.20.6：修 v0.20 升级后 apiserver watch cache 初始化失败与配额虚占

补丁版最要紧的是升级路径：v0.20 起 Kueue 不再提供 kueue.x-k8s.io/v1beta1 的 /convert 转换 webhook，而 ClusterQueue、Cohort、LocalQueue、MultiKueueCluster、Workload 这些 CRD 仍配置着它，导致 kube-apiserver 反复初始化 watch cache 失败。同批修 kueuectl create clusterqueue 拒绝合法配额值（如 cpu=1e-3、资源名 foo--bar.example.com/gpu）、DQO 聚合超过 64 种资源后残留 stale capacity、超过 32KiB 的 Distributed 条件消息被 apiserver 拒收，以及弹性 scale-up 时 workload slice 与其替换体被同时计费导致用量瞬时超配额。

能做什么
一批升级与记账修复：watch cache 初始化、配额值解析、DQO 容量聚合、长条件消息截断、弹性切片重复计费。
解决什么痛点
从 v0.20 之前升上来的集群会遇到 apiserver 刷错、队列对象读不到；配额虚占让队列看似满了却没人能跑。
值不值得
跑 Kueue 的集群建议升级，尤其从 v0.19 跨到 v0.20 的。升级前按 release notes 核对 CRD 是否仍挂着旧 conversion webhook。
