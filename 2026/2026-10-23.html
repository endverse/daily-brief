🔥 今日重点

Anthropic 把 Agent Skills 捐给 AAIF：skill 规范交给 Linux Foundation 托管，MCP 之后第二个

Anthropic 宣布把 Agent Skills——给 agent 提供专门知识与流程的开放标准——捐给 Agentic AI Foundation（AAIF）。AAIF 是去年由 Anthropic、Block、OpenAI 共同创立、挂在 Linux Foundation 下的基金会，MCP 规范此前已捐到同一处；官方理由是让 skills 保持「开放、社区驱动、厂商中立」。Simon Willison 当天写链接帖，翻出自己去年 12 月的判断（当时就推断 skills 会进 AAIF，因为 MCP 已先去），并提到他是用自己博客的 datasette-mcp 让 Claude 检索旧文才翻到这段预测的。

🔎 新闻要点：Agent Skills 标准捐给 AAIF（Linux Foundation 下、Anthropic/Block/OpenAI 共同创立）；MCP 规范此前已捐入同一基金会；官方措辞为「开放、社区驱动、厂商中立」；规范治理与后续演进转入基金会流程。
🔥 今日重点

Google 详解 Agent Compute Engine：每个 agent 一个微 VM，沙箱内零凭证、无网卡，空闲时 checkpoint 到零资源

Google Cloud 首次系统讲 Agent Compute Engine 的设计：每个 agent 会话跑在一个单租户 microVM 里，启动是容器速度、隔离是 hypervisor 级，从而同时满足「要 root 与完整运行时」和「不能信任里面跑的模型」两个要求。安全模型是「假设攻击者已完全控制沙箱」——microVM 内没有任何持久凭证（无 API key、OAuth refresh token、服务账号密钥），不能访问云实例 metadata server，只拿一张 session 级 SPIFFE 证书和短时 token；沙箱没有标准网卡与默认网关，所有流量走 virtio-vsock 到本地无特权代理，再到节点外的 Agent Gateway。成本侧靠「空闲即近零」：agent 大部分时间在等模型或等人，运行时一旦进入 thinking 阶段就 checkpoint，唤醒时 restore，配合 DAX 直映射 + Copy-on-Write 共享基础镜像的物理页，官方称单机能承载比传统 VM 多几个数量级的存活 agent。

🔎 新闻要点：每会话一个单租户 microVM；沙箱零凭证 + 无 metadata server 访问 + 无标准网卡（仅 virtio-vsock → 本地代理 → Agent Gateway）；四种身份（用户 / 用户授权的 OBO 委托 / SPIFFE agent workload / agent 自有 workforce），网关校验「用户委托 + agent 身份 + 节点身份」三元组并做在途 token 替换；Titan + Titanium IPU 承载硬件根信任，宿主机 dm-verity 只读根文件系统、无持久状态；空闲 checkpoint、DAX + CoW 共享页面。

claude-howto 冲上 GitHub Trending 首位：给 Claude Code 补一份「按依赖顺序学」的模板库，4.3 万星

luongnv89/claude-howto 是 MIT 协议的 Claude Code 教程库，用 Mermaid 图与可复制模板把 slash 命令、hooks、记忆、subagent、skills、MCP 串成有先后顺序的学习路径，按「15 分钟入门 → 按角色进阶」组织，另附 CATALOG.md 全量特性索引；仓库目前 43,194 stars，README 提供中英日越乌克兰五语版本，标注对应 Claude Code 2.1+、自身版本 2.1.302。它明确针对官方文档「讲特性但不讲怎么组合」的缺口，示例从 hello-world 级升到带记忆、子代理与安全扫描的 code review 流水线。

能做什么
把 Claude Code 的能力按依赖关系排成路径（命令 → hooks → 记忆 → subagent → skills → MCP），每步给流程图和可直接拷进项目的模板，并说明哪些功能该组合使用、组合后解决什么场景。
解决什么痛点

值不值得

紫荆智康「AI 医院」升级多分身协同：多专科医生分身同时坐诊，意见冲突在界面上高亮

清华 AIR 孵化的紫荆智康把「多学科人类-Agent 协同」做进门诊流程：医生照常问诊，系统从患者持续补充的信息里识别需要哪些专科参与（例如甲亢患者提到哮喘史就引入呼吸科分身），以提醒方式把对应分身意见呈现给医生；对已明确需要 MDT 的病例，多个分身直接围绕诊断、用药给建议，系统分别展示各分身意见并高亮不一致之处，医生能看到意见来自哪个分身再结合依据做最终判断。平台对标的是微软 Healthcare Agent Orchestrator 这类医疗智能体编排系统。

能做什么
把多学科会诊从「挂多个号再凑一次 MDT」变成门诊过程中的实时旁路：分身按患者新信息被动触发、并行给意见，界面保留每个意见的来源与分歧点，形成可追溯的决策建议链。
解决什么痛点
MDT 在现实里是稀缺资源——患者要跑多个科室、等会诊排期，疑难重症之外基本享受不到；而单一大模型给建议时会掩盖科室间分歧，医生无法判断该信哪一条。
值不值得
值得看的是「分歧显式化 + 来源可追溯」这个交互设计，它比「AI 替代医生」的叙事务实得多；但它属于厂商案例、没有公开的对照数据（准确率、误诊率、医生采纳率），医疗场景的合规与责任边界也未展开，短期更适合当产品形态参考。

GitHub 用 AI 把 Copilot 运行时从 TypeScript 重写成 Rust：83 万行、14.5 周，启动交互 5.25s → 292ms

GitHub 把 Copilot CLI、Copilot 应用与 Copilot SDK 背后的运行时从 TypeScript/Node.js 迁到 Rust，AI 辅助重写替换超过 80 万行代码，耗时约 14.5 周、128 个 PR，迁移期间照常发版（共 135 个版本，35 稳定 + 100 预发布）。客户端启动、会话创建与单轮交互从 5.25 秒降到进程内嵌入后的 292 毫秒；旧实现依赖 Node 与 V8、靠进程边界与宿主通信，每个客户端约多 100MB 工作集内存。最终运行时含 832,378 行生产 Rust 与 468,689 行 Rust 单测，临时 N-API 兼容层移除前有 2,019 个导出、3,356 处 TypeScript 调用点，4,478 次 cargo check 中 87.1% 一次通过。

能做什么
给出了「用 agent 大规模重写生产运行时」的可核查流程：增量替换而非一次性切换，每换一个组件用临时 N-API 互操作层桥接，使既有端到端测试在新旧混合状态下仍可跑；Rust 侧通过 C ABI 直接嵌入宿主应用，也保留独立进程模式，SDK 覆盖 TS/Python/Go/.NET/Java/Rust 六种语言。
解决什么痛点
Node/V8 + 进程边界带来的启动 5.25 秒与每客户端约 100MB 工作集，对「随手唤起」的 CLI/IDE 集成是硬成本；而一次性重写 80 万行在多团队并行发版的仓库里几乎不可能。
值不值得
这是目前最值得复盘的 AI 重构样本：真正的方法论是「AI 生成 + 编译/测试/人工评审兜底」和「增量集成保住测试」，而结论同样重要——取消、重试、背压这类行为回归编译期查不出来，社区质疑正集中在边界行为。若要复用到自研 agent 运行时，先按季度估迁移成本，再决定是否值得。

Snowflake Cortex AI Gateway 公测：单端点收口模型与 MCP 工具，动态路由把 dbt 流水线 token 效率提到 3 倍

Snowflake 的 Cortex AI Gateway 进入公开预览，定位是企业 AI 技术栈的集中控制面：一个端点代理 OpenAI、Grok、GLM、Gemini、Llama、Mistral、DeepSeek（Chat Completions）与 Claude（Messages API），流式、工具调用、结构化输出、prompt 缓存、图像输入与推理都按原生语义透传，客户端只需换 base URL 和一个 token（如 `snow ai opencode` 一条命令接管 OpenCode 流量）。访问控制复用 Snowflake RBAC，管理员决定哪些模型可被调用；私有预览中的动态模型路由按 agent 每一步选「能可靠完成且最便宜」的模型，内部评测里 dbt Pipeline 负载在质量相当下 token 效率最高 3 倍，另一项编程测试在 PR 吞吐不变的前提下 token 用量降约 25%。

能做什么
把「谁在调哪个模型、调了什么、花了多少」收进一个控制面：统一端点 + 统一凭证 + 统一计费归因，同时代理模型调用与 MCP 工具调用，并在每步做成本感知的模型选择；平台团队管策略，应用团队只对接一个端点。
解决什么痛点
企业 AI 技术栈碎片化的典型症状是访问路径爆炸——每个 agent、每个脚本各自持有 provider 凭证、各自出账、各自记日志，导致模型调用不可见、成本不可归因、权限不可收紧；而收紧权限又会把人推向未批准的影子 AI。
值不值得
方向对得上任何要做「多模型 + 多 agent」治理的平台：把 gateway 做成控制面而不是简单代理，是能同时解决可见性、成本与合规的少数位置。限制是要接受 Snowflake 作为控制面（绑定其账号与 RBAC），且动态路由还是私有预览、3 倍/25% 都是厂商内部评测。

Qwen 团队的 FlashQLA：把 GDN 线性注意力的四算子融成一个，用序列并行补上并行度短板

阿里 Qwen 团队在 AICon 2026 深圳站讲了 FlashQLA——面向 GDN（Gated Delta Network）线性注意力的高性能 GPU 算子库。主流模型已转向「线性注意力 + softmax」混合架构（Qwen 三层 GDN 配一层 softmax，Kimi K3 用三层 KDA 配一层），但 GDN 的 chunk 递推有强数据依赖：每个注意力头只能开一个 CTA、占一个 SM，而 Qwen 小模型的线性注意力头数约 32、H100/GB 系列有上百个 SM，利用率被卡死；同时 FLA 的四算子实现会把 W/U/S 中间量反复写回 HBM，纯耗带宽。FlashQLA 用 WY representation 把递推改成 chunk=64 的矩阵乘，利用「相邻 chunk 状态差可由 dK×dK 矩阵递推」的性质做序列并行矫正，再用手写 warp specialization 替代 Triton 编排流水线。

能做什么
把线性注意力的 prefill 从「逐 token 递推」变成可并行的 chunk 矩阵乘：序列切开后各段独立算矫正矩阵，最后一次乘法完成矫正；算子融合后不再把 W/U/S 落 HBM；warp specialization 让矩阵乘、递推、输出三阶段按硬件单元分工流水。
解决什么痛点
混合架构把大部分层换成线性注意力，本意是省掉 O(N²)，但实现层面撞上并行度（头数 32 vs 上百 SM）与带宽（中间量往返 HBM）两个瓶颈，长序列 prefill 反而跑不满卡，也让 TP 切分更难。
值不值得
对自建推理栈的人是硬货：它解释了为什么同样的 GDN 模型在不同 kernel 实现上差几倍，以及序列并行并不是「切完再拼」那么简单。门槛在工程——手写 CUDA 级别的 warp specialization 需要团队有能力跟上游 kernel 演进，且结论强绑 Hopper/Blackwell 这一代硬件。

Open WebUI v0.12.3：聊天端到端加密（MLS）落地，Redis 流式改为按 key 追加

Open WebUI v0.12.3 最实质的改动是把 DM 与私有群聊的端到端加密做成产品功能：成员在频道菜单发起 Encrypted Chat，消息在浏览器内用 MLS 加密、单条上限 16 KiB、只经服务器透传不落库，离开或刷新即清空，成员与权限变化时自动结束，参与者可互验短码；管理员在 Admin Settings 开启并受新的 Encrypted Channels 权限控制，要求 HTTPS 且关闭 websocket 服务端日志。另有 Redis 流式优化（每条回复独立 key 追加，不再重写共享 hash；每个实例只订阅本机用户的 room）、Google Drive 改为只申请用户挑选的文件权限（从而免掉受限 scope 审核）、以及给 skill 加读取上限（SKILL_CONTENT_MAX_CHARS 默认 20000、预览 5000）。

能做什么
给自托管 LLM 前端补上两块企业常问的能力：一是 MLS 组密钥的端到端加密会话（服务器只转发密文，不落库），二是 skill 注入的字符预算控制，避免长 skill 一次吃掉上下文；顺带把 Redis 流式与共享搜索做轻。
解决什么痛点
自托管场景里「聊天要能证明服务器看不到」是硬需求，但多数前端只有 TLS 没有 E2E；另一个真实痛点是 skill/知识文件越写越长，模型每次全量读入既费 token 又挤掉对话预算，需要按字符设上限。
值不值得
如果你在用 Open WebUI 做团队入口，这个版本值得升：E2E 加密与 skill 读取上限都是能立刻用上的增量，升级风险主要在反向代理需支持 websocket 且要关服务端日志。注意 E2E 只覆盖临时会话（离开即清空），不是持久加密存档。

中国电信开源 Xing4.0-29B-Intent：意图理解 + 参数抽取一个模型做完，输出几十 token、百毫秒级

星辰通用人工智能实验室开源意图理解专用模型 Xing4.0-29B-Intent，同时放出 275 万条训练语料、模型权重与推理镜像。它把「做选择题」（类型化决策）和「做填空题」（参数抽取）合成一个任务，用 USP（统一 Schema 驱动语义解析）以「类别 + 参数」层级输出 JSON——「把卧室的灯调成暖黄」直接给出房间、设备、目标状态，一句话含多意图、多参数、多实体也能一次解析。相比通用模型先长篇推理再解析，它只输出决策所需字段，平均几十 token、完整响应百毫秒级；评测从 48 个中英文公开数据集抽 6000 题，覆盖意图理解、实体识别、关系抽取、事件抽取，已在电信万号客服、智能家居音箱上做工单路由与口语指令解析。

能做什么
把「自然语言 → 业务系统可执行的结构化参数」做成单次前向：统一 schema 约束字段与类型，输出可直接校验的 JSON，异构任务（意图/实体/关系/事件）共用一套输入输出格式，下游接入与迁移成本低。
解决什么痛点
高频业务调用里用通用大模型做分类与抽取，既贵又慢：长推理对「工单转给谁」这类问题毫无意义，自由文本输出还要下游解析纠错，同一问题能出现十种说法。
值不值得
对客服、工单、IoT 指令这类「场景收敛、选项固定、调用量大」的场合，专用意图模型确实比通用模型划算，且这次连语料都开源了，可以直接微调。限制是 29B 的自托管成本与长尾意图的泛化——先拿自家真实话术做一版评测再决定，不要只看公开数据集分数。

Quant-Arena：A 股真实数据上的端到端量化研究基准，9 个前沿模型没一个跑赢等权市场

Quant-Arena 把量化研究的完整闭环作为评测对象：模型自己构造特征与选股代码，只在 2022–2023 数据上获得反馈，然后必须冻结一个策略，在封存的 2024 年上评估。评估器是现金账户模拟，计入交易约束、成本以及由模拟订单簿估算的市场冲击；分数以已实现的超额收益为主，辅以信号质量与策略所用特征的多样性。九个前沿模型中 GPT-6 Astra 得分最高，但在 2024 年没有任何模型跑赢等权市场；榜单对外开放，任何模型或 agent harness 都可提交。

能做什么
把「LLM 能不能做量化研究」从主观 demo 变成可复现的协议：固定可见区间与封存年份、冻结策略防过拟合、按真实交易约束结算，并对特征多样性单独计分，避免所有模型收敛到同一批因子。
解决什么痛点
现有基准只测公式、代码或单笔交易决策，无法回答「这个 loop 跑完能否产出在样本外有效的策略」；而量化研究恰恰是全流程问题，任何一步（特征、回测、取舍）出错都会让样本外失效。
值不值得
对量化从业者这是少见的「说真话」的基准：结论（无模型跑赢等权）比任何正向结果都更有信息量，且协议本身可以直接借用来做内部 agent 评测。限制是单市场（A 股）、单一年份（2024）、市场冲击来自模拟订单簿，绝对结论不宜外推；另外它是 arXiv 预印本，未经同行评审。

蚂蚁数科发 LingDT-Decision-1.0：4B/27B 决策模型，客服场景 token 降 90%、风险识别 76%→89%

蚂蚁数科发布决策模型 LingDT-Decision-1.0，提供 4B 与 27B 两档，面向智能客服、安全风控、金融等企业场景，处理意图识别、任务分类、工具选择与风险判断这类结构化决策，已上线 DTMaaS 平台限时免费体验。官方数据：数据标注场景相比 DS-V4-flash token 消耗降约 97%、速度提升约 10 倍；智能客服场景相比 Qwen-3.7-flash token 降约 90%、风险识别准确率从 76% 提升到 89%；23 项开源基准上 27B 版综合评分超过 Microsoft-Decision-1、Jev 1.13.0 与 Fastino/GLiDE。除单选/分类评级外还加了原生多选与按序决策，用于复合意图与存在依赖关系的任务链。

AWS Continuum 代码漏洞服务 GA：先证明可利用再修，给攻击路径与爆炸半径而不是一个分数

AWS Continuum for code vulnerabilities 正式 GA：它把代码仓库与 AWS 环境（账号内的 collector 采集 AWS Config 资源与网络配置）合成一张上下文图，判断某个漏洞在网络与实际可达资源上是否真的可利用，并给每条结论标注证据等级；能复现的漏洞会在隔离沙箱里跑通 exploit、附 PoC 与复现步骤。输出不是 CVSS 分数，而是攻击路径、源码分析与爆炸半径评估，同时评估既有防护能否拦住这条路径；修复以代码补丁、依赖升级或 PR 形式提交，默认「提出 → 人工批准 → 才发布」，未来才允许在护栏内自主执行。

能做什么
把漏洞处理从「按分数排队」变成「按可达性排优先级」：结合代码路径与云上资源/网络上下文证明可利用性，给出攻击链与影响范围，并生成可审的修复补丁或 PR。
解决什么痛点

值不值得
方向值得跟：把「可利用性证明 + 爆炸半径」做成服务输出，比再做一个扫描器有价值。限制是强绑 AWS 环境（collector 只能看 AWS 侧资源），非 AWS 资产等于半盲；且默认人工批准意味着它省的是分析时间而不是决策责任。

CNCF 实测：一次 Claude Code 小任务产生 181 条遥测、289KB JSON，用 Collector 双流水线砍掉大头

CNCF 博客给出一组实测：让 Claude Code 修两个失败测试并补边界用例，全开内容开关后一次运行产出 181 条遥测记录、289KB JSON。问题在于默认埋点是按「调试单次运行」设计的——工具内容同时落在 span event 与 log 里（一次 Write 把整个文件存两份），指标按 session.id、user.id、user.email 和两个账号 id 打标签，25 个会话就让 8 个指标膨胀到 300 条时间序列。作者的做法是在 OpenTelemetry Collector 里用同一个 OTLP receiver 扇出两条流水线（原样 vs 优化），优化侧加过滤、去重与属性上提，两条都进同一个 Grafana LGTM，用红绿两条曲线直接量出省下的存储。

能做什么
把 agent 遥测从「全量落库」改成「先整形再发」：在 Collector 里丢弃不承载告警/看板价值的内容字段、把高基数属性从指标上提到 resource、对重复的 span event 与 log 去重，同时保留回答「跑了哪些工具、花了多少 token、哪一步失败」所需的计数与短属性。
解决什么痛点
agent 遥测天然高基数高体积：内容字段（prompt、文件体、diff）对排障有价值但对趋势分析无用，却占据绝大部分字节；session/user 级标签制造永不回收的时间序列，存储与索引成本随用量线性上涨。
值不值得
如果你正在给 coding agent 接可观测性，这篇给了可直接复用的对照方法（同一输入扇出两条流水线量差），比任何「降本 N%」的宣传都实在。注意它只解决管道侧整形，不解决「哪些字段该留」的治理问题——那需要先和看板/告警对齐。

能做什么
修掉两个运维期才会暴露的坑：ambient 模式下节点过早解除 not-ready 污点导致流量落到 ztunnel 未就绪节点；istiod 长期缩容后自签 CA 过期无法启动（现在自动用私钥续期，无需人工重建 secret）。
解决什么痛点
前者造成「pod 起来了但流量黑洞」，排查方向容易误判到 CNI 或应用；后者会让「按需缩容省钱」的策略在恢复时直接卡死控制面。

能做什么

值不值得
如果集群里 Kyverno 策略数量可观（尤其 CEL 策略），这是低风险高收益的补丁版：改动集中在热路径与 bug 修复。升级后建议对比 apiserver 的 admission 延迟指标确认收益，并把分配回归测试纳入自家 CI。
