🔥 今日重点

OpenAI 发布 GPT-6 家族落地指南：从选型、推理强度到 skill 与工具编排

OpenAI 发布面向团队的 GPT-6 家族落地指南，围绕「选哪个模型、怎么配推理强度、怎么写 prompt 与 skill、怎么编排工具、怎么把工作流推上生产」给出官方建议。指南确认 GPT-6 Astra 与 GPT-6.1 Sol 不支持 none 推理档，最低为 low；reasoning.effort 可取 low / medium（默认）/ high / xhigh / max 五档。工具调用建议走 Responses API，Chat Completions 仅在无工具的请求下可用。官方给出的调参路径是：先用默认推理强度，只在任务需要更深规划或分析时才逐级上调，以便在延迟、token 成本与效果之间取平衡。

要点：①按任务所需的推理深度、速度与成本选模型；②推理档 low→max，Astra/Sol 不支持 none，minimal 需从 low 起步对比；③prompt 与 skill 协同、工具编排建议用 Responses API；④给出从原型到生产的迁移与治理建议。
🔥 今日重点

DeepSeek 开源华为昇腾全套基础设施组件，与英伟达版接口一一对应

DeepSeek 正式开源面向华为昇腾算力平台的全套基础设施组件，涵盖 TileLang 昇腾版高级语言/编译工具、计算库与分布式通信库，所有组件与此前英伟达平台版本在接口层一一对应。本次开源的组件包括 DeepGEMM（通用矩阵运算加速）、DeepEP（大规模跨设备通信）、TileKernels（向量计算与访存算子）、FlashMLA（稀疏注意力）与 DeepSelect（数据筛选）；多项关键测试中，其计算与通信性能已接近硬件上限。TileLang 昇腾版封装 Ascend C 底层指令，提供高级语言编程方式且不损失硬件性能，DeepSeek 训练中用到的每个 TileLang 算子在昇腾上都有对应的高性能实现。此举意味着前沿大模型训练在软件栈层面不再唯一依赖 CUDA/英伟达。

要点：①覆盖编译工具 + 计算库 + 分布式通信库三大层；②组件与英伟达版一一对应，降低换芯迁移成本；③TileLang 已承载 DeepSeek V4 系列训练的大部分算子；④昇腾已启动核心算子开发，国产 AI 芯片生态加速成型。

AutoCompact：训练编码 agent 自己判断「何时压缩上下文、保留什么」

AutoCompact 是一个面向长流程编码 agent 的上下文管理方法：让 agent 自己学会「何时压缩上下文、保留哪些工作状态、压缩后如何继续」，而不只是被动防止上下文溢出。论文指出，随着任务推进，早期的代码探查与搜索会逐渐过时，因此上下文管理的关键不是「塞不塞得下」，而是「该丢什么、该留什么」。方法通过训练编码 agent 来做这一决策。

能做什么
训练编码 agent 自主决定压缩时机、保留的工作状态与恢复方式，把上下文管理从「防溢出」变成「状态取舍」。
解决什么痛点
长任务里早期探索过时，窗口被无效信息占满，agent 易丢失关键状态导致后续步骤跑偏。
值不值得
做 coding agent / 长程任务框架的值得跟进；目前是论文方法，落地需自接训练管线，门槛中高。

论文：预训练 Transformer「想得太浅」，一个 rank-8 LoRA 补上深度推理

研究发现预训练 Transformer 只用了很浅的深度来处理上下文引用：13 个基座模型可靠跟随的引用行数仅 1.4–3.6 行，增加预训练循环也几乎无改善。作者在某早期层加一个任务训练的 rank-8 LoRA（冻结全部原权重），即可延长这段计算：Qwen3-8B 在 24 行链条上的精确率从 15.5% 提升到 99%，更长时间训练的 LoRA 可处理 50 行。

能做什么
用冻结主干 + 单层 rank-8 LoRA 延长模型的「深度计算」，显著提升长链条引用跟随（Qwen3-8B 24 行 15.5%→99%）。
解决什么痛点
预训练模型在长依赖/多行引用任务上过早「停止思考」，浅层深度限制推理。
值不值得
对做模型微调/长上下文推理的团队有直接参考；需自行复现训练，属研究阶段。

值不值得

AI21 Labs 采用 Google Cloud AI Hypercomputer 后，高优先级训练任务的等待时间从 72 小时降到 12 小时，每周人工调度干预从 20 次降到 0。该案例覆盖 Jamba 系列等基础模型的训练，说明托管 AI 基础设施在大规模训练调度上的一体化收益；AI21 现聚焦专用 LLM 与 agent 优化技术。

能做什么
托管 AI 超算（GKE/TPU + 调度）支撑大规模训练，高优任务等待 72h→12h、人工调度 20 次/周→0。

做 AI 平台/集群调度的直接对标案例；GCP 托管方案，自建集群可对照 Kueue/Volcano + 优先级队列。

GKE CPU startup boost：不超配也能加速 Pod 启动

GKE 推出 CPU startup boost，在 Pod 启动阶段临时提升 CPU 配额以加速应用启动，稳态再回落到正常配额，从而无需长期超配资源。面向微服务应对突发流量、新版本发布、副本扩容等场景，目标是兼顾启动速度与成本。

能做什么
Pod 启动阶段临时给足 CPU、稳态回落正常配额，加速启动且不长期占资源。
解决什么痛点
应用启动时需要更多 CPU，长期按峰值配置会造成稳态超配、成本高。
值不值得
跑 GKE 且受困于 Pod 冷启动慢的团队可试；需在自身负载下评估效果。
