🔥 今日重点

智能体 Harness 三阶段演进：从链、图到代码化，LinkedIn 用「生成代码 + 验证」替换脆弱工作流

LinkedIn 把 agent harness 的演进拆成链、图、代码化三代，并给了各自的边界：链是固定 prompt 流水线，靠文本保真度传递、错误会级联；图用 LangGraph 把控制流显式化（条件路由、重试回退、状态管理、显式验证），配合 A2A 多 agent 与人在回路，撑起了招聘智能体 Hiring Assistant；代码化则把推理媒介从提示词换成可执行代码，沙箱 + 埋点 + 验证 harness + 迭代循环四件套，用「跑通/跑不通」的确定性取代对模型输出的信任。实践口径是：先用能可靠解决问题的最简单范式，别为了架构漂亮把线性任务做成代码 agent。

LinkedIn 工程团队梳理了 agent harness（围绕概率模型搭的结构化执行框架）的三个范式。第一代是「链」：他们早期的生成式 agent 用 LangChain 搭固定三步——路由（判断问题是否在范围内、交给哪个专家）、检索（必应/内部 API 建档案供 RAG）、生成（过滤与综合）；完全依赖上一步的文本保真度，一个上游错误级联到底，且没有系统性识别和自动修复的机制。第二代是「图」：用节点表示 LLM 调用/工具调用/验证，用边控制流程，把控制流变成显式可声明的东西，带来条件执行、重试回退、状态管理、显式验证；多 agent 由顶层编排器管理，靠 A2A（ACP 已并入 A2A）做异步通信，人在回路（HITL）负责关键决策点；LinkedIn 复用自家消息系统实现 FIFO 投递与持久重试来做长耗时任务编排，并把认知记忆做成一个独立 agent 供业务 agent 集成，这套支撑了首个招聘智能体 Hiring Assistant。但它本质仍是人预先定义的工作流，状态空间一复杂，故障恢复、校验、边界处理都要手写，流程定义与评测框架越写越脆。第三代是「代码」：让 coding harness 在沙箱里生成、执行、优化代码，靠「编译/运行通过与否」的确定性拿到紧反馈回路；架构含四个组件——执行沙箱、埋点与日志、验证 harness（单测/断言/检查规则）、迭代优化循环。LinkedIn 用这套做了内部数据分析工具：把自然语言问题编译成声明式 SQL + 命令式 Python，在样本数据上执行，按隐私/可见性/合规规则校验输出并循环到满足全部条件，省掉了定制提示词、工具、工作流图和评估调优的工作量，可审计性与可复现性也更好。文章最后给的原则是：把 LLM 输出当不可信输入、把规划与执行解耦、把可观测性做进每一步、以及选「能可靠解决问题的最简单系统」——链适合线性任务（客服回复、文档摘要、内容审核），图适合需要分支/重试/显式状态的流程，代码 harness 适合输出可被测试或编译验证的场景。
🔥 今日重点

Kubeflow Trainer v2.4.0 正式版：TrainJob 接入 DRA，工作负载感知调度进 Phase 1

Trainer v2.4.0 正式发布，把 TrainJob 接到 DRA 上（KEP-2782），并用 KEP-3015 落地工作负载感知调度 Phase 1，同时支持按 TrainJob 覆盖 schedulerName、终结时清理 Volcano PodGroup、多切片 TPU 的 Job Replicas。升级前要注意三条破坏性变更：MPI 插件换 PRTE_MCA_* 环境变量导致旧的挂起 TrainJob 无法恢复，ReplicatedJob 名限 20 字符，Helm 卸载改为保留 CRD。

Kubeflow Trainer v2.4.0 从 rc 转正式。核心是把训练作业接进 Kubernetes 的新调度原语：KEP-2782 让 TrainJob 直接使用 DRA（Dynamic Resource Allocation）申请设备，而不是靠扩展资源计数；KEP-3015 带来工作负载感知调度 Phase 1，并允许按 TrainJob 覆盖 schedulerName，从而在同一集群里分别走默认调度器、Volcano 或 Kueue 管理的队列；TrainJob 进入终结或挂起状态时会清理 Volcano 的 PodGroup，避免残留占配额。其余新增包括多切片 TPU 的 Job Replicas、Prometheus 监控 overlay、slurm-bridge 调度文档，OptimizationJob 控制器以 alpha 特性门控上线（Phase 1 的 HPO API 在 rc.0 已引入）。破坏性变更三条：MPI 插件改用 PRTE_MCA_* 环境变量，升级前创建且处于挂起状态的 MPI TrainJob（DeepSpeed、MLX 等）无法恢复，因为新环境变量加不进已存在的不可变 JobSet，必须先等它们跑完或升级后重建；ReplicatedJob 名字长度限制到 20 字符；Helm 卸载会保留 CRD（helm.sh/resource-policy: keep），不再连带 GC 掉集群里的 TrainJob。

StrataFlux：把主机内存和 SSD 当「额外精度层」，2-bit 权重下 AIME 从 11.0% 拉到 47.1%

针对低比特量化掉精度的老问题，StrataFlux 不放弃量化，而是把主机 RAM 与 SSD 里保存的高精度数据做成可按需流式回填的「精度层」：选择性精度流只传当前解码步真正需要的部分，传输与计算重叠，同一次取回的数据在后续解码步复用，生成不必等每次传输完成。实测 2-bit Llama-3.1-8B 权重把 WikiText-2 困惑度从 9.46 降到 8.40，同时保持量化基座 95.4% 的吞吐（RTX 5090）；2-bit 权重 + 2-bit KV 让 Qwen3-8B 的 AIME 2024/2025 从 11.0% 提到 47.1% 且显存不增；128K 上下文下 3-bit 权重 + 2-bit KV 做到与 vLLM 4-bit AWQ + 8-bit KV 相当的困惑度和速度，显存约省一半。

能做什么
在 GPU 显存之外开辟「精度层」：把高精度权重/KV 存主机内存与 SSD，按解码步选择性流式回填并与计算重叠，跨步复用；覆盖 2–4 bit 权重与 2–3 bit KV，在独显和统一内存平台上都验证过。
解决什么痛点
量化省显存但掉精度、offload 高精度数据又卡生成——尤其 2-bit 量化下推理模型（数学、长链）能力塌到不可用，而买卡升级显存成本最高。
值不值得
做私有化推理、显存受限又不想牺牲推理模型能力的场景值得细读，它说明「GPU 内精度不必是精度上限」；但实现依赖 SSD 带宽与调度栈，工程复杂度不低，短期更适合当技术路线参考而不是直接替换 vLLM 的量化方案。

用 SAE 拆 MoE：Qwen3-30B-A3B 的专家分工细到「Java 代码」与「前端代码」各一个

以往判断 MoE 专家职责靠统计它在领域标注语料上被选中的频率，粒度粗且只记录「被选中」不记录「贡献」。这项工作在 MoE 层输出上训练稀疏自编码器（SAE），利用「层输出 = 各专家输出的路由加权和、SAE 编码器是仿射变换」这一性质，把每个 latent 的 pre-activation 精确分解到各专家头上，从而给每个专家算出它主要驱动的 latent 集合。在 Qwen3-30B-A3B 的第 4、30、46 层上，贡献比门控集中得多，多数 latent 只有一到两个主导专家，自动解读后发现分工远细于粗粒度领域：Java 代码与前端 Web 代码、几何与算术/多项式都各有独立专家，而粗领域占用的专家数极不均衡。

能做什么
给出一种把 MoE 层输出按专家精确归因的方法（仿射分解），得到每个专家的主导 latent 集合，并在 30B 级 MoE 上给出层内分工的实证。
解决什么痛点
MoE 容量大但「哪个专家管什么」长期说不清，导致剪枝、专家并行放置、路由改造都靠猜；按选择频率统计既粗又会误判。
值不值得
做 MoE 推理部署或路由优化的可以看方法本身，它比「专家=领域」的直觉更能解释负载不均；不确定的是结论能否跨模型迁移，论文只给了 Qwen3 一个家族的三层。

同样数据、同样安全训练，换个随机种子越狱面就变：150 个 1B 模型的对照实验

论文问了一个评测方法论问题：jailbreak benchmark 通常只测一个 checkpoint，并把「哪些越狱能打穿它」当作预训练数据与安全训练的属性。作者对 25 组预训练数据配方各取 3 个随机种子训练 1B 基座，再对每个基座用 2 个种子做相同的安全后训练，共 150 个模型，然后对同一批越狱提示各采 20 条回复。结果是：把「相同数据 + 相同安全训练」重跑一遍，模型会栽在不同的越狱上——越狱成功率对随机种子敏感，单一 checkpoint 的结论不足以代表这条 pipeline 的安全水平。

能做什么
用 25 配方 × 3 预训练种子 × 2 后训练种子 = 150 个 1B 模型的受控实验，量化越狱鲁棒性对随机种子的依赖，每模型每提示采 20 条回复做统计。
解决什么痛点
安全评测与模型验收常以一个 checkpoint 的越狱成绩下结论，容易把随机方差当成 pipeline 的安全属性，导致发布判断和红队结论不可复现。
值不值得
做模型准入/安全评测体系时值得一看：它提示评测要按种子取分布而不是单点。但他只做到 1B 规模，大模型上方差是否同样主导，需要自己在目标尺寸上复现一遍才有结论。

04

Harness-S：不追求「最好的 harness」，而是让兄弟 harness 互相补失败样本

论文先给出 harness 演进的三条经验规律：局部性（变体各自的修补只覆盖部分失败）、互补性（不同变体修的是不同失败）、非平稳性（随着策略学习，某个 harness 变体的价值会变化）。据此提出 Harness-S：不再寻找一个普遍更优的 harness，而是让多个兄弟 harness 分工「救」基座执行系统的失败样本，再把救回来的能力蒸馏进单一策略，使其在原 harness 下仍然有效。配合方向性 harness 演进（directional harness evolution）生成专门化的变体。

能做什么
把「harness 工程」形式化为可学习的对象：用多个 harness 变体采集互补的失败样本，蒸馏回单一策略，结论是收益来自互补性而非某个万能 harness。
解决什么痛点
自研 agent 时常见做法是不断往 prompt/工具/流程里打补丁，越补越复杂且收益不叠加；也缺少判断「该改 harness 还是该训策略」的依据。
值不值得
做 agent 训练或 harness 迭代的值得读，尤其「局部性/互补性/非平稳性」这三条可以直接当评估 harness 变体的检查项；但属研究阶段，需要能改训练流程的团队才用得上。

SwarmEvolve：数百个廉价 agent 在 latent 空间里做进化搜索，3–8 分钟追平别人 60 分钟

LLM 引导的进化搜索（如 AlphaEvolve 一类）慢在每轮都要生成一大段文本思维链，为维持种群多样性还得反复生成。SwarmEvolve 让每轮几百个低成本 agent 分成 swarm、各自从不同角度看问题，在 latent 空间里推理而不解码成文本，通过传递 KV cache 共享信息；用隐藏状态向量之间的距离做新颖性过滤，交叉则靠一个 summarizer agent 接收全 swarm 的 KV cache 自然完成。在数学发现与科学计算的 21 个问题上平均分最高，达到其他 SOTA 框架 60 分钟才能拿到的最好成绩只需中位数 3–8 分钟；在若干问题上，用 Qwen3 8B 就超过了 AlphaEvolve 当初用前沿模型找到的解。

能做什么
以 KV cache 为通信介质的 agent swarm：latent 空间推理 + 距离度量的新颖性过滤 + summarizer 汇聚 KV 完成交叉，省掉每轮的文本解码成本，21 个问题上把收敛时间从小时级压到分钟级。
解决什么痛点
进化式程序搜索的成本几乎全在「反复生成文本思维链」上，导致要么种群小、要么跑得慢，用前沿模型跑一次动辄一小时。
值不值得
对做程序搜索/自动优化的团队有直接参考价值——省的是解码开销，换的是并发与迭代次数；但需要能改推理栈（KV cache 传递不是标准 API），且效果在数学/科学计算类问题上验证，业务型任务未必同样成立。

Terminal-Bench 2.0 自查发现约 30% 的题有问题，修完准确率涨 10 个百分点

论文提出「benchmark 维护债」：基准发布时校验得再好也会腐坏——模型变强后会给出被旧验证器拒绝的合法解，评测基础设施改动也会让题目内嵌假设失效，于是分数与实际能力越离越远。作者给出一套持续校验流程（社区报告、任务工件、agent trace、自动 oracle 检查、人工闸门修复），并对发布前已做过大量人工与 LM 辅助评审、红队的 Terminal-Bench 2.0 做审计：约 30% 的题被查出问题，修复版发布为 2.1。修复直接改变结论：准确率上涨超过 10 个百分点，排行榜位次最多移动三名（整体排序仍高度相关，Spearman rho = 0.958）。论文还证明资源预算本身就是测量规格的一部分：固定 wall-clock 时，延长时限能让 GPT-5.4 上 20 个百分点的 harness 差距消失，GPT-5.4 mini 上 30 个百分点的差距缩到 5 个百分点。

能做什么
一套可复用的 agentic benchmark 持续校验流程，并用它审计 Terminal-Bench 2.0（约 30% 题目有问题），量化修复对分数与排名的影响，同时把「时限/资源预算」纳入测量规格做敏感性分析。
解决什么痛点
内部拿 benchmark 选模型/选 harness 时，最容易踩的坑是题目本身失效或时限设死：分数差可能来自评测债和资源预算，而不是能力差。
值不值得
如果公司在用 Terminal-Bench/SWE-bench 这类基准做 agent 选型，这篇的 30% 缺陷率和「延长时限抹平 20pp harness 差距」两个结论，足以让你在下次评审时先质疑评测配置。可直接借鉴它的校验清单，成本不高。

tsrs：一个人指挥 Claude Opus 5.5 几周做出的 TypeScript 编译器 Rust 移植，单测 15,197 个全过

Cloudflare 联合 VoidZero 与 Owner.com 的 Max Schwenk 推出 tsrs——TypeScript 编译器的 Rust 移植，在 Oxc 工具链里孵化，与 TypeScript 团队合作，并声明不是 fork（语言设计仍由 TS 团队掌控）。移植过程不是手写：Schwenk 称自己一行代码没写，全程指挥以 Claude Opus 5.5 为核心的 agent，以 TypeScript 自身的 15,197 个一致性测试用例作为规格。官方称相同类型检查线程数下速度最高提升 8 倍、内存降约 70%，且能编译成 @tsrs/wasm 在浏览器或 Workers 上跑检查；Owner 37,000 文件的单体仓库，原本 TS 7.0 需 19 GiB 内存、80 秒，换成 tsrs 后 7 秒。第三方基准测得 5.3 倍加速、内存降 72%，诊断结果一致、生成代码逐字节相同，但发现 tsrs 遇类型错误以退出码 2 结束而 tsc 返回 1，足以悄悄打挂 CI；以 TS 7.1 beta 为基准时提升缩到 2.7 倍，说明 8 倍是相对旧版本的。目前仍是实验状态：不支持 watch 与语言服务器，--init/--showConfig 不可用。

能做什么
一个由 agent 主导完成的真实大型移植：15,197 个一致性测试当规格、Rust 重写类型检查器、可编到 WASM，带第三方可复现的加速与内存数字（5.3×/72%），以及退出码不一致这类兼容坑。
解决什么痛点
「AI 能不能做几万行级别的系统级移植」长期只有演示没有交付物；同时 TypeScript 类型检查在大型 monorepo 里确实是分钟级瓶颈，Go 重写（tsgo）之外的路线值得看。
值不值得
值得一读的理由不是让你换编译器，而是它给了「用测试集当规格 + agent 迭代」的一个工业规模样本，可直接类比到内部工具迁移项目；生产上先别用——实验状态、退出码差异会破坏 CI，且团队应先在 TS 7 上再迁 tsrs。

腾讯 Hy4 调用激增，WorkBuddy 十倍扩容：Agent 能力称开源模型第一

11 月 5 日腾讯宣布，因 Hy4 调用量激增，办公智能体 WorkBuddy 已完成十倍扩容；官方强调 Hy4 的 Agent 能力在开源模型中排第一。这条的实质是国产大模型在办公 agent 场景的负载侧信号——不是基准分数，而是接入产品后被迫扩容的实际并发。

能做什么
Hy4 上线后在自有办公产品里承压，腾讯用十倍扩容回应；官方口径把 Agent 能力定位为开源模型第一。
解决什么痛点
