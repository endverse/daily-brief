阿里云把云电脑做成「Agent 工位」：好未来两周部署约 1000 个 Agent，人可随时接管现场

在 1024 模力工场 AI 社区日上，阿里云把无影云电脑的位置重新定义为智能体的工位：Agent 在里面跑桌面软件和企业应用，不再只靠浏览器，对没有开放 API、只能点界面的老系统尤其关键；身份登录、数据范围、可执行操作和审计都沿用云电脑原有的 IAM 体系，不另起一套 Agent 账号。任务被登录失效、验证码或人工判断卡住时，云电脑保存当前状态、说明阻塞原因并通知人接管，人处理完再由 Agent 接着跑，不必从头重来。落地案例是好未来：不到两周通过企业级云电脑部署约 1000 个 Agent，做教案、课件与作业批改，员工可进同一台云电脑调试。张献涛的落点是「Agent 需要人用的工具」，而不是给 Agent 造一套新协议。

阿里云智能集团研发副总裁、终端智能计算事业部负责人张献涛在 1024 模力工场·AI 社区日主论坛演讲，主题是云电脑从「人的办公桌面」变成「智能体的工位」。云电脑给 Agent 提供运行桌面软件与访问业务系统的环境，并统一管理身份、可访问数据、可执行操作与操作审计；Agent 遇到登录失效、验证码或需人工判断的步骤时，云电脑保存当前工作状态并通知人接管，人处理完 Agent 继续执行。落地案例是好未来：不到两周通过企业级云电脑部署约 1000 个 Agent，承担教案、课件制作与作业批改，员工可进入同一台云电脑调试。产品侧，云栖大会发布了定位「智能体电脑」的千问 Book，阿里 2026 年还推出 Personal Agent 千问 Go。
🔥 今日重点

NVIDIA 用 AICR 配方固化 Vera Rubin 的 K8s 就绪状态：DRA v0.5.0 + GPU Operator v26.7.0，NCCL 实测 744.71 GB/s

NVIDIA 在 Vera Rubin NVL72 早期硬件上把「驱动 + DRA + 内核 + 网络」的组合写成可复现的 AICR recipe：R615.23 开源内核模块驱动、带 ComputeDomain 的 DRA driver v0.5.0、64k page 内核的 Ubuntu 26.04，加上 NFD topology updater 的内存上限。GPU Operator v26.7.0 部署后跑通跨节点 NCCL all-reduce，16 GiB 消息在 NVLink 上的 bus bandwidth 达到 744.71 GB/s。验证过程还揪出一个 go-nvlib 不认识 Rubin 架构值、让 DRA kubelet plugin CrashLoop 的 bug，修复已进 v0.5.0。

NVIDIA AI Cluster Runtime（AICR，属 DSX AI Factory Platform）把调好的集群配置写成 recipe，生成可交给现有部署工具的 bundle，并能对运行中的集群做验证。Vera Rubin NVL72 的 recipe 固化了这些选择：主机安装的 R615.23 开源内核模块驱动、带 ComputeDomain 的 DRA driver v0.5.0、64k page 内核的 Ubuntu 26.04、NFD topology updater 的内存上限。在 Vera Rubin NVL72 参考集群上用 GPU Operator v26.7.0 + DRA driver v0.5.0 跑通部署、一致性与跨节点 NCCL all-reduce 性能门禁（16 GiB 消息在 NVLink 上 744.71 GB/s）。验证中还发现 go-nvlib 不认识 Rubin 架构值、导致 DRA kubelet plugin CrashLoop 的 bug，修复已随 v0.5.0 发布。Vera Rubin 换用 ConnectX-9 SuperNIC 与 BlueField-4 DPU（DOCA 3.3.0），每个 tray 暴露 8 个 ConnectX-9 PCI device group、32 个 function，而 GB200 tray 是 4 张 ConnectX-7。

LeCun 新论文给「柏拉图表征假说」补上证明：1.09 亿参数 JEPA 的跨模态对齐分超过 Qwen2.5-72B

10 月 29 日 LeCun 与布朗大学助理教授 Randall Balestriero 发布 37 页论文，用数学框架说明：不同模态的 JEPA 若按「Good Views」（同一场景的有效观察）构造正样本训练，学到的表征空间只差一个旋转变换。实验里 1.09 亿参数的文本 JEPA 在跨模态对齐指标拿到 0.184，高于 Qwen2.5-72B 的 0.154，参数差约 660 倍；达到同等对齐水平只需 2160 万样本，下一 token 预测要 9 亿（按 token 数算约 14 倍）。作者明确：比较的是表征对齐，不是推理、代码或问答能力。

能做什么
给出「不同模态独立训练也能对齐」的充分条件：正样本必须是同一潜在世界状态的不同观察（Good Views），而非同一段文本的前缀-续写或同图遮挡；满足条件时两个 JEPA 的表征只差一个旋转，可用线性变换对齐。
解决什么痛点
多模态对齐长期靠堆参数、堆配对数据，成本高且说不清为什么有效；这篇把「数据关系怎么构造」提到比规模更前的位置，并给出可测的对齐指标。
值不值得
做多模态预训练或需要跨模型表征复用的值得读原文的样本构造部分；不适合直接拿去判断「小模型能否替代大模型」——指标只测表征对齐，与通用能力无关，且 Good Views 的工程化构造没给成本数据。

colibri：纯 C 零依赖推理引擎，MoE 专家按需从磁盘流式加载，46.5k star

JustVugg/colibri 用纯 C 实现、零第三方依赖，把 MoE 的专家权重放在磁盘上按需流式读取，让前沿规模的 MoE 模型能在已有硬件上跑起来，仓库已 46.5k star。取舍很直接：用磁盘 IO 换显存占用，适合显存不够、对吞吐不敏感的单机场景。

能做什么

Buildkite 给 CI 加了三个 MCP 工具：校验流水线 YAML、对比失败构建、补 Webhook，密钥收到流水线作用域

Buildkite 的开源 MCP server 新增 validate_pipeline：按官方 schema 校验流水线 YAML 的语法与结构，不上传文件、不触发构建，直接返回路径和错误给编码 agent 修，但不覆盖环境变量插值、插件配置、依赖引用和动态生成步骤。compare_builds 把失败构建与同分支上次成功构建（或指定构建）对比，报出哪些步骤新增失败、已恢复、仍失败，并附运行时长与重试变化，对最多三个新失败步骤还带日志尾部。create_pipeline_webhook 给已有流水线补上缺失的 GitHub Webhook。凭证侧推出流水线作用域密钥：值创建后保持隐藏，可按分支、队列、构建来源、创建者加访问条件，CLI 3.59.1 支持从 GitHub Actions 迁移密钥。Agent v4.1.0 把缓存保存/恢复的耗时与大小、提交/PR/发起人写进 OTel job span；GitHub Actions 兼容层补上 Linux arm64，ubuntu-24.04-arm 这类标签需显式配置队列映射、不会回退 x86。1.23.0 把 create_pipeline 改为必须指定 create_webhook，是破坏性变更。

能做什么
给 CI 场景补三个专用工具而不是让 agent 硬读全量日志：validate_pipeline 做 schema 级校验、compare_builds 做构建间差异与日志尾部取证、create_pipeline_webhook 修配置；配套流水线作用域的密钥与分支/队列/来源条件，另有 OTel span 里的缓存耗时与提交元数据。
解决什么痛点
agent 改 CI 配置最容易写错 YAML 结构，而错误要等上传触发构建才暴露；构建失败时只能把几千行日志塞进上下文，既贵又抓不住「哪一步是新坏的」；集群级密钥对流水线过宽，泄露面大。
值不值得
他的流水线若已经在用 agent 改 CI（或准备让 agent 直接提 PR 改 pipeline），validate_pipeline + compare_builds 这个组合可以直接照搬思路，哪怕底层不是 Buildkite。注意 validate 不管 env 插值、插件与动态步骤，别把它当完整校验；1.23.0 的 create_pipeline 变更会让旧调用失败。

worktrunk：给并行 agent 一人一个 git worktree 的 CLI，10k star

max-sixty/worktrunk 是 Rust 写的 git worktree 管理 CLI，专门服务「多个 AI agent 并行改同一个仓库」：每个 agent 分到独立 worktree，不抢工作区和索引，创建、切换、清理与状态查看由一条命令统一处理，已 10k star。相比多 clone，worktree 共享同一份对象库，省磁盘也省 fetch。

能做什么
把 git worktree 的创建/切换/删除/状态做成单一 CLI，按分支或任务给每个 agent 一个独立工作目录，共享对象库；适合同时跑多个编码 agent 或并行 PR。
