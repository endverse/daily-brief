Agent Sandbox v1.0.7：warm pool 不再把等 Kueue 准入的成员当卡死删掉，sandboxd 加 bearer-token 认证

Kubernetes Agent Sandbox（kubernetes-sigs）v1.0.7 于 10 月 15 日发布，核心是把「热沙箱池」和调度系统接上：warm pool 成员若卡在 SchedulingGated（典型场景就是等 Kueue 准入），现在按 Unschedulable 一样保留，而不是在就绪宽限期到点后被当成卡死回收——这一条直接针对「预热的沙箱被自己回收掉」这类事故。sandboxd 增加了可选的 bearer-token 认证，Go SDK 支持流式命令执行，Python 与 TypeScript SDK 补齐 env/cwd、命名 claim、自定义 kubeconfig，并在 Pod 已终止时 fail-fast；sandbox-router 新增流量指标。示例侧补了多集群 fleet、KubeRay RLlib、跨 sandbox 存活的 agent 记忆，以及 RL fleet 的 namespace 级网络策略。破坏性变更三项：被信号杀死的进程退出码从 -1 改为 128+n（SIGKILL 报 137），Python SDK 不再配置 root logger，WarmPoolNotProgressing 事件的 action 改为具体 hold 原因（HoldingUnschedulable / HoldingSchedulingGated）。

🔎 新闻要点：v1.0.7（2026-10-15）— sandboxd 可选 bearer-token 认证；Go SDK 流式执行命令；Python/TS SDK 对齐 env 与 cwd、命名 claim、自定义 kubeconfig、Pod 终止 fail-fast；warm pool 成员处于 SchedulingGated（如 Kueue 准入）时保留而非删除；sandbox-router 增加流量指标；新增 KubeRay RLlib、跨 sandbox 存活记忆、RL fleet NetworkPolicy 示例；破坏性变更含信号退出码 128+n、SDK 不再配置 root logger、WarmPoolNotProgressing 事件 action 改为 hold 原因。

Google Cloud 复盘 agent 评测四条教训：11 条 prompt 里 3 条被 LLM-as-judge 误判

Google Cloud 开发者关系团队拿自家 Google Cloud Developer 插件当试验场，总结了 agent 评测工程的四条教训。第一条是别用 LLM-as-judge 只看最终回复：初始 11 条 prompt 的评测被判 3 条失败，翻原始工具调用日志发现三条其实都做对了（agent 第一步就跑了 gcloud help 校验语法，只是结尾在提醒数据丢失风险而没「邀功」）。第二条是遥测抽取必须保留 turn 结构——现代 harness 会把 skill 加载和两次文档检索塞进同一个 tool_calls 数组并发发出，而 skill 正文往往在检索执行之后才注入上下文，扁平化成一条时间线就永远查不出「agent 为什么无视 skill 指令」。第三条是 live run 与 plan-only run 并排跑：约一半关键发现来自两者差异（某次 live run 第二步就被权限拦住，plan-only 却产出一份 8000 字符、完全无视组织策略与审批的计划）。第四条是用人工专家策展的 golden set 做持续回归，把评测当 CI，而不是拿一次性 demo 当 eval。

能做什么
给出四条可直接照做的评测工程规则：按工具调用轨迹（而非最终回复）打分；遥测保留 turn 结构以暴露并发分发导致的「skill 指令注入晚于执行」；live 凭据跑 + 去凭据 plan-only 跑双条件对照；用专家策展的 golden set 当回归基线。
解决什么痛点
agent 评测最容易骗自己：LLM-as-judge 只看文本会放过「做了但没说」的正确行为、也会漏掉并发工具调用抢在 skill 指令之前执行的时序 bug；只跑 live 又常被权限错误在第二步打断，看不到模型真实的推理与路由意图。
值不值得
你在做 skill/agent 落地，这几条直接对应「skill 写了但 agent 不遵守」的排查路径——先怀疑并发分发时序，再怀疑模型；代价是要把评测当持续工程投入（轨迹采集 + golden set 维护），不是加几个 prompt 就完事。

Orca：一个 prompt 扇出五个 agent、各自独立 worktree，单日 +830 star

Orca（stablyai/orca）把「同时跑一队编码 agent」做成桌面工具：同一个 prompt 分发给最多五个 agent，每个跑在独立 git worktree 里，结果并排比较后择优合并；支持 Codex、Claude Code、OpenCode、Pi，可用自己的订阅。配套能力包括 Ghostty 级 WebGL 终端（无限分屏、重启保留 scrollback）、Design Mode（点选真实 Chromium 窗口中的 UI 元素，把它的 HTML/CSS 与裁剪截图直接塞进 agent prompt）、SSH worktree（在远端机器跑 agent，带自动重连与端口转发）、以及 diff 行内批注回传 agent。发布当天 GitHub Trending 单日 +830 star。

能做什么
把多 agent 并行比较做成日常工作流：prompt 扇出 → 独立 worktree 隔离改动 → 并排 diff → 择优合并；Design Mode 让前端任务不用手抄 DOM 结构和截图，SSH worktree 让重活跑在远端机器上。
解决什么痛点
多 agent 并行时最大的摩擦是「改动互相踩」和「结果没法比」——共用工作区会互相覆盖，纯 CLI 又没有并排 diff 与可视化上下文；前端任务还要人来回贴 DOM 和截图。
值不值得
你在用多个 agent CLI（含 opencode）时，这类编排层决定的是并行尝试的成本而不是模型能力；注意它绑定各家订阅、以桌面端为主，团队共享与 CI 化支持如何要自己验证，别指望它替你做评测。

OmniVerifier-C1：把视觉验证器从「真/假」改成按规则拆解逐项打分

OmniVerifier-C1 针对生成式视觉模型/世界模型的验证环节：传统验证器只输出 True/False 二分类，对「组合式要求」几乎没法定位问题；它把复杂 prompt 或环境规则自动分解成细粒度组件，对每个组件给出连续分值与批评，从而在规则约束的生成任务上提供可定位的反馈。HF Papers 32 赞、同题在 arXiv cs.AI 也有条目。

能做什么
把「这个生成结果合不合规」变成一组可分解、可打分的子判断：规则拆解 → 逐项打分 → 输出连续批评，可直接用作世界模型/视频生成的奖励或筛选信号。
解决什么痛点
二分类验证器只告诉你失败、不告诉你哪条规则失败，对多约束的组合式 prompt 既不可解释也无法指导重采样。
值不值得
如果你要给生成式流水线加自动质检或做 RL 奖励，这类「规则拆解 + 分级打分」是比二分类更可用的信号；但它属于评测层改进，先看你现有 pipeline 里是否真有规则可枚举。

FlashMask-3：Hopper 上 mask-aware 分布式 attention，118B MoE 128K 训练吞吐 +7.3–11.0%

FlashMask-3 打的是长上下文训练里「结构化 attention mask（document、prefix-LM、share-question、sliding-window、block-sparse）× 多机 context parallelism」这个瓶颈：在 FlashAttention-3 的 TMA/WGMMA 流水线上做三角色 warp specialization 的 mask-aware Hopper kernel，并把每个 rank 的 mask 定位归约为边界向量上的零通信 clip-shift-max，另加稀疏感知负载均衡（HCC-IPO）与 mask 驱动的通信剪枝。单 H100、12 种 mask、4K–128K 上下文下，TFLOPs 比 FlashMask / FlexAttention / MagiAttention 高 45–141% / 34–71% / 2–44%；CP 度 4–32 时吞吐比 Megatron-Core CP ring 高 1.80–3.71×；118B-A14B MoE 在 128K、128 张 H100 上端到端吞吐提升 7.3–11.0%，attention 前后向快 24.5–44.9%。

能做什么
在 Hopper 上把「带结构化 mask 的长上下文训练」做快：mask 感知的 warp 特化 kernel + 零通信的分布式 mask 定位 + 稀疏感知负载均衡 + 通信与计算重叠，覆盖从单卡到 32 路 CP 的场景。
解决什么痛点
结构化 mask 会把 attention 的算力利用率打下来（旧实现 O(n²) 掩码、只支持 Ampere、且不能跨节点扩展），多机 CP 时 mask 定位又要额外通信，长上下文训练因此卡在 attention 这一段。
值不值得
你在做推理/训练集群规划时，这类工作直接影响「同一批 H100 能跑多长上下文」的账；限制是绑定 Hopper（H100/H200）与 FlashAttention-3 体系，B200 或非 NVIDIA 卡不适用，且是论文阶段、需自己接 Megatron 侧。

模域 ModelSphere 开源：Apache 2.0 的生产级 AI 部署平台，统一纳管昇腾/摩尔/海光等国产卡

范式智能与睿思智联开源「模域 ModelSphere」（Apache 2.0）：把算力管理、模型部署与运行优化收进一个平台，内置自动弹性扩缩容、PD 分离部署、三级 KV 缓存、高可用负载均衡与断流续写，并用 EngineX 推理引擎统一/混合调度昇腾、天数智芯、摩尔线程、海光 DCU 等国产算力。官方称 AutoTune 排期加自适应负载均衡让极限吞吐提升约 285%（约 4 倍），已适配 DeepSeek-V4/V4-Flash、Qwen、Kimi、MiniMax、GLM。定位与 vLLM/SGLang 互补：后者管单机推理效率，它管集群级纳管、缓存感知路由与线上自动调优。

Akka 用 65 个开源项目验证「规格驱动移植」：99.3 小时 94.1 亿 token，57/65 有改善

Akka 发布一份规格驱动的 AI 辅助移植实验：先用结构化规格（声明 + 证据 + 类型化行为）描述代码、模型与运行时行为，再让 agent 实现每个项目最多 10% 的功能，之后挑 10 个做完整移植。首轮测试耗时 99.3 小时、消耗 94.1 亿 token，65 个项目中 57 个在代码行数或性能上有提升。成本结构上 Sonnet 平均每项目 61 分钟、Opus 120 分钟但 token 少约 40%，提高 effort 设置并没有持续收益。性能结果分化：应用、框架、库普遍提升，基础设施与工具类中位数反而下降（Dify 提升 143333 倍来自不同工作负载对比，Netflix Metaflow 慢了约 100 倍）。

能做什么
把「大规模代码移植」变成可度量流水线：需求发现 → 规格定义 → 移植 → 基准测试 → 优化，配自动化验证（原单元/集成测试）与人工审查串行化、错误处理、PII、幂等性、架构边界。
解决什么痛点
直接让 agent 改代码，跨组件决策写不进上下文，首次实现就跑偏；规格化后模型有稳定契约可依，且能用原有测试证明没破坏行为。
值不值得
你要判断的是「规格先行的成本能否换来可验证的移植」——结论是能，但成本以十亿级 token 计（94.1 亿），且基础设施类项目收益为负；用它评估是否值得把某次大改写成规格驱动流程，而不是当成通用提效手段。
