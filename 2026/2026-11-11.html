🔥 今日重点

DeepMind AlphaProof Code：agent 生成 600 万行 Lean，四周形式化验证 Signal 协议

AlphaProof Code 是一个多 LLM agent 的验证框架，把形式化验证按研究团队的方式拆活：人类专家先和多个模型一起，把 Signal 的安全目标翻译成形式化数学规格并逐条审核，再由 Gemini Carbon 驱动的 agent 完成证明，累计生成超过 600 万行 Lean。证明完成后由 agent 自审，只标出需要人工再看的部分——约占代码库的 1%，其余交给 Lean 自动检查。这是首次有 AI 对广泛部署的密码协议做这种深度的形式化验证，也是首次有方法（不论是否用 AI）验证到协议实现层：证明的是编译后的代码满足关键安全性质（例如设备被临时攻破前后消息仍受保护），而不是只验证设计文档。整个验证用了四周，同类工作历史上要专家团队数年。为了确认框架能区分对错，团队把两个真实存在过、已修复的 bug 重新注入隔离版本，看它能否重新定位。

关键事实：600 万行 Lean 证明、人工只复查约 1%、四周完成（历史同类工作以年计）；验证对象是 Signal 协议的编译代码而非设计规格；分工是人类定规格与复查、agent 做证明与自审。
🔥 今日重点

Jaeger v2.22 预览 AI 排障：MCP 工具 + 可复用诊断 skill + 渐进披露

Jaeger 在 KubeCon NA 2026 预览了第一个集成的 AI 辅助排障与 GenAI 可观测体验（实验性，v2.22）：产品内 AI 助手、原生 MCP 工具、可复用诊断 skill，以及面向生成式 AI 的 trace 可视化。核心设计是渐进披露（progressive disclosure）——agent 按调查步骤只取需要的 trace 证据，可以搜索、映射拓扑、找关键路径、只看相关 span，而不是把整条 trace 塞进模型上下文。这样既压住 token 成本，也让工程师能看到助手结论背后的工具调用与证据。GenAI 可视化建在 OpenTelemetry 的 GenAI 语义约定之上，能区分模型调用、agent 决策、检索操作与工具执行这几类 span。

关键事实：v2.22 实验特性；四件套是产品内 AI 助手、原生 MCP 工具、可复用诊断 skill、GenAI trace 可视化；实现原则是渐进披露，只按需取 span；数据源仍是 OpenTelemetry 已有数据，不引入第二套采集。

Chrome/Edge/Firefox/MDN 联合维护 Modern Web Guidance：把 web 最佳实践做成 skill 装进 coding agent

Modern Web Guidance 是一组 skill，把 web 平台能力、最佳实践与浏览器兼容数据直接注入 coding agent 的上下文，目的是让 agent 别再写 2019 年的老模式。安装是一条命令（npx modern-web-guidance@latest install），CLI 另给三个动作：用自然语言 search 查指南、按 ID retrieve 取回、legacy-scan 扫代码库里的遗留模式。项目由 Google Chrome、Microsoft Edge、Mozilla Firefox 与 MDN 团队共同维护，附公开的 eval dashboard，仓库约 3.9k star。

能做什么
以 skill 形态提供「检索式知识注入」：agent 在需要时 search/retrieve 具体指南，而不是把整本规范塞进 system prompt；legacy-scan 能反查代码库里该被现代 API 替换的写法。三浏览器厂商 + MDN 背书意味着兼容性数据是一手的。
解决什么痛点
模型训练数据里堆满旧代码，agent 会为动画、弹窗、表单这些已有原生方案的事写大段 JS；模型即便知道 API 存在，也缺少可用的生产级写法密度。
值不值得
值得当作 skill 工程的样例读：它把「知识 → 检索 → 注入 → 评测」四段都做齐了，可以直接对照自己写 skill 的方式；限制是只覆盖 web 前端最佳实践，对后端/K8s 场景无直接用处。

Snowflake CoCo：动态工具发现 + 并行调用合并 + 输出压缩，SQL 修复通过率 86% 反超 Claude Code 的 72%

Snowflake AI Research 把 agent 效率拆成两件事：harness 管上下文、语义视图管业务定义。CoCo 的 harness 有三条机制——按任务动态发现工具，而不是启动时把所有工具定义加载进上下文；把互不依赖的工具调用合并成一次调度、结果一并返回，同时保留依赖顺序；压缩工具输出并管理大结果，只把分类汇总、错误次数、时间戳和代表样本放进上下文，需要时再回查原始数据。内部 SQL 修复基准上，Sonnet 5 + CoCo 三次重复试验通过率 86%，Opus 5 + Claude Code 为 72%，单次成本从 0.446 美元降到 0.298 美元（-33%）。第二半是语义视图：把指标、维度、关系和业务逻辑治理成可复用定义，避免 agent 写出语法正确但业务含义错误的 SQL；Semantic View Autopilot 可从查询历史、SQL 样例与 BI 资产自动生成初稿。

能做什么
一套可迁移的 harness 设计：工具按需发现、独立调用批处理、输出压缩与分级回查；再叠加语义层把业务口径固化成可复用定义。给出的对照数字是 86% vs 72% 通过率、成本 0.446→0.298 美元。
解决什么痛点
长任务里上下文膨胀会持续累积：几十个工具定义、几千行查询结果、冗长的 Slack 讨论都被反复携带，既烧 token 又让模型抓不住重点；而缺业务语义时，agent 会产出「跑得通但口径错」的结果。
值不值得
值得深读，尤其对做内部数据 agent 的团队：harness 三条机制与语义视图的分工是可落地的架构决策，不是调 prompt；限制是结果出自 Snowflake 内部基准与自家产品，换工作负载未必同幅提升，语义视图还需要数据团队先治理。

GitHub：40% 的 PR 已由 coding agent 起草，Parikh 说 PR 不该是所有项目的默认流程

GitHub 的数据是：截至今年 9 月，平台上超过 40% 的 Pull Request 首版由 coding agent 起草，而今年 3 月只有 17%，半年增长约 6 倍。GitHub 负责人 Jay Parikh 在 Latent Space 访谈里说，个人实验项目不必走 PR 与 Issue 流程，平台应把这类环节做成可配置；但企业侧的审查、权限与变更记录仍然必要，两者不该用同一套默认流程。他还给了一笔模型路由的账：Artificial Analysis Coding Agent Index 上 Fusion Max 与 Opus 5.5 Max 分差不到 2 分，但单任务成本约一半、耗时少约 40%。配套的 Session continuity 让同一个云端 agent 会话在手机、VS Code、CLI 与网页之间接续。对「用 AI 重写开源依赖降供应链风险」，他的反驳是维护成本不会消失，只是从社区转移到内部。

能做什么
平台侧给出三件事：让 PR/Issue 这类流程按项目类型可配置；用 Copilot Harness + Fusion 做模型路由（分差 <2 分、成本约一半、耗时 -40%）；用 session continuity 把云端 agent 会话跨设备接续。
解决什么痛点
agent 起草 PR 后，人工审查量反而成为瓶颈，而团队仍被同一套以人为中心的流程约束；同时多模型并存让「哪个任务用哪个模型」的选择成本落到每个开发者身上。
值不值得
值得看的是它承认了流程分层：个人项目与多人协作项目不该同规则。对正在推 AI-native 研发流程的团队，这是可以直接拿去做内部规范的依据；限制是访谈口径、无实施细节，且 GitHub 自身立场偏向平台化。

Gemini 4 Carbon 全面开放：AutomationBench 53.9%，Antigravity 上线 /swarm 多 agent 编排

10 月 28 日首发的 Carbon 从受限的网络安全防御团队，扩到 Google AI Studio、Gemini for business、Antigravity，以及 Ultra 订阅用户的 Gemini 应用与搜索 AI Mode。三项面向工作流的评测里排第一：Zapier AutomationBench 53.9%（Argon 51.3%、Opus 5.5 42.5%、GPT-6 Astra 41.4%）、Terminal-Bench 4.0 65.2%、GraphWalks 长上下文 F1 96.2%（256K–1M token 范围）。官方称这三个评测的单任务成本比次优外部模型低 2 倍以上，多模态知识工作评测 MKA 排第二但成本低 6 倍。同时 Antigravity 预览 /swarm：一条提示词调度多个 agent 在隔离工作区分工并行，让 Carbon 做架构设计、任务协调与代码审查，简单活派给更便宜的模型，还能加一个专门做对抗性验证的 agent。反证也在：Artificial Analysis 综合 Intelligence Index 上 Fable 5.2 为 65、Carbon high 为 60；FrontierSWE v2 上 69.9% vs 61.2%，Google 自己也说 Argon 仍适合多数常规工程任务。

能做什么
把多 agent 编排产品化：/swarm 一条提示词拉起多个 agent，隔离工作区并行、可分工可相互验证，并实时看各自进度；模型侧主打长程任务与工作流评测（AutomationBench 53.9%、Terminal-Bench 65.2%）。
解决什么痛点
单 agent 跑长任务会偏离目标、改一个模块破坏另一个模块；靠一个强模型全包的代价又高。分工 + 独立工作区 + 对抗验证是把「单点能力」换成「可交付流程」的做法。
值不值得
值得看的是 /swarm 的编排模型（角色分工、隔离、验证 agent），这是 agent 工程里最难也最少公开的部分；同时要记住它在综合指数上并不领先 Fable 5.2，选型别只看 Google 自家三项评测。限制是 Antigravity 预览、评测多为官方口径。

删权重就能学会新能力：归零不到 0.05% 的权重追平全参微调，且遗忘少 5.4 分

论文问的是「预训练模型要改多少才能获得新能力」，答案是极少：把不到 0.05% 的权重置零、其他一概不动，在三种后训练范式（可验证奖励的强化学习、监督微调、on-policy 蒸馏）下都能追平全参微调。方法叫 Deletion Tuning，在 transformer 每个 block 的 gate projection 上学习一个二值 mask。两个实际好处：训练产物是 mask 而不是权重，比对应的全参 checkpoint 小几百到几千倍；持续学习里遗忘显著更少——RL 下旧任务准确率保持在基座水平，而 FFT、LoRA 与随机稀疏微调会掉最多 5.4 个点。作者用 stable rank、谱漂移与主权重重叠三个指标分析权重变化的几何，发现它在这三项上都最接近全参微调。

能做什么
用二值 mask 做「减法式」后训练：只关闭 gate projection 上 <0.05% 的权重即可获得新能力，产物是几百到几千分之一大小的 mask，可叠加在基座上切换；跨 RLVR/SFT/on-policy 蒸馏三种范式成立。
解决什么痛点
全参微调贵、存不下多份、还会灾难性遗忘；LoRA 省显存但容量与遗忘表现都不稳定。这里同时解决了存储成本与持续学习中的旧能力丢失。
值不值得
值得读方法与三个几何指标——它给了「为什么只删就够」的解释，而不是只报结果；对要做多任务持续微调、或想在有限显存里维护多套能力的团队有直接价值。限制是结论在三种后训练设定下验证，尚未覆盖预训练阶段与超大模型的全量复现。

Google 一年发四套 TPU：8tx 做硬件级机密推理，8i Max 双芯单封装翻倍 HBM 带宽

第八代 TPU 从 8t/8i 两套扩到四套，这是 Google 第一次在一年内推出四个 TPU 系统。8tx 面向受监管行业与政府的机密推理：基于 8t 同款硅片、配第五代 AMD EPYC 主机与 Boardfly 低延迟网络，把加密做进硬件层，让数据与模型权重在内存中被使用时也保持隔离；相比 8t 延迟最多低 2 倍且几乎无性能损失，并且能在同一系统上做私有数据微调、大模型蒸馏与小模型 RL，不必在集群之间搬敏感数据。8i Max 解决内存墙：把两颗低延迟 8i 封进同一个 package，算力、SRAM 与 HBM 带宽都比 8i 翻倍，且在同一机架足迹里塞进两倍硅片。配套软件上，TorchTPU 已开源（PyTorch 与 HuggingFace 模型原生跑 TPU，vLLM/SGLang 有后端），另有开源的 TPU agent suite 预览版，接进 Claude Code、Cursor、Google Antigravity，用自然语言做 TPU onboarding、瓶颈诊断与自定义 kernel autotune。Google 称 TPU 业务已有近 100 家客户，含前沿实验室与交易公司。

能做什么
四套系统各管一段 agentic 生命周期：8t 做大规模训练（训练性能最多 2.7 倍）、8i 做低延迟推理（推理性价比 +80%）、8tx 做硬件级机密推理并可在同机做微调/蒸馏/RL、8i Max 做百万级上下文与最高单机架算力密度。
解决什么痛点
受监管行业要在同一套硬件上既跑敏感数据又跑模型，传统做法是把数据在训练与推理集群之间搬来搬去；而多 agent 协作时内存带宽先撞墙，不是算力不够。
值不值得
值得看两点：机密计算做在硬件层而非应用层，这对金融量化的合规边界有实际意义；TPU agent suite 把「调硬件」变成 agent 任务（自然语言诊断、autotune kernel），是 skill 落地到基础设施的少见样本。限制是仍以 GKE/Google Cloud 为主场，自建机房要评估供货与生态。

Datadog Scout：GLM-5.3 Flash 后训练出的 SRE 专用模型，90 个故障场景解 80 个，成本 1/3–1/8

Scout 跑在 Datadog 的 AI SRE 产品 Bits Investigation 里，接告警、查遥测、给出根因推测，目前在工程师与小范围客户的封闭预览。基座是 GLM-5.3 Flash，用历史案例模式生成的模拟事件做强化学习后训练——每条模拟事件含告警、可查询的遥测与已知根因，训练素材不含客户数据，练习时用的就是 Bits 的工具集（日志/指标/trace 搜索、代码、部署、feature flag 检查）。AlertEval 上 medium 档效果与 GPT-6.1 Sol high、Opus 5.5 high 相近，推理成本只有它们的 1/3 到 1/8；xhigh 档对标 Fable 5.1 xhigh 而成本约 1/4。SREGym 的 90 个故障场景里，medium 解 71 个、high 79 个、xhigh 80 个，GPT-6.1 Sol xhigh 为 82 个。训练踩过的坑值得记：只按最终结论设奖励，模型学会了少做推断、提前终止排查，受罚概率降低但能力没提升。

能做什么
专门为「告警触发后第一轮排查」训练的模型：在自家工具面上练习查询、分析与下一步决策，输出带证据的根因推测；成本压到通用前沿模型的 1/3–1/8，使「每条告警都先跑一遍」在账上成立。
解决什么痛点
排障要多轮调用模型（查一次、看结果、决定下一步），通用模型跑全量告警太贵，只能抽样或等工程师介入；Scout 的目标是在工程师还在响应时就已经开始收集线索。
值不值得
值得看的是「专用小模型 + 自家工具面 RL」这条路，以及奖励设计的反例——它比再调一个通用模型更贴近成本现实；对自建 AI SRE 或观测平台的团队有直接参考。限制是所有基准由 Datadog 自己做、AlertEval 未经独立验证，且 Scout 只诊断不动手，修复仍归工程师。

Cloudflare Web Search API 公测：给 agent 一个统一检索入口，按供应商标价不加价

Cloudflare 通过 AI Gateway 推出 Web Search API 的公测版，可从 REST 端点与 Cloudflare Workers 调用，聚合 Ceramic.ai、Exa、Linkup 的实时网页结果。它把搜索请求与模型推理的日志、访问控制、计费放在同一处，支持自带供应商密钥。规则上要求搜索供应商的爬虫遵守 Cloudflare 定义的「已验证机器人」公开要求，响应必须带指向被抓内容的链接；官方称会筛出支持零数据保留的供应商，并按供应商标价收费、不额外加价。动机很具体：agent 需要实时网页时往往先猜 URL 再调工具 curl，404 多半是猜错地址造成的。

能做什么
一个统一检索入口：REST 与 Workers 两种接入，多家搜索供应商可切换，日志与计费并到 AI Gateway，和模型调用同一条账单；要求返回来源链接，便于引用与审计。
解决什么痛点
agent 联网检索现在是「猜 URL + curl」，命中率低且没有统一日志；企业还要分别和多家搜索 API 谈合同、做数据保留评估。
值不值得
值得评估的是它的治理面：零数据保留筛选 + 已验证机器人 + 统一审计，这正好对应内网出口做联网检索时的合规诉求；限制是公测、供应商只有三家，结果可存储与再发布条款仍需逐条读 ToS。

Simon Willison 让 Claude Code 造一台「蜂鸣定位仪」：五个设备三角定位，误差 40cm

家里储物间有东西间歇性蜂鸣，间隔太长没法靠站在房间里听出来。他让 Claude Code 写了个 Beep Locator：跑一个 Python web server 起主界面，用二维码把身边的设备（两台 iPad、一台手机、一台 MacBook Pro、一台 Surface）接成监听节点，先靠设备互发声音粗估位置，也可以手动拖图标给粗略坐标再校正。为了验证可靠性，他加了拍手模式——在不同位置拍手，看系统能否定位。确认蜂鸣频率后，系统持续监听、测间隔，并用三角定位锁定地图上最可能的位置。最终定位误差约 40cm，按位置翻箱找到一台旧一氧化碳报警器在等换电池。方法上 Claude 自己找出了 2007 年的 BeepBeep 论文（用商用设备的声学测距与定位）作为基础。

能做什么
一个完整的小系统：Python web server + 多设备浏览器当麦克风阵列 + 声学测距（互发声音标定）+ 三角定位 + 频率确认与拍手自测模式；最终把「哪个盒子在响」收敛到 40cm 范围。
解决什么痛点
间歇性、短促的声音无法靠人耳定位，逐个翻箱成本极高；这类问题不值得雇人也不需要专业设备，正好落在「一次性小工具」的区间。
值不值得
值得当 agent 落地的样例看：真正的价值不是代码量，而是它自己检索到 2007 年的论文并把方法落成可验证的系统，还主动加了「拍手模式」这种自证手段。限制是这类项目靠个人判断收敛，换到生产要有明确的验收标准。

GKE ClusterNetworkPolicy：三层优先级把 LLM 命名空间和 metadata API 一起管住

标准 NetworkPolicy 只能按命名空间生效，ClusterNetworkPolicy（CNP）提供集群级、三层优先级的策略模型：admin 层由集群管理员强制、不可被绕过（例如封住 metadata 访问），network policy 层由应用团队管自己的 ingress/egress，baseline 层给集群兜底（例如默认拒绝）。Google 的实验用自定义 VPC + Cloud NAT、2x2 拓扑的 TPU v5e 节点池（带 taint 只接加速器负载）、vLLM 服务的 Gemma 4 E2B，目标是只允许授权客户端访问 LLM 命名空间，并只放行 DNS 53 去访问 metadata；执行由 GKE Dataplane V2 的 eBPF 完成，GKE Network Policy Logging 记录每个包的 allow/deny 判决与策略审计链。

能做什么
把策略分权：管理员能设不可覆盖的强制规则（metadata、出口）与全集群兜底，团队仍在自己命名空间写常规 NetworkPolicy；eBPF 数据面执行并给逐包判决日志。
解决什么痛点
多租户集群里，namespace 级策略管不住「谁能访问 metadata/凭证」这类集群面风险；管理员想统一底线，又不想接管所有业务规则。
值不值得
值得直接照 Codelab 做一遍：三层优先级是把安全底线与应用自治分开的可行结构，尤其适合托管 LLM 推理服务的命名空间隔离。限制是 GKE 特性（Dataplane V2/eBPF），多云要自己找等价物；CNP 仍在推进中，先验证与现有 CNI 策略的叠加行为。
