🔥 今日重点

Kamaji + HAMi：一台无 GPU 的机器上跑出两个隔离租户集群，各自切分 GPU 调度

CNCF 博客给出一套可复现的多租户 GPU 方案：Kamaji 把每个租户的控制面（API server、controller-manager、scheduler）跑在管理集群的 Pod 里，HAMi 在租户 worker 上做 GPU 显存/算力切分。作者在单台 4 核 8GB 内存、20GB 磁盘的 Linux 主机上用 kind 起管理集群，HAMi 的 mock device plugin 通过节点 annotation 描述假卡并注册 gpumem/gpucores，无需真实 GPU 就能跑通 HAMi 的 webhook、scheduler 与配额逻辑；最终两个完全隔离的租户集群、八个测试全部通过。关键在于两层交汇处：租户 API server 在管理集群，HAMi webhook 在租户 worker，每次 GPU Pod 创建都依赖 Konnectivity 隧道从管理集群回连租户。

🔎 新闻要点：Kamaji 解决「每团队一套控制面太贵」，HAMi 解决「一张卡只能整卡分配」；租户之间不共享节点也不共享 API server，只共享管理集群与 kamaji-etcd（租户数据分开存）；HAMi mock device plugin 跳过硬件发现、以节点 annotation 声明假卡，使 HAMi 的调度与配额路径可完整验证；实验目标是证明 Konnectivity 回连路径在 GPU Pod 创建时可用。

讯飞把 Agent 推进企业核心流程：Agent OS + APA，称跨系统协同效率提升 90%

讯飞开放平台披露：开发者总数 1187 万，2026 年大模型相关企业开发者同比增长超 104%；以单次调用互动数超 1 万衡量复杂任务，平台处理复杂任务的用户占比从不足 10% 升到 60%。此次推出星辰 TaaS（底层星辰 MaaS 供模型、中层做调度/智能体引擎/知识工程/工具编排/运行治理）、Agent OS（用「场景包」组织员工、智能体与业务系统，做组织级上下文工程）、APA（用录屏或自然语言把填表、查库存、发起审批封装成技能）与 XFYUN CLI。官方数据：引入 Agent OS 后跨系统协同效率提升 90%、75% 以上流程可自主流转；国家能源集团招采场景把评标拆给材料归集、文档解析、标准提取与多模块评审多个专家智能体，由总智能体协调，准确率约 97%，已服务 50 多家央国企。

能做什么
Agent OS 的实质是「组织级上下文总线 + 任务调度」：让不同 Agent、不同系统之间的上下文可流动，否则每个系统各挂一个 Agent 也拼不成闭环；APA 把传统 RPA 的人工编排换成录屏/自然语言理解 UI 并生成技能，降低技能生产的边际成本；TaaS 把「卖 Token」重构成「交付业务结果」的三层结构。
解决什么痛点
企业 Agent 落地最硬的两个墙：一是上下文出不了系统边界（CRM/ERP/OA/合同/项目管理各一套），二是流程自动化要技术人员手写脚本、维护成本高。招采场景用「无引用不结论、无材料不判断」把可追溯性做成约束，正好对应金融/央国企对结论可审计的要求。
值不值得
对他关注的「Agent 进核心流程」有参考价值的是两个机制：组织级上下文工程与多专家智能体 + 总协调者的拆分方式。但所有数字都是厂商口径（97% 准确率无测试集说明，90% 效率提升无定义），选型必须自测；且它强绑讯飞模型栈，与自建 Agent 平台的路线是竞争关系。

GitLab 19.4：Duo CLI 加 /goal 目标驱动模式，两个模型互相验收

GitLab 发布 DevSecOps 平台 19.4，为 Duo CLI 增加 /goal 命令（公测）：接受一个开放式目标并持续执行到完成或触达迭代上限，一个模型实施变更、另一个模型对照目标检查进度，开发者可停止、改目标或重新引导；任务本地运行并沿用项目现有上下文与权限。同时托管 Kimi K3、MiniMax M3、GLM 5.3 三个开源权重模型，官方称每 GitLab 积分可支撑的调用量最多为同类前沿模型的 4 倍；MCP 服务器工具扩展后，只读工具默认「始终允许」、写入删除默认「始终询问」，管理员可在群组/项目级改；积分导出为每条计费事件一行（含用户、项目、会话、流程类型、积分与 Token 数），可设单用户用量上限并在月度 50%/80% 触发预警。

能做什么
把 agent 从「单提示词响应」推到「持目标迭代」：/goal 用执行模型 + 验证模型的双模型结构做自检闭环，并把迭代上限、可中断、可改目标做成产品级开关；MCP 工具按读写分级授权，把「agent 能干什么」下沉到工具粒度而不是一把梭的 token 权限。
解决什么痛点
长任务 agent 的两个现实问题：跑飞（无限循环、越改越远）与权限过大（能读就能写、能写就能删）。GitLab 的解法是双模型互检 + 迭代上限 + 工具级默认拒绝写操作 + 计费按事件归属，正好对应企业采购时最常问的「怎么控成本、怎么审计」。
值不值得
值得看的是权限模型与成本归属设计，而不是 /goal 本身（语义验收不等于形式验证，官方也承认清晰验收标准仍必需）。限制：官方没给三个开源权重模型的基准或绝对价格，4 倍调用量是积分口径；漏洞管理类 MCP 工具仅旗舰版可用。

Gremlin 把可靠性工程交给四个智能体：Foresight AI 正式可用，闭环验证靠重跑故障注入

Gremlin 宣布智能体产品 Foresight AI 全面上线，作为平台附加组件提供。工作拆成四个角色：分析师收集服务数据并推荐测试用例，测试员安排并执行故障注入，运维解读失败结果并提出修复方案，技术项目经理跟踪各团队测试覆盖率、可靠性风险与承诺并生成周报推 Slack。推荐基于 Gremlin 的 Failure Atlas——十多年、数万个分布式系统的数百万次故障注入记录；Gremlin 称客户系统数据不用于训练 LLM，模型只做搜索、总结与解释。核心机制是闭环验证：发现薄弱点后提出变更建议，再重跑原始测试验证；未获许可不执行任何测试、不应用任何修复。

能做什么
把混沌工程从「人设计实验」变成「agent 提案实验 + 自动重跑验证」：四角色分工覆盖从数据收集、执行、解读到管理追踪；可靠性评分把改进进度量化；还能用自然语言生成含图表/表格/分页/链接的报表，解决「被避免的事故没有证据」的老问题。
解决什么痛点
可观测性与 AI SRE 产品大多是被动型——从已经出问题的遥测开始分析；故障注入是主动型，在事故前造受控故障并记录响应。Foresight 补的正是「谁来持续设计并复验这些实验」的人力缺口，且用审批边界避免 agent 自主改生产。
值不值得
方向值得跟（主动验证 + 闭环复跑），但落地门槛在组织而非工具：分析师 Jason English 的提醒是对的——可靠性计划不能当软件包装上，哪些风险可接受、是否采纳变更仍要团队与管理层决定。厂商私有 Failure Atlas 是护城河也是锁定点，且数据不可导出。

千问 Personal Agent 的三要素：30 多个行业需求透视图、8000 多项原子能力、按关联强弱分层的记忆

在 2026 中国计算机大会上，阿里千问 AI 算法负责人蒋冠军分享 Personal Agent 实践：把 AI 应用分为对话、代理、助理三阶段，认为当前正加速进入助理阶段。模型层面强调执行稳定性，建了覆盖 30 多个头部行业的用户需求透视图、梳理 8000 多项原子模型能力要求，并引入行业专家参与评估；记忆层面反对简单堆叠对话历史，改为分析事件关联、按关联强弱分层存储与调用；生态层面构建以模型为中心的开放服务体系，整合专业工具、行业 Skill 与第三方 Agent。数据侧：过去三个月复杂任务平均 Token 消耗增长 1.6 倍，「千问 Go!」上线「我的应用」——不写代码、说需求即搭应用，已开启邀测。

能做什么
给出的是一套 Personal Agent 的能力分解：把「懂用户」拆成需求透视图（行业 × 原子能力矩阵）、分层记忆（按事件关联强弱决定存与取）与生态连接（工具/Skill/第三方 Agent）。记忆分层是里面最具体的一条——目的是降低无关键历史带来的噪声与推理成本。
解决什么痛点
个人助理类 agent 的两大失效模式：一是模型能力与真实需求错配（能答题但完不成任务），二是记忆越积越脏、越久越贵。用行业需求矩阵对齐能力供给、用关联强弱替代全量上下文，都是在控这两个成本。
值不值得
对做多用户 agent 平台有借鉴意义的只有「记忆按关联强弱分层」这一条工程判断，其余多为产品叙事。它没有公开记忆结构的实现细节与召回评估，1.6 倍 Token 增长也不能证明能力提升；判断价值需要用自家会话数据复现分层记忆的召回率与成本曲线。

Meta/MIT/华盛顿大学提出「上下文语言模型」：让模型自己编辑上下文，24 小时任务同算力性能高 65%

研究者提出 Context Language Model（CLM），把上下文当作可无限更新的文件由模型自主编辑——改写历史消息、保留关键事实、删除无关信息、维护进度记录，并习得自己的上下文管理策略，替代摘要、压缩、外存检索等外部机制。三种训练形态：零样本、上下文学习（自然语言指导 + 迭代技能优化）、强化学习（任务成功为主目标、算力效率为次要目标）。结果：零样本在 BrowseComp-Plus 准确率 +11.4%、FLOPs −21.5%；12 小时 EdgeBench 得分 +5%、FLOPs −59%；24 小时多仓库 agent 集群任务同算力下性能高出 65%。上下文学习版在 ContextBench 最高 +35.9 个百分点；RL 版把 Qwen3.5-9B 在 BrowseComp-Plus 从 28.8% 提到 42.5%（+47.6%），FLOPs 还降 12%。

能做什么
把上下文管理从外部框架（摘要器、压缩规则、检索器）变成模型内在行为：模型自己决定改哪条历史、留哪些事实、记什么笔记，并能迭代生成一份「上下文技能文档」供后续复用。这天然打通上下文学习与参数学习——策略可以直接用自然语言教，也可以 RL 学。
解决什么痛点
长任务的算力与信息双损失：摘要会丢细节或引入错误，压缩靠预定义规则，外存要 agent 自己判断何时重新载入；上下文越长越贵，而 agent 任务动辄数小时到一天。CLM 用「可编辑上下文 + 算力效率奖励」把这两个成本一起压。
值不值得
方向值得跟，但论文自陈三个硬伤：可能丢弃之后无法找回的信息；可编辑上下文成为提示注入与自生成指令的持久通道（安全面变大）；重写上下文会让 KV 缓存失效（社区也指出缓存技巧不完美）。做生产 agent 时更现实的做法是借鉴「记笔记 + 删中间结果 + 保留失败路径」这套行为模式，而不是直接换掉外置上下文管理。

StartLux 开源决策模型专用推理引擎 Prism：单张 H200 最高 5.3 倍，输出概率逐位一致

StartLux 开源为 StartLux-Decision 设计的专用推理引擎 Prism（此前 10 月 20 日 DeepSeek 也开源了 DeepInfer）。在单张 H200、27B 模型上，Prism 相比原 vLLM 方案加速 1.2 至 5.3 倍：同一材料回答三个问题从 92.9ms 降到 17.4ms（5.3 倍），约 256 Token 的短问题从 53.1ms 降到 19ms（约 2.8 倍）。做法针对「有限候选项算概率」而非「逐 Token 生成长文本」：只对有效候选计算输出分数，跳过 24.8 万词表的全量 Logits 计算；多问题共享同一材料时复用分词、调度与公共上下文计算；支持 TP 与 DP 组合部署。确定性方面称相同请求不受并发、批处理与 GPU 数量影响，逐位一致输出概率；7 个评测集 12351 次决策上平均准确率 92.94%（BF16 原始精度 92.97%）。

能做什么
把推理引擎从「生成式」改成「判别式」：LM Head 只在候选 Token 上算分（并对候选集合重新归一化，数学上等价于全词表打分后归一化），多问题共享材料时合并重复的分词/调度/公共前缀计算，推理结果可复现到位级。
解决什么痛点
通用引擎（vLLM/SGLang）为逐 Token 生成优化，用在决策/分类这类只需几个候选概率的任务上会浪费：24.8 万词表的 Logits 全算一遍、同一份材料被反复 prefill、批处理与并发导致评分漂移——最后一条在金融风控/合规场景是硬伤，因为同一输入必须得到同一结论。
值不值得
值得看的是「按任务形态专用化引擎」这个思路，以及位级确定性对金融场景的意义。限制：只支持自家 27B 决策模型（不是通用引擎）、加速比是特定测试场景（单卡 H200、三个问题共享材料），且没有开源生态与第三方复现。

IQuest-Q1：320B MoE（激活 15B）的 agentic CLI 基座模型

IQuest-Q1 是稀疏 MoE 的 agentic 基础模型，总参数 320B、激活 15B。三阶段训练：预训练用 Stable SplitNorm + Muon + muP 与两阶段课程（第二阶段提高代码数据配比，保持安全与最优学习率之间的稳定裕度）；中训练按领域与格式扩展数据混合；此后针对 CLI/终端类 agent 场景强化。论文把它定位为「agentic CLI 系统」的基座能力，即模型直接在命令行环境里规划、执行与自我纠错。

能做什么
把一个 320B/15B 激活的 MoE 专门对齐到 CLI agent 形态：终端里读输出、改文件、跑命令、看错误再修，而不是把 CLI 动作当成普通工具调用。训练侧的关键是保持学习率裕度与代码数据配比，让 agentic 能力不掉通用能力。
解决什么痛点
通用模型在 CLI 环境里常见的失效是「读不懂命令输出」和「一次只改一步就丢上下文」；MoE 结构则为在保持 320B 容量的同时把单次推理成本压到 15B 激活量级——这是自建 agent 平台最关心的成本/能力比。
值不值得
值得跟的是「agentic CLI」作为独立基座方向的成熟度，以及 MoE 激活比（15/320）对自建推理成本的影响。限制：目前只有论文，没有公开权重与独立基准；要判断能否替代通用模型，必须看它在真实仓库改造任务上的表现，而非论文自测。

BeNice!：让循环架构的 KV 缓存跨层共享，缓存命中率最高 +31.4%、p90 首字延迟降 83.6%

循环（looped）架构靠反复过同一组层来提升质量而不增参数，但推理时每次循环各生成独立 KV 缓存，显存随深度线性增长。论文先解决「KV 可共享性」成因不清的问题：第一阶段在预训练用 stochastic depth 诱导收缩性残差动力学，让各次循环的表示收敛到同一极限；第二阶段提出 BeNice!，把最后一次循环的 KV 缓存广播进第一次循环，训练它产出兼容残差且不掉质量（与标准微调的不共享验证困惑度持平）。该方法与多潜注意力、Kimi delta attention 等高效序列混合器以及 fp8/mxfp8/nvfp4 KV 量化正交可叠加。模拟低显存长上下文推理中：缓存命中率最高 +31.4%，吞吐最高 +23.6%，p90 首字延迟最高降 83.6%。

能做什么
给循环架构一个后训练手段，把「每层各存一份 KV」变成「只有一份可复用 KV」：先靠预训练期的 stochastic depth 造出表示收敛，再用 BeNice! 把末次循环的 KV 广播给首轮并训练兼容性。可与 MLA/KDA 与低精度 KV 量化叠加，不是替代关系。
解决什么痛点
长上下文 + 循环架构的显存墙：KV 随循环次数线性涨，直接限制并发与上下文长度；命中率与 TTFT 是线上推理成本与体验的两个直接指标，这篇给的正是这两个数。
值不值得
偏研究但方向清晰：收益要在「模拟低显存长上下文」条件下才成立，且需要改预训练流程（stochastic depth），不是纯推理侧补丁——现成模型无法直接套用。值得跟的是它与 KV 量化/高效注意力叠加后的复合收益曲线。

一篇论文指出 softmax / log-softmax / cross-entropy 标准实现里的两个数值 Bug

能做什么
给出可直接替换的 log-softmax/cross-entropy 实现，修掉「目标 logit 过大导致梯度归零」与「教师学生 logit 相等仍有梯度」两种数值误差，保持梯度性质（求和为零、相等时零梯度）。
解决什么痛点
这两类误差在训练时不报错、只是悄悄让梯度失真：置信度高的样本学不动、蒸馏在收敛区抖动。混合精度与低精度训练下概率分布尾部更容易被压平，问题更明显。
值不值得
值得在自研训练/蒸馏代码里对照检查——代价极低（换一个 loss 实现），潜在收益是训练稳定性。注意它不是框架级可配置项，需要自己核对实现是否已规避。
