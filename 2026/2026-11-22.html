OpenAI 公布反蒸馏防线：改版后各类抽取攻击平均成功率降到 1% 以下

OpenAI 11 月 20 日公开对抗性蒸馏的防护体系：对抗测试、模型训练、分类器与 API 级防护叠加，再配合对协同抽取行为的调查与执法，防护等级对齐生物与网络安全领域。给出的量化结果是「从早先请求抽取受保护推理」这类攻击的攻击成功率从 54% 级降到 1% 以下，改版后每种攻击类型的平均 ASR 均低于 1%。文章强调保护 reasoning trace 本身就是安全边界：被蒸馏的模型会脱离原有拒答与审核。

能做什么
四层叠加：训练阶段硬化、推理侧分类器、API 级行为限制，加上对批量抽取账号的调查与封停；公开的度量是各攻击类型平均 ASR <1%。
解决什么痛点
蒸馏把前沿能力复制到没有同等防护的模型上，再用它做原模型会拒答的事（如网络攻击）；单靠输出过滤挡不住成规模的抽取。

值得关注两条：一是「保护推理过程」正成为供应商的默认立场，做二次训练/评测数据管线的团队要重新评估合规边界；二是它和本月两条用量政策收紧是同一套逻辑。

Gemini CLI v0.70.0：策略引擎换 re2js 线性时间匹配，跳过启动命令不安全的系统 MCP server

v0.70.0 把策略引擎里 argsPattern 的求值换成 re2js，避免正则回溯导致的线性时间退化，等于给策略匹配上了执行时间上限。安全侧新增：启动命令权限不安全的系统级 MCP server 会被跳过；对含未解析变量展开的 shell 命令继续保留 ASK_USER 确认；commandPrefix/commandRegex 规则改为匹配顶层命令参数，减少误放行。可用性上，models 列表现在报告准确的输出 token 上限，请求超时超过 300 秒时同步放大 undici 的 bodyTimeout。

能做什么
策略求值不再可能被恶意正则拖死（re2js 线性时间），系统 MCP server 的启动命令要先过权限检查，shell 展开无法解析时强制问人。
解决什么痛点
agent 工具的 allow/deny 规则本身就是攻击面：正则回溯能让策略进程卡住，系统级 MCP server 又常以高权限启动。
值不值得
值得跟进，尤其你在用 MCP + 细粒度命令策略；升级后要复读自己的 commandPrefix 规则，因为匹配对象改成了顶层命令参数。

Entire：前 GitHub CEO 做的 agent 原生 Git 平台，用 trails 给每次推送打合并分数

Entire 是 Thomas Dohmke（前 GitHub CEO）做的代码托管平台，判断 PR 模式不适合 agent 高速迭代：合并请求的时间线变成只有 agent 会读的审计日志。它的核心对象是 trails——按缺陷工单或需求发起、可跨多个仓库，每次推送都会触发云沙箱里的评审 agent，从代码质量、安全性、slop（低质量代码）与是否需要人工评审四个维度打分并给理由，界面同时显示最近 5 轮与当前结果，分数稳定前应继续迭代；仓库级 Gates 定义合并门槛。平台称推送速度最高达 GitHub 的 89 倍，另配 continuous memory：两个开源工具把仓库图谱与历史会话、Git 历史合成持久记忆层。

能做什么
把「能不能合」变成可迭代的分数：每轮推送重新评审，看 5 轮趋势而不是单次结论，Gates 定义硬门槛；continuous memory 给 agent 提供「变更原因」的上下文。
解决什么痛点
agent 一天能提几十个 PR，人类评审跟不上，时间线也读不完；单次评审经常漏掉关键问题。
值不值得
值得关注它的评分口径（质量/安全/slop/人工必要性）——这套指标能直接搬进内部 CI 门禁；限制是平台绑定，89 倍推送速度是官方数据，尚未有第三方复现。

Kata Containers 4.4.0：快照恢复保留设备生命周期，CLH 上用 VMDK 装多层 EROFS

4.4.0 的重点在 runtime-rs：快照恢复时保留设备生命周期状态（dragonball 后端），并补完热插块设备与 VFIO 设备的清理链路；Cloud Hypervisor 后端改用 VMDK 磁盘格式承载多层 EROFS 容器镜像，减少逐层拉取；热插前先显式预留 PCIe root port 地址，避免地址冲突；网络清理从 Tokio worker 里隔离出来，防止阻塞运行时主循环。部署侧 kata-deploy 支持追加 CRI 配置、保留未改动的 mtime、写入 TOML 时保留空数组，devkit 安装要求 kata-ctl；GPU 侧 dcgm-exporter 升到 4.8.4，nvgpu 镜像带上 kata-ctl。

能做什么

火山引擎把企业上下文做成目录树：规则召回率 43%→100%，Issue Fix 机器人两天提 67 个 PR

能做什么
用目录树 + 分层摘要 + 上下文编译，把散落的文档/代码/Wiki/指标变成 agent 可寻址的上下文；规则单独成类保证不漏，ACL 在检索期生效，记忆与 Handoff 做跨会话沉淀。

值不值得
值得看它的分层与 ACL 设计——这两点决定了「上下文」能不能进生产；目前数据来自厂商自述（召回 43%→100% 的口径要看 benchmark 定义），但目录树 + 检索期授权这套结构对多租户 agent 是可复用的。

vLLM v0.34.0：KV cache 改为按剩余显存自动定容，Model Runner V1 移除，GB200 解码快 1.95 倍

v0.34.0 是 1061 个 commit、412 位贡献者的大版本，新增 10 个模型（含 Mistral Large 4 的 1T 总参/52B 激活、MiniMax-M3.1-Flash、Nemotron-3.5-Transcribe）。最大变化是可扩展 KV cache 默认开启：显存按 warmup 与 CUDA graph 捕获之后实际空闲的内存来定容，MiniMax-M3 在 H200 上从 433k 扩到 672k token；代价是部分模型在并发 128 时 TPOT 上升 6–18%，可用 --gpu-memory-utilization 0.9 或关闭该特性退回。Model Runner V1 被删除（V2 成为唯一 GPU runner），默认 block size 从 16 改为 64，ROCm 7.2 产物不再发布，要求 huggingface_hub ≥ 2.0.0。性能上 Blackwell 解码最高 1.95 倍（GB200 上的 Step5）、GLM-5.3-Flash 吞吐 1.6 倍、长 prompt TTFT 改善 1.24–1.40 倍。

能做什么
KV cache 从「按 gpu_memory_utilization 估算」改成「按 warmup 后的真实空闲内存定容」，同一张卡能装更多 KV；同时删掉 V1 runner、统一走 MRV2（含投机解码与 DCP 的 dual-batch overlap）。
解决什么痛点
显存估算偏保守导致 KV cache 留白、高并发时 TTFT 变差；配置项又要人肉按卡型试。
值不值得
跑推理服务的话这是必须评估的升级点：多数场景应直接删掉 gpu_memory_utilization；但 block size 64、MRV2 唯一、ROCm 与 fp_quant/Marlin W4A8 的移除都是破坏性变更，先在灰度集群验证 TPOT 与 OOM。

Dynamo v1.5.1-kimi-k3-post.1：Kimi-K3 跑在 SGLang 后端，GB300 给出聚合与 1P1D 两套配方

这是一个实验性快照发布，明确不建议上生产：把 moonshotai/Kimi-K3 跑在 Dynamo 1.5.1 + SGLang 0.5.18 的运行时上，并内置两个 Kimi-K3 必需的修复——DCP prefill/decode 配合 DSpark draft-KV 传输，以及 SM100 上 MoonViT 的 cuDNN 守卫。GB300 给了两套配方：聚合式用 2 个 worker、16 张 GB300、DCP8 attention + TP8 MoE、带 load-aware 路由；分离式是 1P1D，prefill TEP8、decode DCP8+TEP8，KV 走 Mooncake over NVLink。配方里还带了 64K 输入/400 输出/90% KV 复用率的 agentic trace 的 AIPerf 回放。

能做什么
把新模型的上线前置工作做成可复用的容器与配方：镜像、并行度（DCP/TP/TEP）、KV 传输后端与压测 trace 都给全，换模型时不用从零调并行。
解决什么痛点
新模型（尤其是带 DSpark 草稿的 Kimi-K3）在 vLLM/SGLang 上常有缺失的 kernel 补丁，团队要自己踩；GB300 这类新硬件配方更稀缺。
值不值得
适合当作模板：它的价值是「K8s 上跑 16 卡大模型的配方长什么样」，而不是版本号本身；实验性构建 + 单模型，生产要等 1.7 稳定线。

BuildKit v0.35.1：恢复与 docker pull 共享快照键名，修大文件同步模式列表报错

0.35.1 是补丁版：跳过空的 attestation manifest；恢复 v0.33.x 之前允许的「与 docker pull 共享快照键名」的行为；修掉 filesync 模式列表过大导致报错的回归。

能做什么
三处修复分别对应：空 attestation 造成的 manifest 异常、与 docker pull 共享快照键导致的重复拉取、大仓库 filesync 规则过多时的失败。
解决什么痛点
0.33 起的回归会让多工具共用同一镜像缓存的构建变慢或直接报错。
值不值得
值得跟一个小版本：如果 CI 里 buildkit 与 docker pull 混用同一 store，0.35.1 修的就是你；无破坏性变更。
