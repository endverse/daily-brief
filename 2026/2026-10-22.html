OpenAI 案例：Terminal X 的 Eval Agent 按 54 条 rubric 给投资建议打分，与资深投资人一致率 88.6%

OpenAI 10 月 20 日发布的客户案例里，资管 SaaS 公司 Terminal X 把机构的投资流程、历史决策与内部观点编码成客户自有的 agent（Capital Memory），部署在本地或客户自己的云上。它的 Eval Agent 按 54 条 rubric 逐项判定一段分析——来源准确性、论证连贯性、是否符合基金 mandate——每项只给 pass/fail，失败项附解释与修正文本或更可靠的来源，修正结果再回流成后续工作流的指令与测试用例。在 500 次打分中，跑 GPT-6.1 Sol 的 Eval Agent 与资深投资人一致率 88.6%，次优模型 86.4%（+220 个基点），偏离 mandate 的建议多抓出约 25%，单次查询成本低约 30%。这些数字全部来自厂商自述案例、未经独立审计，OpenAI 与 Terminal X 都把它定位成「工作流控制工具」而不是交易信号。

🔎 新闻要点：54 条 rubric（来源准确性 / 论证连贯 / mandate 对齐）逐项判定；500 次判定与资深评审一致率 88.6%，次优 86.4%；mandate 偏离多抓 25%；单查询成本 -30%；agent 本地或客户云部署；结果为 vendor-reported。
🔥 今日重点

DeepSeek 开源推理框架 DeepInfer：单集群日吞吐 155 万亿 Token，KVCache 落 3FS 保存 3–7 天

10 月 20 日 DeepSeek 开源大规模云服务推理框架 DeepInfer（已用于 V4.1 Flash 线上推理），同时开源生产级 Token 编解码组件 deepseek-recipe；KVCache 管理与负载均衡因与内部基础设施耦合较深暂未完整开源。架构上把视觉编码器、Prefill、Decode 三段分开部署：Prefill 用常见 8 卡服务器、Decode 用 64–128 卡超节点，MoE 在 Prefill 侧 2–8 路专家并行、Decode 侧扩到 64–128 路 Wide-EP，并按未命中 Token 数与实际计算请求数分别对两侧自动扩缩容。KVCache 被做成集群级共享数据层：以 128 Token 为 Block 分页写入独立 3FS 集群（约 100 PiB SSD），Agent 流量 TTL 3 天、Chatbot 7 天，峰值聚合读 10 TiB/s、写约 850 GiB/s，从而不必做前缀亲和路由。SWA 部分改用 Bounded Replay，缺失时只重算尾部 128 Token，官方称总 Prefill 计算量接近减半；推测解码框架 DSpark 按预测接受率变长验证，比固定验证 5 个 Token 吞吐高 6%。线上单集群日吞吐 155 万亿 Token，按谷价折算每卡每小时 38 美元。

🔎 新闻要点：Prefill(8 卡)/Decode(64–128 卡超节点) 分离 + Wide-EP 64–128 路；KVCache 128 Token/Block 落 3FS，约 100 PiB，TTL Agent 3 天、Chatbot 7 天；3FS 峰值读 10 TiB/s、写 850 GiB/s；SWA Bounded Replay 只重算尾部 128 Token，Prefill 计算量近半；DSpark 变长验证 +6% 吞吐；单集群 155 万亿 Token/天、每卡每小时 38 美元。

Cloudflare 开源 Clef 决策模型：27B 一次前向输出各选项概率，9B 版中位延迟 38.8ms

Cloudflare 在「生日周」发布 Clef——一组开源权重的决策模型，不做自由生成，而是在预设选项之间做选择。270 亿参数的多模态版本接收「状态 + 带类型问题的 Schema」，可吃文本、JSON、图像或视频，一次前向推理就返回每个问题所有可选项的概率；9B 的 Clef-Flash 面向延迟敏感场景，官方基准中位延迟 38.8ms（27B 为 209.3ms）。与 Typesafe 的 Jev System Once 相比，Clef 多了视觉编码器、上下文 64k（Jev 32k）。模型托管在 Cloudflare 边缘 GPU 上，可通过 Workers AI 调用，权重在 Hugging Face 可下载，另提供用客户自有数据微调的服务。HN 上的争议集中在两点：这是否算新范式，以及公开基准是否可信（有人指出更该测「它知不知道什么时候该放弃判断」）。

能做什么
把 agent 循环里的「分类/路由/是否升级人工」从生成任务变成分类任务：输入状态 + 类型化 Schema，输出每选项概率，无需解析自由文本；9B 版 38.8ms 中位延迟足以放进同步决策路径，并可与 Workers AI 上的 LLM 串起来做后续动作。
解决什么痛点
用通用 LLM 做路由/分单，成本高、延迟高、输出还要解析和纠错；决策模型把这一步变成结构化概率输出，便于阈值化与降级。
值不值得
如果 agent 里有大量「选一个」的环节（工单分级、工具选择、是否转人工），这一类小模型比再调一次大模型划算得多，且有开源权重可自托管。风险在基准可信度与校准——上线前必须测「该弃权时是否弃权」，而不是只看准确率。

HarnessAdapt-RL：训练时连 harness 一起进化，9B 模型 SWE-bench Verified 比 GRPO 高 9.8 个点

这篇论文指出训练 coding agent 时的常见做法是「策略更新、harness 冻结」，但训练轨迹里暴露的失败修复策略与交互问题会随策略变化而漂移。HarnessAdapt-RL 让两者一起演化：对修复策略问题，用冻结的教师模型生成任务级、机制级的 skill；对跨任务复现的交互问题，用另一个教师模型演化工具与 hook，只有观测到的 pass rate 或 trainable rate 提升且互不拉低才保留改动；策略在新 harness 下训练，新轨迹再驱动下一轮适配。9B 基座上，SWE-bench Verified / Multilingual / Pro 上比 GRPO 分别高 9.8、12.6、6.4 个点，也优于用人工设计的 OpenHands harness 的 GRPO；机制级 skill 在评测时移除后增益仍保留，而把演化出的工具与 hook 在部署时移除会掉最多 7.7 个点。

能做什么
把「模型 + harness」作为一个整体来优化：教师模型按失败类型分别产出机制级 skill（对修复策略）与工具/hook 改动（对交互问题），改动以观测到的通过率为准入条件，策略与新 harness 交替迭代。
解决什么痛点
冻结 harness 训练出的策略会把 harness 的缺陷学进权重；而手工改 harness 又靠人猜。这条路线把 harness 演进变成可度量的优化步骤。
值不值得
做 agent 训练/微调的话，结论很实用：技能可以在部署时剥离（增益保留），但演化出的工具与 hook 必须一起带走——否则掉 7.7 个点。对只做 harness 工程不训练模型的团队，也有借鉴：把「工具演进」的准入条件写成 pass rate 不下降。

TEAL：无标注下让 coding agent 自建工具库，10–15 步预算内 Sonnet-5 在 LakeQA 涨 21.7 个点

数据湖分析类问题没有标准答案标签（要专家先做一遍），所以这篇工作在无监督设定下做工具演进：TEAL 为给定的 Worker agent 演化一套工具库与使用技能，两个 agent 从互补证据提改动——Explorer 从数据湖本身提，Critic 从 Worker 的历史轨迹提；只有当 Worker 重跑时无需额外步骤就采纳该工具、且被改动过的答案有轨迹证据支撑，这项改动才被保留。在 KramaBench 与 LakeQA 上、四个 Worker 模型、严格步数预算下评测：10 或 15 步的紧预算里每个 Worker 都提升，Sonnet-5 在 15 步时 KramaBench +9.3、LakeQA +21.7；在 20 步演化的库拿到 30 步部署，LakeQA 得 68.3，高于基线 59.6 与直接在 30 步演化的 64.2。用合成问题演化的库与真实问题演化的效果相当（TEAL-Q）。

能做什么
让 agent 把每次问答里做过的发现、清洗、join 沉淀成可复用工具，且不需要标签：以「Worker 是否主动采纳」和「答案变化是否有轨迹证据」作为双重准入，避免把偶发结果固化成工具。
解决什么痛点
coding/data agent 每次任务都从头探索同一批表，重复劳动；而有监督的工具学习在真实数据湖里没有 ground truth 可用。
值不值得
对内部数据平台做 agent 的场景很直接：先把「工具库」当成一等资产，用步数预算做压力测试（紧预算下增益更大，说明工具是真复用不是补上下文）。落地门槛是轨迹证据的采集质量，也就是可观测性要先到位。

Sage-A1.5：35B MoE 长程 agent 模型，子 agent 隔离上下文 + 过程验证，转向开放式科研

Sage-A1.5 是 35B 的 MoE agent 模型，在 A1 基础上把「解单个任务」推进到「组织工作并在执行中修正方法」，三个改动：agentic orchestration 用子 agent 委派与并行协作（各自隔离上下文）来拆解复杂任务、减少并发子 agent 之间的干扰；agentic verification 用进度检查、证据校验与反思式策略修正来提升长程可靠性，让 agent 识别走不通的搜索路径并换路；open scientific discovery 把能力从回答既定问题扩到探索式研究，产出可检查的研究工件。论文以多学科科研任务做展示，定位是给社区一个可及的开源科研 agent 基座。

能做什么
一个 35B MoE 的 agent 模型把编排（子 agent 并行、上下文隔离）、验证（证据校验 + 反思换路）与科研探索（可检查的中间产物）做进同一个模型，而不是外部 harness 拼出来。
解决什么痛点
长程任务的失败多数不是单步能力不够，而是「错了不回头」和「子任务互相污染上下文」；验证与隔离是这类系统的两个结构性缺口。
值不值得
35B 规模意味着单机多卡可部署，适合评估「自托管 agent 模型能不能替代一部分闭源调用」。但论文以展示性任务为主、缺少与主流闭源模型的系统对比，先看它在你自己任务集上的可靠性再谈替换。

Épi：跨会话持续的自我改进科研 agent，产出 120 项纪录，算法解题比 Codex 高 5.4% 而成本仅 64%

Épi 是一个能跨模型会话持续同一项研究的自主 agent，靠持久研究历史、分层记忆、分支与独立评审来保持连续性并从实验里学习方法。它的实验跨会话运行、由固定 verifier 评判，共产出 120 项纪录：12 个族的 20 个数值界纪录与 8 个族的 100 个构造纪录，包括 n-queens 常数区间收窄约 84 倍、四次 Feigenbaum 吸引子维数的严格区间收窄超过 360 万倍；还给出 Tuza 猜想在一类 split graph 上的计算机辅助证明。同一套流程的轻量版 Épi-turbo 在 30 个 FrontierOR 任务上比 Codex 总分高 5.4%，只用 64% 的模型成本（同模型、同推理强度）。

能做什么
把「研究」做成有状态的长期进程：记忆 + 分支探索 + 独立评审 + 固定 verifier，让 agent 在多次会话之间接着上次的实验往下做，并能解释自己用的方法与论证。
解决什么痛点
现有 agent 一次会话结束就遗忘，长任务变成反复重启；科研/优化类任务的收益恰恰来自「试错历史」的积累。
值不值得
数字很硬（360 万倍区间收窄、120 项纪录），说明「持久状态 + 验证器」在可验证任务上是真增益；但适用边界是可形式化验证的问题。工程上的可迁移点是 Épi-turbo 的成本结构：同模型下靠流程编排省 36% 成本还更高分。

COBOL 迁移评测：GPT-6.1 Sol 逐字节一致率 97.9%，MultiLangBench 20 语言平均 87.4%

OpenAI 10 月 19 日发布低资源编程语言研究。COBOL 迁移评测要求把现有 COBOL 程序迁到 C++/Java/Kotlin/Python/Rust 并保持行为一致，判据不是「能编译」而是隐藏测试下可观察输出逐字节相同：上一代 GPT-5.6 Sol 在低推理强度下只有 5.4%，GPT-6.1 Sol 同强度 86.6%（估算 API 成本还降 39%），提高推理强度到 97.9%。另一项 MultiLangBench 要求用 20 种语言从零实现兼容 SQLite 的数据库引擎（以数据库文件为统一接口比对），GPT-6 Astra 平均通过率 87.4%，上一代 26.8%；OCaml 25.6%→85.8%、Fortran 21.4%→83.5%、Visual Basic 27.5%→89.4%，而 COBOL 仍是最难的一门（72.1%）。难点被点得很准：COBOL 的定点数舍入语义、缺失记录处理、异常输入响应这些行为往往没写进文档，只藏在代码里。

能做什么
在受控评测里做「行为等价」的跨语言迁移：以输出逐字节一致为成功标准，而不是语法正确；MultiLangBench 还公开了评测代码与测试套件，可用同一套 SQLite 兼容性测试横向比 20 种语言的实现能力。
解决什么痛点
遗留系统迁移的真正成本在语义：COBOL 定点数截断、记录缺失处理这类规则迁移后不报错但算错账，人工评审几乎无法穷举。
值不值得
对金融/量化系统的代码现代化是最值得跟的一条线，但 97.9% 是「评测任务上的逐字节一致率」，不等于大型机核心系统可直接交给 AI——样本由 OpenAI 构造、且是短程序级任务。可行路径是先拿非核心的批处理/对账模块做影子比对（新旧并行跑、比输出），再谈扩大范围。

Cache Engineering：让 agent 直接操作 KV cache（drop / repos），成本降 27.7%、吞吐 1.2 倍

论文指出 agent 轨迹变长后，KV cache 的 I/O 与存储成为主要成本，而现有做法（裁剪或摘要历史）会改动前缀、使后续缓存失效并触发昂贵的重新 prefill，留太少上下文又掉准确率。它提出 cache engineering：agent 主动用 drop 把选定缓存排除出后续 attention、用 repos 调整保留 key 的位置编码，全程不改轨迹、不重新 prefill。由此暴露服务侧难题——相同 token 序列在不同 cache 操作序列下状态不同，前缀匹配不足以正确复用，于是他们配套设计了 AKV 引擎（对外无状态接口，内部管理有状态复用/驱逐/恢复）。实验里「工具响应滚动丢弃」策略比阈值触发的摘要平均涨 1.7 分、成本降 27.7%；AKV 上输出吞吐最高 1.2 倍、P95 延迟 1.5 倍加速，缓存策略递归自改进再省 7.1%。

能做什么
把上下文管理从「改文本」下沉到「改缓存」：drop 掉不再需要的工具输出、repos 调整位置编码，保持前缀不变因而不触发重算；配套 AKV 引擎负责有状态缓存复用与驱逐。
解决什么痛点
agent 长轨迹的成本大头是重复 prefill；trim/summarize 省了 token 却让整个前缀缓存失效，省下的和浪费的经常抵不过。
值不值得
自建推理服务+长轨迹 agent 的话，这是少见的「同时降成本、提吞吐」的机制，且暴露成无状态接口意味着业务侧改动很小。门槛是要改推理引擎（vLLM/SGLang 未必支持 drop/repos 语义），先评估你的引擎是否有对应 hook。

Token-Energy Law：用「活跃字节 × 实际耗时」预测每 token 焦耳数，覆盖架构与部署参数

论文提出 Token-Energy Law：一个紧凑、可解释的模型，用来预测稠密、全历史解码时 GPU 板级每输出 token 的能耗，把模型架构、硬件与 serving 参数（批大小、并行方式）一起纳入，而不是只看参数量。核心量是每 token 的「活跃字节」与「实际耗时」——即这一 token 解码真正从显存搬了多少权重与 KV、以及这些搬运在多少时间里发生。它的用途是给容量规划与能耗核算一个可算的公式，而不必为每个配置实测功率。

能做什么

解决什么痛点

值不值得
