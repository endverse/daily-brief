AAE：把「可证伪假设 + 正确性断言」写进 agent 循环，KaHIP 求解器 122 次实验后快 3.9×

海德堡大学算法工程组开源 AAE（Agentic Algorithm Engineering），一个给 Claude Code 和 Codex 用的算法优化 skill。用法是先和 agent 谈定基准、指标、正确性断言与实验预算，之后它自主循环四步：从 profiling 与分析出发写下可证伪假设（「改 X 会让指标提升约 Z，因为…」）、做最小改动并提交 Git、跑正确性断言、跑基准，只有「更快且仍正确」才保留，否则回滚。KaHIP kaffpa 会话的实测记录是 122 次实验、69 个假设、41 个被接受的 patch、整体 3.9× 加速；每次接受的改动都是一个可评审 patch，整场会话导出 PDF 报告，学到的技巧进跨会话共享知识库。同组把这套流程用在共享内存精确最小割上，成果进了 DIMACS Implementation Challenge 的论文（arXiv:2609.07204）。

AAE 由海德堡大学 Algorithm Engineering Group 发布，支持 Claude Code（/plugin install aae --marketplace CHSZLab/AgenticAlgorithmEngineering）与 Codex（scripts/install_codex_skill.py，调用 $aae），其他 agent 可跟随仓库里的 AAE.md。每轮实验强制三件事：先写方向与量级的可证伪假设、改动后跑正确性断言、跑基准并只在更好时保留。KaHIP kaffpa 会话累计 122 次实验、69 个假设、41 个 patch、3.9× 总加速。仓库带 10 分钟 quick-start（一个慢但正确的最短路程序 + 基准 + 正确性检查）。

E2B 2.66.0：沙箱内存从「模板写死」变成可调——模板定上限、创建时分配、恢复时换规格

E2B 2.66.0 把沙箱内存做成可调参数：构建模板时用 maxMemoryMB 设上限，创建沙箱时用 memoryMB 选实际内存，暂停的沙箱在 Sandbox.connect 恢复时可以指定新的内存与 CPU 数。onResume 在原有 'restore' / 'reboot' 字符串之外新增对象形式 {action, memoryMB, cpuCount}（Python 为 memory_mb / cpu_count），旧写法保持有效。规格只在该次 connect 真正恢复暂停沙箱时生效，沙箱承受不了的规格会被明确拒绝而不是静默降级。Template.list()、getInfo()、listBuilds() 现在返回 maxMemoryMB，CLI 的 template list 增加一列 Max RAM MiB。

AAE skill：用可证伪假设约束 agent 的每一次实验，41 个 patch 换来 3.9× 加速

海德堡大学算法工程组把算法工程循环做成 Claude Code / Codex 的 skill：setup 阶段与 agent 谈定基准、指标、正确性断言和预算，之后每轮先写可证伪假设、再提交最小改动、跑断言与基准，只有更快且正确才保留。KaHIP kaffpa 会话记录 122 次实验、69 个假设、41 个 patch、整体 3.9×。所有被接受的改动都是可评审的单 patch，整场会话导出 PDF 报告，技巧沉淀进跨会话知识库。

能做什么
把「先假设、后测量、不达预期就回滚」固化成 agent 的强制流程，并输出 Git 单 patch + PDF 报告两类可审计产物。提供 /aae 斜杠命令与 10 分钟 quick-start，其他 agent 可跟 AAE.md 走。
解决什么痛点
性能优化交给 agent 后最常见的失控是：说不清改了什么、说不清为什么快、正确性悄悄退化、想回滚找不到边界。AAE 用假设和断言把这三件事都变成硬约束。
值不值得
值得精读它的流程设计而不只是用。它证明「skill = 带断言的流程」比「skill = 提示词模板」可靠得多，可直接搬到调度器、存储引擎、编解码这类有基准的优化工作；前提是你得先有可重复基准。

Google 要把 agent 的 Workspace 访问收进自家 MCP，但 Gmail 那个至今不能发信

11 月 24 日 Google 把八套 Workspace MCP server 转为 GA，同时在 API 条款里加了 Workspace AI Tools Addendum：2027 年 2 月 1 日起，任何「本身是、或由 AI agent / AI harness / AI 模型驱动」的工具访问 Gmail、Drive、Calendar 必须走 Google 的 MCP server，伪装成非 agent 规避被明确禁止，违反可被切断访问或停号。技术面同步收紧——同日起来直接调 REST 的 agent 一律按 Standard 档配额限速，无论项目付费到哪一档。Gmail server 只能搜信、读串、建草稿、打标签，发信/回复/转发/改草稿都标注「需要 partner access，未 GA」。

能做什么
用条款把 agent 的 Workspace 数据通路统一到官方 MCP，同时用配额档位让绕过 MCP 直连 REST 的 agent 降速；非 AI 的确定性脚本、备份任务、CRM 同步不受影响。
解决什么痛点
Google 要在「让 agent 能用 Workspace」和「不让 agent 无限制读写邮件」之间划界。对平台方是治理手段，对开发者则是能力天花板：官方 MCP 拿不到发信权限，业务就断在最后一步。
值不值得
值得当作合规截止日记下来：2027-02-01 前要判定自建 agent 是否踩到定义，以及是否接受「只能读到草稿、发不出去」的功能边界。想做完整邮件自动化的，路子只剩 partner access 或换通道。

E2B 2.66.0：模板定内存上限、创建时分配、暂停恢复时还能换规格

模板构建时用 maxMemoryMB 设上限，创建沙箱时用 memoryMB 选实际内存，暂停沙箱在 Sandbox.connect 恢复时可指定内存与 CPU；onResume 新增对象形式 {action, memoryMB, cpuCount}（Python 为 memory_mb / cpu_count），旧的 'restore' / 'reboot' 字符串继续有效。规格只在该次 connect 真正恢复暂停沙箱时生效，超出沙箱能力的规格被拒绝而不是静默降级。Template.list() / getInfo() / listBuilds() 返回 maxMemoryMB，CLI 的 template list 多一列 Max RAM MiB。

能做什么
同一模板派生不同内存档沙箱；暂停后按新规格恢复，状态不用重建。内存与 CPU 一起成为运行期参数而不是部署期常量。
解决什么痛点
模板按最大用例定规格会让所有沙箱都按上限计费，按小任务定规格又会在跑大任务时被迫重建丢状态。可调内存让「保留状态」与「按需给资源」同时成立。
值不值得
值得跟进。这是把「空闲挂起 + 恢复时调档」做成 SDK 一等公民的少数方案，直接对着自建多租户沙箱平台的成本项；注意规格只在恢复时生效、且会被校验，容量规划按 maxMemoryMB 留余量。

能做什么

Mixture-of-Loops Transformer：用 KV 当跨循环记忆，700M 模型 CE token 效率 1.7×、3B MoE 十任务涨 2.1 点

Looped Transformer 靠复用共享层提升表达力但牺牲效率，MoLT 重新定义「循环之间传什么」：MoLA 把 keys/values 当作跨深度、跨循环选择性复用的记忆。MoLT-R 保留 residual stream、跨循环读本地 KV 换表达力；MoLT-KV 从 embedding 重启、只读当前循环的本地 KV 加前序循环的 memory KV，消除同位置跨循环依赖，配合 loop forcing 可并行训练，并解锁超出训练循环范围的单遍 MoL 解码。U 形 U-MoLT 把记忆构建与预测读出分离、跳过无用的 decoder 遍历。400B token 预训练下，U-MoLT 在 700M/1.5B dense 与 3B MoE 上全面优于 OLMo3，700M 达 1.7× 验证 CE token 效率，3B MoE 十域困惑度改善 0.75、十任务准确率 +2.1 点。

能做什么
在不增加参数量的前提下，通过控制「循环间传什么」把表达力与效率同时往前推；单遍解码让推理不必真的跑满训练时的循环次数。
解决什么痛点
循环复用层的思路一直卡在效率账上：多跑一遍循环就多一遍算力。把 KV 选择性地跨循环复用、并让无用的遍历可跳过，等于把「深度」做成可调度资源。
值不值得
值得关注但不紧迫：这是架构层研究，短期不改变你手上的部署选型；如果你的推理平台按 token 成本核算，1.7× CE token 效率这类指标值得记一笔作趋势判断。

NVIDIA 让模型自己管上下文：32K 预算下 GPT 6.1 分数从 21% 到 56%，Kimi 输入 token 少 41%

现有 agent harness 在窗口满时替模型做 compaction 摘要；这篇研究反过来——给模型一个 context API，由它自己决定何时、压缩什么。作者在 NVIDIA 开源 harness nooa 里给了模型这个控制权，在文档研究与机器学习工程两类任务、8K 到 512K 的预算区间对比两种策略：会用 API 的模型准确率更高且常常输入 token 更少，紧预算下尤其明显——GPT 6.1 在 32K 预算的 OfficeQA Pro v2 上从 21% 升到 56%（近三倍），Kimi 最多省 41% 输入 token。但模型之间差异极大：用 API 的频率、压缩力度、开始压缩的时机都不同，改提示词就会改时机。作者还证明推理引擎能降低这种编辑的成本：复用未改动后缀的 KV cache，每请求 prefill 计算最多减 15%，准确率无可测变化。

能做什么
把「什么时候压缩上下文」从 harness 的固定策略交给模型自己判断，并把压缩变成推理引擎可增量重算的 KV 编辑；结果是紧预算下准确率与 token 效率同时改善。
解决什么痛点
harness 统一 compaction 的坏处是「一刀切」：简单任务被过度摘要，复杂任务摘要得太晚。模型自管上下文能按任务调节，但代价是行为差异大、提示词一变时机就变。
值不值得
值得读，因为你正在做多用户多会话的 agent 平台：结论直接指向两个可落地点——暴露 context API 给模型、以及让推理引擎支持 KV cache 编辑以降低 prefill。也要注意「模型间差异大」意味着不能指望换模型后行为不变。

ELITE：不在进化环里跑下游评测，SWE-bench Pro 从 60.0% 提到 85.6%

自我改进的 coding agent 通常用「evaluate-and-select」：把候选实现放到下游任务上跑，用结果决定哪条血统继续。这篇问的是能不能在进化环里完全不跑下游评测。ELITE（Explore-then-Integrate）每一代让 agent 提出多个聚焦改进、从同一父本独立实现，然后检查这些程序找出互补/冗余/冲突的机制，再把兼容子集重新实现成一个连贯后代；环内只用结构化与运行有效性的确定性检查，不用任务成绩或解题轨迹。SWE-bench Pro 上把初始 agent 从 60.0% 提到 85.6%，对比 evaluate-and-select 的 86.7%。

能做什么
把「多方案探索 + 机制整合」作为进化算子，用确定性检查替代昂贵且有基准污染风险的下游评测；一次整合出一个连贯的后代而不是留下多条互斥血统。
解决什么痛点
evaluate-and-select 的两个死结：探索越广评测成本越高；反复对固定评测分布优化会滑向基准特化。ELITE 用「不看下游成绩」绕开两者，代价是略低的天花板（85.6% vs 86.7%）。
值不值得
值得看它的取舍逻辑，尤其如果你在搭自改进 pipeline：用确定性有效性检查替代下游评测，能把进化成本压到常数级。1.1 个点的让步换来的是没有评测成本和基准污染风险。
