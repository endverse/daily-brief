Cloudflare ADLC：用可编程 Workflows + 信任棘轮，把 agent 开发生命周期做成「自动化软件工厂」

Cloudflare 提出智能体开发生命周期（ADLC），目标是取代人在回路的传统 SDLC：核心编排层用 Workflows，能动态生成容器、跑无头浏览器、调度子智能体，并在其上推出直接跑在 Workflows 上的 @cloudflare/ci，让 agent 自主处理故障、修复和故障分诊。安全侧引入「智能体访问模型」——agent 拿到的是绑定任务的短期凭证并设权限上限，一旦碰到受保护资源，「信任棘轮（Trust Ratchet）」会动态降权、强制最小权限，防止处理恶意输入时横向越权。可观测性用兼容 OpenTelemetry 的追踪，能回放会话、看子智能体交接与 token 消耗。

ADLC 把 CI/CD 从静态流水线升维为可编程工作流：动态起容器、并行预览部署、原子化变更、生产数据驱动的自改进闭环。安全在网络层和 harness 层强制执行，用短期任务凭证 + 信任棘轮动态降权实现最小权限。工具仍处早期迭代。

CNCF：为什么 agent 需要一套云原生 harness

CNCF 撰文论证：编码 agent 从「聊天框」变得真正有用，靠的是四件事同时到位——有能力的工具、共享的仓库与文件系统、子智能体、以及把系统学到的东西沉淀下来的 skill。文章把这四点抽象为一个「agent harness」，主张它应该长在云原生基础设施上（可编排、可隔离、可复用），而不是各家自己拼一套。核心观点是：agent 的生产化不是换个更强模型，而是给它配一套像 K8s 承载工作负载那样的运行时底座。

能做什么
把 agent 生产化拆成四要素（工具/共享文件系统/子智能体/skill），并论证这套 harness 应云原生化：像调度普通工作负载一样调度、隔离、复用 agent 运行环境。
解决什么痛点
当前 agent 栈各自为战、缺共享状态与隔离标准；文章指向用云原生底座统一承载，解决多 agent 协作时的文件共享、子智能体编排与经验沉淀。
值不值得
对你「多用户 agent 上 K8s」的方向是纲领性参考——它把你面对的沙箱/隔离/多路复用问题放进了 CNCF 语境。偏理念论述、暂无落地组件，适合用来对齐方向而非直接抄实现。

能做什么

Block Sparse Attention with Log-Linear Complexity（PISA）

长上下文受限于自注意力的二次成本，块稀疏注意力是高效替代，但选哪些块保留本身仍是瓶颈——常规块选择要给所有 query-block 对打分，复杂度还是二次。论文提出 PISA，用金字塔 Top-K 逐层收窄候选，把块选择做到对数线性复杂度。

能做什么
PISA 用金字塔式 Top-K 选择策略逐步收窄候选块，把块稀疏注意力的块选择开销从二次降到对数线性。
解决什么痛点
长上下文推理里，稀疏注意力虽省了算力，但块选择本身仍二次，成了新瓶颈；PISA 直接攻这一步。
值不值得
对关注长上下文推理成本的场景有价值——属推理 infra 层优化。是研究论文，是否已进主流推理框架需自查，暂当趋势信号。

Disaggregated Quantization：给 LLM 的 prefill 与 decode 分别定制量化

prefill 和 decode 对量化的诉求不同：低精度算术加速 prompt 处理，紧凑权重减少生成阶段的内存流量。论文提出「解耦量化」（DQ），为两个阶段分别定制计算格式、权重和存储放置。在 Qwen 3 和 Gemma 3 上，专门在 decode 阶段去掉激活量化能提升 decode 密集任务的精度，且不增加推理成本。

能做什么
把 LLM 的 prefill 与 decode 两阶段的量化策略解耦，分别定制精度/权重/存储放置；在 Qwen3、Gemma3 上 decode 去激活量化提精度且不增成本。
解决什么痛点
统一量化方案对两阶段并非都最优；解耦后能针对各自瓶颈（算力 vs 内存带宽）分别优化。
值不值得
对自建推理、抠 decode 精度/成本的场景有实操价值。属模型压缩细分技术，需要对量化管线有一定掌控才能用上。

SLCA-GRPO：解决工具调用 RL 里的跨段信用错配

工具调用 agent 的输出是异构的——结构化工具调用与面向用户的自然语言摘要交织。标准在线 RL（如 GRPO）会把一个轨迹级标量优势无差别广播给所有 token，导致摘要生成的梯度噪声泄漏进工具决策 token，造成跨段信用错配、训练脆弱。论文提出 SLCA-GRPO 分段处理这一问题。

能做什么
针对工具调用 agent 的异构输出，把信用分配按「工具调用段/自然语言段」分离，避免摘要梯度噪声污染工具决策 token。
解决什么痛点
GRPO 等把轨迹级优势平摊到所有 token，在工具调用场景导致信用错配、训练不稳。
值不值得
对自己训 tool-use agent 的团队有价值，是 RLHF/agent 训练的细分改进。只用现成 agent、不自训则关系不大。

循环语言模型的深度自适应推理：连续深度批处理

循环语言模型的一大卖点是深度自适应推理——通过对共享层块循环可变次数，模型能对「简单」token 少算、「难」token 多算。但不同循环次数的 token 无法共享统一前向传播，因而无法被 vLLM 等标准批处理系统处理，实用价值取决于批处理能否高效。论文提出首个高效的连续深度批处理方案。

能做什么
为循环 LM 的深度自适应推理设计连续深度批处理，让不同循环次数的 token 也能高效批处理，补上 vLLM 类系统无法处理的空白。
解决什么痛点
深度自适应推理理论上能按 token 难度分配算力，但缺乏高效批处理就无法落地服务；这是把它变成可部署能力的关键一步。
值不值得
对做 LLM serving infra、关注吞吐与算力分配的你切题——它触及推理服务系统层。属研究阶段，是否已有生产实现需自查，先当技术趋势跟踪。
