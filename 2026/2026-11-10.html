Google 给出跑在 K8s 上的开源 AI-native 栈：OpenRL + llm-d 1.0 + Agent Substrate + gVisor

Google Cloud 在 KubeCon NA 2026 把「AI 负载跑在 Kubernetes 上」拆成六个开源组件：OpenRL（K8s 原生 RL 后训练服务，研究者只写 forward_backward/optim_step/sample/save_state 四个 Python 原语，OpenRL 翻译成 K8s 调度；训练与 rollout 在同一批加速器上时间片交错，只传权重 delta，并按上下文长度/batch/LoRA 配置自动用 DRA 装箱）、llm-d 1.0（前缀缓存感知路由 + HBM→主机内存→NVMe/Lustre 三层 KV offload + 基于 LeaderWorkerSet 的 EPD 分离）、KubeRay、Agent Substrate、gVisor、TorchTPU。llm-d 给出的生产数字：KV cache 命中率从 35% 提到 70%，多轮 agent 的中位 TTFT 降 70%–85%。路由由 Gateway API Inference Extension 的 Endpoint Picker 实现，GKE 用 Inference Gateway 原生托管，文末附了 InferencePool + PrefixCacheAware 的样例 manifest。

Addy Osmani：用 coding agent 的工程师其实在做管理，要建验证机制而不是逐行读代码

Anthropic Claude Code 团队工程师 Addy Osmani 11 月 8 日发长文《Your Coding Agents Made You a Manager》，InfoQ 编译。核心论点：选任务、写指令、分配、跟进、验收这套动作和管一支工程团队没有区别，所以解法不是把自己变成最终测试员，而是建让 agent 自己验证的机制。落地手段很具体：把测试套件、构建检查、Linter 交给 agent 自查，UI 任务让它开浏览器看实际效果；测试命令写进 CLAUDE.md，用 /goal 每轮检查目标是否达成，用 Stop Hook 阻止类型检查不过的任务结束，用 /code-review 让独立子 agent 审代码。任务上下文只补 agent 查不到的东西——为什么做、有什么约束、怎样算成功，例如「把万人规模组织的 /team 仪表盘 p95 加载降到 2 秒内、不改数据库 schema 与 API 响应结构，并用指定脚本验证」。同一个问题纠正两次就写进 CLAUDE.md 或封装成 skill，同时定期清理过期规则，避免指令文件自己变成维护负担。最后一条反直觉：agent 越强，人越该少干预（借 Andy Grove 的管理理念）。

能做什么
一套可抄的 agent 管理工作流：验证机制（测试/构建/lint/浏览器）+ 目标检查（/goal）+ 结束闸门（Stop Hook）+ 独立评审（/code-review 子 agent）+ 经验沉淀（CLAUDE.md / skill），并把上下文限定在仓库里查不到的信息上。
解决什么痛点
agent「看起来完成」就停下、review 成为流水线里最稀缺的资源、每次会话从零开始重复纠错——这三件事是 coding agent 上量后真正的瓶颈。
值不值得
最值得直接照做的一篇：门槛为零，全是 Claude Code 已有功能；对你在公司推 agent 实践、以及写 skill/CLAUDE.md 的组织方式都有现成抓手。局限是绑定 Claude Code 的工具名，换到 Codex/OpenCode 要自己映射 Stop Hook 与 /goal 的等价物。

openJiuwen TTSE 双轨自演进：把「环境事实」和「执行方法」分开学，五个基准验证

openJiuwen 提出 TTSE（Two-Track Self-Evolution）双轨自演进框架，起点是一个很具体的失败模式：同一个模型和 Harness，换成自己的文件就反复返工——因为环境认知没有跟着更新，旧方法在接口/格式变化后成了障碍。TTSE 借鉴认知科学对陈述性知识与程序性知识的区分，把经验拆成 FACT（环境属性与规律，可直接验证、跨任务稳定）与 TIP（执行方法，写成「在什么条件下执行什么操作」），两类各自独立编号、呈现方式与证据追踪，难判定的一律归 TIP，避免把未验证的操作当成环境事实。框架分四段：双轨知识表示 → 冷启动（首批任务 chunk 0 归纳初始库）→ 在线增量演进（每批任务后按 Blame→Retire→Contradict/Synthesize→Induce 四步更新两条轨道）→ 输出与评估。在 ALFWorld、ScienceWorld、GDPevo、SOPBench、PinchBench 五个基准、每项三次独立重复上评测，GDPevo 消融显示完整双轨优于只记事实或只记技巧的单轨；论文《A Two-Track Online Self-Evolution Framework for LLM Agents》已公开。

能做什么
双轨经验库 + 四步在线演进循环（归责→退役→矛盾/合成→归纳），每条经验可单独引用、核对与退役；框架把「环境判断」与「行动方法」用不同的验证方式区分开，并把分类不确定项默认归到可证伪的 TIP 一侧。
解决什么痛点
agent 的自我改进常把「偶然成功」固化成稳定规律，环境一变就全部失效；单轨经验库既无法解释失败归因，也无法只退役其中一半。
值不值得
对做 agent 记忆/技能沉淀方向有直接参考价值：双轨拆分比「把一切写进 memory」更可运维，且给了可测量的消融证据。门槛是要有按批次推进的任务流和评估器；目前是论文级框架，还没看到工程化实现。

千问办公 2.0：把 Agent 放进团队协作空间，跨群汇总选题、认领任务、按 ddl 建提醒

千问办公 2.0 是公测三个月来最大一次升级，核心是「协作」：建一个协作空间，把项目相关钉钉群聊、AI 听记、云文档与本地资料关联进来，同一个 Agent（小 Q）就带着这些背景工作。实测场景是编辑部三个群：让小 Q 跨群汇总「有哪些题、谁在跟、哪些卡住了」并标注信息来自哪个群，再生成任务看板；它能按群聊进展更新任务认领状态、给未定 ddl 的选题留待定、甚至按 15:00 交付自动建一个 14:00 的提醒任务。多人可 @ 同一个 Agent 接续推进，也可把回复规则设为自动判断是否接话；Agent 可加载技能市场的 skill 与专家套件。定位是与 Personal Agent 的分界：Team Agent 围绕团队共享的项目背景，而不是个人偏好。

能做什么
协作空间 = 群聊 + 听记 + 云文档 + 本地资料 的上下文池，Agent 在同一池上做跨群信息归拢、任务认领跟踪、待办与定时任务生成，多人共享同一份工作背景。
解决什么痛点
项目信息散在多个群、分工和排期随时变、换人接手要重新解释背景——这类协调成本很难靠单机版 AI 助手解决。
值不值得
值得看的是「上下文池 + 多成员共享」这个产品结构，而不是具体功能；门槛是绑定钉钉生态（群聊、听记、云文档），团队不在钉钉里基本用不上。

DeepSeek Harness：日活 154 万、插件 3.5 万个，但插件太多会反噬上下文

截至 11 月 4 日，按使用官方 API 的用户口径，DeepSeek Harness 日活 154 万、日消耗约 92 万亿 token；第三方插件约 3.5 万个，约 60% 活跃用户制作或装过至少一个。平台自我定位是「Agent 时代的操作系统」，主张一切皆插件，连内置功能都可被第三方替换。生态里出现了把 Cursor、Claude Code、Codex、OpenCode、Kimi Code 接进统一界面的 dsh-aio-agent，做本地长期记忆（中文关键词检索、按项目召回、去重）的 dsh-ltm，以及按话题把消息路由到独立会话的 TheOne。反噬同样具体：有用户装了 15 个以上插件后出现无限循环、上下文溢出与 token 暴涨，完成一个小项目的 token 消耗达到 OpenCode 的 20 倍、单任务 30–40 分钟对 30 秒；社区建议借鉴选择性披露，只在需要时把插件说明喂给模型。

能做什么
插件化 Agent 平台：3.5 万插件覆盖内容创作、设计、上下文管理、科研；「一切皆插件」允许替换内置能力；官方开始给插件作者发 token 作为生态激励。
解决什么痛点
定制化需求与开箱即用之间的矛盾：插件给自由度，但每个插件的说明与规则都占上下文，装得越多模型越分心、成本越高。
值不值得
值得作为「agent 平台该不该插件化」的一手样本读——154 万 DAU 说明需求真实，20 倍 token 成本说明代价真实。对自建 agent 平台的启示是插件描述要做按需加载，而不是全量注入 system prompt。

Anthropic 把单体仓库换成自研 Scion：日合并 3 万次，检出速度提升两个数量级

Anthropic 详解把单体代码仓库从 Git 迁到自研 Scion 的过程：把提交、合并、rebase、历史与代码追溯查询全部挪到服务端，客户端只保留容量受限的对象缓存，虚拟化检出按需实体化文件，工具可直接通过 API 查 diff、做部分写入而不必检出代码。变更集只记录相对第一父变更集变化的文件并用内容寻址指针引用 Blob，创建变更集与更新引用解耦，因此接收变更集不需要跨服务器协调。驱动力是数字：单日合并变更从 5 月约 2500 个涨到 9 月 3 万多个，CI 每天约 2500 万次检出，主分支历史接近 100GB、压缩工作副本超 25GB，浅克隆/稀疏检出/Promisor Remote/数百个 Git 镜像都开始撑不住。结果：每层缓存命中率均超 99%，CPU 与内存基础设施占用仅为原 Git 镜像的 1/200，CI 与研究任务检出速度提升两个数量级。代价是牺牲离线独立性、强依赖服务端可用性，且需要配套的评审、搜索与 CI 系统。

能做什么
服务端执行仓库操作 + 内容寻址存储 + 分层缓存（节点本地守护进程 → 区域缓存 → Spanner/云存储权威层），各层共用同一套检出协议 RPC 并强制调用顺序以隔离故障。
解决什么痛点
agent 与 CI 把检出与合并频率推高一到两个数量级后，Git 的本地全量克隆模型在带宽、磁盘与运维复杂度上同时失效。
值不值得
对架构师而言价值在「工作负载变了就要重新考虑计算放在哪」这个判断，以及缓存分层 + 强制调用顺序的故障隔离设计；门槛极高——官方明说 Scion 不是通用 Git 替代品，配套系统都高度定制。

Bedrock AgentCore Runtime V2：快照恢复把 P75 冷启动稳定在 2 秒

AgentCore Runtime V2 改了两件事：内存改为按需分页、冷会话归还，只按实际使用计费；冷启动改为「准备一次环境 → 打快照 → 每个新实例从快照恢复」。AWS 的测试里，镜像从 200MB 到 2GB，P75 冷启动稳定在约 2 秒，而旧运行时随镜像变大从约 5.4 秒涨到近 30 秒。开启方式是把创建/更新时的 platformVersion 设为 V2，代价是创建与更新要花几分钟准备快照，且容器必须在 120 秒内对 /ping 报健康、并确保只在初始化完成后才报健康。单价更高但 GB-hours 大幅减少，AWS 预计多数 agent 账单会下降（不保证）。当前在 10 个 Region 可用。

能做什么
会话级内存分页 + 环境快照恢复；V2 通过一个 platformVersion 字段切换，沿用现有 runtime 与健康检查协议。
解决什么痛点
agent 冷启动是 serverless 形态最大的体验敌人：镜像一大就几十秒，用户等着、按峰值预留内存又在烧钱。
值不值得
如果你的 agent 平台在多租户沙箱和冷启动之间找平衡，这份数字（2s 稳定 vs 5.4→30s）是最直接的对照；限制是绑 AWS、创建期变慢、且 /ping 语义容易踩坑（先报健康再初始化会拿到假就绪）。

蚂蚁灵波开源 LingBot-Touch：近 5000 小时触觉数据，真机成功率提 14–26 个百分点

蚂蚁灵波 11 月 10 日开源触觉基础模型 LingBot-Touch，基于近 5000 小时真实触觉数据预训练，同时覆盖磁触觉、视触觉与压阻式三类传感原理。架构上按传感原理分别设编码入口，再把不同触点布局映射到统一的指尖坐标空间，输出统一的触觉 Token——这样人戴触觉手套采的数据与遥操作灵巧手采的数据可以一起训练。在 Sharpa Wave 与 XHand1 两款灵巧手上做了 26 项真机测试（翻书页、拧瓶盖、辨识麻将牌等），接入后 LingBot-VLA、π0.5、Diffusion Policy、T-Rex 四种动作模型平均任务成功率提升约 14–26 个百分点；T-Rex 控 Sharpa Wave 拧瓶盖从不用触觉的 56.25%、直接喂原始信号的 62.5% 提到 90%。轻量版 Tiny 约 530 万参数，接入后模型参数只增加 0.13%–0.16%；技术报告、模型与代码已在 Hugging Face、GitHub 与魔搭开源。

能做什么
跨传感原理的统一触觉表征：分原理编码 → 统一指尖坐标 → 共享模型输出触觉 Token，可跨传感器、跨灵巧手、跨动作模型复用，并为新传感类型留了扩展位。
解决什么痛点
视觉看得到位置却判断不了受力是否合适、物体是否滑移；不同触觉传感器的原始信号不通用，换硬件就要重采数据重训。
值不值得
值得关注的是「统一表征」这个思路本身（和 tokenizer 抽象一层传感器是一个路子），而不是机器人本身；门槛在数据与硬件，纯软件方向能借鉴的是分模态编码 + 统一坐标空间的设计。

值不值得

Akamai 的答案：让 agent 提 PR 的前提，是平台能吸收一个「格式完美但完全错」的改动

Akamai 内部 K8s 平台团队在 KubeCon EU 2026 的分享：该不该让 coding agent 对基础设施提 PR，答案与 agent 无关，取决于平台能否吸收一个自信、格式完美但完全错误的改动——如果不能，这个洞在 agent 出现前就存在。他们按五层堆防护：测试（规格/TDD 先行 + canary 集群，因为天天在建集群）、配置抽象（kro / ResourceGraphDefinition 把一组资源收成一个自定义 API，租户只看到 K8s 版本、节点数、区域三个字段；应用侧用 Score 转译，Crossplane 建云资源、Argo CD 收敛）、K8s 自带保护（最小权限 RBAC、带健康探针的滚动、PDB、finalizer、Kyverno 在 API 层拦截）、云厂商删除保护（Crossplane Usage 拒绝删除并约束顺序）、人工评审（CODEOWNERS + 线性历史）。关键论证是转译器确定性、LLM 不确定——遇到没见过的字段会即兴发挥。最后他们把破坏性场景收敛成一个决策：在 kro 集群定义里置一个受保护字段，平台就自动施加上述多层保护；这套抽象花了约三年半和很多版 CRD。

能做什么
五层防护 + 把「破坏性操作」收敛成一个受保护字段：测试、确定性转译（kro/Score）、K8s 原生保护（RBAC/PDB/finalizer/Kyverno）、云侧删除保护（Crossplane Usage）、CODEOWNERS 人工评审。
解决什么痛点
agent 让 6 人团队以 30 人的速度提 PR，但评审仍是 6 人的速度，且每个 PR 的上下文更少；单点错误在 GitOps 里几秒铺满整个基础设施。
值不值得
最值得照抄的不是工具清单，而是「用确定性转译器替代 LLM 写 YAML」这个分界，以及把多层保护收敛成单一开关的产品思路；门槛是要先有一套成熟的平台抽象（他们花了三年半）。

GKE Dynamic Slicing GA：逻辑切片与物理 nodepool 解耦，启动快 5 倍、恢复快 4.5 倍

GKE Dynamic Slicing 正式 GA，核心是把「逻辑 TPU slice 的组成」与「物理 nodepool 的供给」解耦。过去每个 slice 要一套固定拓扑的静态 nodepool，改需求就得删了重建，且单个硬件故障会拖垮整条 slice。新方案用 TPU 光交换（OCS）动态把 16 VM 的 TPU cube 拼接成更大的 slice（super-slicing），或把 cube 切成小 slice 让多个负载共用一个 nodepool（sub-slicing）。官方数字：相比静态 nodepool，负载启动时间最多缩短 5 倍、故障恢复快 4.5 倍，同时支持多租户装箱与供给「部分健康」的 nodepool（把健康主机也用起来）。

能做什么
OCS 动态拼接/切分 TPU cube；提交负载时即时组装拓扑，不再删建 nodepool；可按需供给部分健康的 nodepool。
解决什么痛点
静态 nodepool 带来的慢启动、手动重建、大故障域（一个硬件故障崩掉整条 slice）是 TPU 平台运维的主要摩擦。
值不值得
对在评估 GPU/TPU 池化与拓扑感知调度的团队有直接参考价值——它说明「拓扑」正在从 provisioning 期的静态对象变成提交期的动态对象；限制是只在 GKE + TPU 上可用。

TPU Sync：TPU 上的 KV cache 与权重传输层，TTFT 平均降 90%

TPU Sync 是一个开源原生 C++ 库，设计前提是把加速器 HBM、主机 DRAM、共享存储与数据中心网络当成一套协同设计的内存层级，用异步 DMA 直接在设备缓冲上原位搬运 TPU-tiled tensor（不拷贝、不加锁），让数据搬运与计算重叠。推理侧它把主机 DRAM、本地 SSD 与 Managed Lustre 变成自动化的多层 KV cache，并把 TPU 计算与网络背压解耦；RL 侧暴露底层 DMA/DCN 原语，供上层框架把更新后的权重流式推给 rollout 采样器。官方数字：KV 传输延迟降 90% 以上，235B–480B 的开源 MoE 在 prefix-caching 与分离式服务下平均 TTFT 降 90%。它已作为 vLLM、SGLang 与 llm-d 分离式服务的 TPU KV cache connector，并通过 TorchTPU 接入 PyTorch，同时供 Pathways 与多控制器 JAX 的 RL 管线使用。

能做什么
统一内存层级 + 异步 DMA 原位搬运；推理侧做多层 KV cache 自动卸载，训练侧做权重流式广播；已接入 vLLM/SGLang/llm-d/TorchTPU。
解决什么痛点
百万 token 上下文与分离式服务把瓶颈从算力移到「搬状态」：KV cache 与权重卡在单芯片内存或网络传输上，加速器就空转。
值不值得
值得读它的分层设计与 90% 这个量级，尤其是「把主机 DRAM 与对象存储当成 KV cache 的下一层」这个做法；限制是绑 Cloud TPU/Lustre，自建 GPU 集群要自己找等价物（LMCache 一类）。

Kubernetes 三种探针的分工：liveness 重启、readiness 摘流量、startup 只在启动期生效

文章把三种探针的职责边界讲清楚：liveness 失败触发容器重启，用于进程还在但已经卡死（死锁、连接池耗尽）；readiness 失败只是把 Pod 从 Service Endpoints 摘掉、不重启，用于依赖未就绪或过载时停止接流量；startup 只在启动期生效，成功后才把控制权交给 liveness，用于避免慢启动应用被误杀。参数上 initialDelaySeconds / periodSeconds / timeoutSeconds / failureThreshold 要按应用真实启动曲线给，startup 探针的 failureThreshold × periodSeconds 实际上定义了允许的最长启动时间；没有 readiness 的滚动更新会把流量打到还没准备好的 Pod 上。

能做什么
三种探针的语义分工与参数语义，以及「startup 保护慢启动、readiness 控流量、liveness 治卡死」的组合用法。
解决什么痛点
探针配错的两种典型事故：慢启动应用被 liveness 反复重启；没有 readiness 时滚动更新把请求打到未就绪实例，表现为发布期间 5xx 尖刺。
值不值得
建集群做业务接入规范时可以直接拿来当基线要求（每个工作负载必须定义 readiness，慢启动必须加 startup）；内容偏入门，价值在于把三者边界写清楚、避免混用。

CNCF 调研：VM 仍占生产应用 53%，AI/agent 负载正在推动 VM 用量回升

Linux Foundation Research 受 CNCF 与 Broadcom 赞助，调查 492 名云原生从业者（2026 年 9 月）。核心数字：受访者平均 53% 的生产应用跑在 VM 上，51% 表示至少一半应用是 VM；万人以上组织平均 64%，500 人以下为 45%；71% 预计未来 12 个月 VM 占比维持同一区间。扩 VM 的原因里，53% 提到 VM 应用增长、48% 提到硬件利用率、47% 提到安全与隔离需求、34% 明确提到 AI 与 agent 负载。62% 的受访者已用至少一种 VM 级隔离（硬件 VM、VM 内容器、microVM 沙箱）；管 VM 与管容器的团队有 61% 是协作或完全一体，14% 仍各自为政。用 KubeVirt 在 K8s 上管 VM 的只有 8%，用 microVM 运行时的 2%。

能做什么
492 人样本的 workload 结构数据：VM 占比、组织规模差异、扩 VM 动因、隔离方式采用率、VM/K8s 团队协作度。
解决什么痛点
「全面容器化」的叙事与生产现实有落差：VM 仍是主力，而 AI/agent 负载因为要隔离不可信代码，反而在推高 VM 用量。
值不值得
对建集群方案有直接参考意义——它支撑「K8s 之外 VM 长期共存」的判断，也说明 agent 沙箱的需求真实（但 KubeVirt 采用率只有 8%，说明 K8s 管 VM 仍非主流）。
