🔥 今日重点

FDE-Gym：把「AI 交付的最后一公里」做成 95 个真实客户任务——最强配置只解决 14 个

FDE-Gym 是一个针对 forward-deployed engineer（FDE，前向交付工程师）的交付型基准：95 个端到端交付任务取自 20 个客户场景、覆盖 18 个行业，由行业专家从真实交付项目改编。评测环境模拟客户系统与「有脚本的利益相关方」，agent 要与客户对话、在类生产系统上操作，最终交付按「客户自己的业务指标改善幅度」打分——0 分为系统无变化、1 分为参考解，并对交互（消息、试跑、等待时间）扣分。论文评测了来自 7 家供应商的 13 种模型配置：在需要自己挖出未言明约束的真实设定下，最佳配置平均分 0.56，95 个任务里只有 14 个达到「分数 ≥0.8 且无事故」的解决标准。瓶颈被定位为「发现未言明的约束」，但信息发现本身不足以解释差距：即便只看最佳配置已从客户处拿全所有关键事实的 23 个任务，也只有 10 个达到 0.8 以上的归一化业务提升。作者同时开放了一个在线平台，让人类按同一套标准练习 FDE 技能。

🔎 新闻要点：95 个端到端交付任务 / 20 个客户场景 / 18 个行业，由行业专家改编自真实项目；打分 = 客户业务指标改善（0 = 系统无变化，1 = 参考解），并对消息、试跑、等待时间扣分；评测 13 种模型配置（7 家供应商）；真实设定下最佳平均分 0.56、95 个任务只解决 14 个（≥0.8 且无事故）；在最佳配置拿全关键事实的 23 个任务中仅 10 个达 0.8+；瓶颈为「发现未言明的约束」；提供人类可用的在线练习平台。
🔥 今日重点

LeaderWorkerSet v1.0.0 GA：DisaggregatedSet 支持分角色独立扩缩，gang scheduling 仍是 alpha

kubernetes-sigs 的 LeaderWorkerSet（LWS）于 2026-10-16 发布 v1.0.0，主线是把「一个 leader + N 个 worker 作为一组」这套多节点推理 / 训练编排抽象的发布协调与扩缩补齐。rollout 窗口改为按各角色副本数按比例推进，允许新批次在旧批次完全 Ready 之前启动，同时不突破配置的 maxSurge / maxUnavailable 预算（#907）；滚动更新期间仍可扩容，并可选地在更新完成前缩容（KEP-1022）。新增「可独立扩缩的子角色」：把同一角色拆成共享同一 workload 配置的扩缩池与路由池，组标识支持 Ordinal 与 Hash 两种（KEP-960）。原生 gang scheduling（KEP-666）修了 PodGroup 生命周期与组大小更新处理，组重建与改大小的 rollout 不再把负载卡死，但该集成仍是 alpha 且需显式开启。组恢复新增边界：maxGroupRestarts 限制每个副本组的自动重建次数、restartBackoff 限制重建频率（KEP-820）；podTerminationPolicy: Parallel 让 leader 与 worker 并发终止，Sequential 仍为默认（KEP-956）；控制器配置 API 毕业为 config.lws.x-k8s.io/v1，v1alpha1 弃用但继续支持。

🔎 新闻要点：2026-10-16 发布 v1.0.0；fractional rollout window 按角色副本比例推进（#907）；KEP-1022 更新期间扩缩容；KEP-960 独立可扩缩子角色（Ordinal / Hash）；KEP-666 原生 gang scheduling 生命周期修复（alpha、opt-in）；KEP-820 maxGroupRestarts / restartBackoff；KEP-956 podTerminationPolicy: Parallel（Sequential 仍为默认）；配置 API → config.lws.x-k8s.io/v1（v1alpha1 deprecated）；破坏性默认变更 #1169——未配 rollingUpdateConfiguration 的 DisaggregatedSet 角色变为 maxSurge 0 / maxUnavailable 1。

LEASH：用弱模型隐状态的不确定性决定「何时交给强模型」，OSWorld 上比随机升级高 6.55–11.94 分

长程 computer-use 任务里每一步都跑前沿模型太贵、小模型单独跑又常失败，weak-to-strong 升级是折中方案，难点在「何时升级」需要一个每步都能廉价获取的不确定性信号。LEASH 是免训练框架，三层：先用初始任务不确定性做早期路由，再用步级不确定性决定运行时升级；交接之后用一个 shadow observer 继续监督强模型——因为强模型通常以黑盒 API 形式提供，暴露不出内部状态。不确定性信号来自弱模型自身隐状态与它过去成功 / 失败轨迹隐状态的比较（越像失败轨迹越不确定），并且复用动作生成时已经产生的激活，不需要额外前向传播、也不需要专门训练监控器。在 OSWorld 上、四种当代模型底座下，LEASH 一致优于单独跑弱模型，并在匹配升级率的前提下比随机升级高 6.55—11.94 分。

能做什么
在「弱模型默认跑、只在必要时升级到强模型」这条线上，给了一个免训练的三层方案：初始任务不确定性做早期路由 → 步级不确定性做运行时升级 → shadow observer 在交接后继续监督；不确定性复用动作生成时已有的隐状态，不需要额外前向或训练监控器。
解决什么痛点
全用前沿模型逐步跑 computer-use 成本不可接受，而小模型单独跑长程任务会失败；现有升级策略要么靠固定规则、要么随机交接，等于把贵的算力花在不该花的地方，而且黑盒强模型交接后没人监督。
值不值得
你在评估多用户 agent 沙箱与成本控制时，这种「廉价不确定性信号 + 分层升级」是直接可借用的思路，尤其它复用已有激活、不引入额外推理开销；限制是实验只在 OSWorld 上做、不确定性强依赖弱模型的隐状态可读（走闭源 API 的弱模型用不了）。

MAI-Gym：GUI agent 的评测、数据采集与在线 RL 训练合成一个平台，训出 9B 模型在 OSWorld-Verified 拿 76.2%

GUI agent 的在线 RL 卡在交互环境成本高、真实训练任务稀缺。MAI-Gym 是开源一体化平台，用一个共享 rollout 流水线统一移动端、桌面与网页环境的 GUI agent 评测、数据采集与在线 RL 训练，保证评测与训练下的 agent 行为口径一致，支持十套既有基准并扩展到 20,000 个并行环境实例；同时能自动合成多样的 GUI 应用与有难度的任务，包括可重置的 mocked 应用、带执行校验任务验证器的连贯跨应用世界。团队用它训出统一 9B agent MAI-Gym-9B，在 10B 以下的开源 GUI agent 里取得 MobileWorld 78.4%、OSWorld-Verified 76.2%；关键迁移结果是在 mocked 抢票应用里做 RL 能迁到真实应用，真机任务成功率从 28.8% 提到 48.1%。框架、合成技能、mocked 应用、2000 个已验证任务与模型权重均已放出。

能做什么
用一条共享 rollout 流水线把 GUI agent 的评测、数据采集与在线 RL 训练打通（移动 / 桌面 / 网页），支持十套基准、可扩到 20,000 并行环境；并能自动合成可重置的 mocked 应用与跨应用任务、带执行校验的验证器；用它在 9B 规模上训出 MobileWorld 78.4% / OSWorld-Verified 76.2% 的开源 SOTA，并证明 mocked 应用里的 RL 能迁移到真机（28.8% → 48.1%）。
解决什么痛点
GUI agent 的在线 RL 受限于交互环境昂贵与真实训练任务稀缺，评测与训练环境口径还不一致，导致训出来的能力难以复现或迁移；真机环境又贵到无法大规模试错。
值不值得
你关心 agent 落地与训练成本结构，这份工作最值得看的是「mocked 环境里练、真机上涨」的迁移路径与 2 万并行实例的工程规模；限制是面向 GUI 操作类 agent，且真机迁移只在抢票这一个场景上验证过（单场景、28.8%→48.1% 的绝对值仍不高）。

Pi 1.0 推出 Harness「Pi Durable」并把 MCP 装进核心：工具搜索 + 渐进披露控制上下文，Code Mode 在 QuickJS 沙箱里写 JS 编排工具

Pi 迎来今年规模最大的一次更新：项目升级到 1.0，Code Mode 与原生 MCP 进入稳定版，同一天推出全新 Harness「Pi Durable」（架构前后经历八轮迭代；MCP 协议过去一年也经历了六七轮调整）。Pi 一年来是最直言不讳的 MCP 批评者，官网曾写着「不支持 MCP」，批评其臃肿、浪费 token；此次接入但不把工具名、参数、说明一次性塞进上下文，而是用工具搜索与渐进式披露按需加载。与 MCP 同期进入稳定版的 Code Mode 允许 agent 在 QuickJS 沙箱中编写并运行 JavaScript：并行调用工具、过滤 / 去重 / 计算，只把真正有用的结果送回模型，大量中间数据留在沙箱里，从而降低 token 消耗与上下文负担；它还支持在 JS 循环内部直接调用 System 1 小模型（如 Jev）做逐条判断，前沿模型只看分类汇总结果。Pi Durable 负责持久化用户消息、模型回复、工具执行结果与任务状态，进程崩溃后从中断处继续——可安全重放的操作重跑、可能产生重复副作用的不重跑；有开发者估计它可直接替代自己一半的代码。

能做什么
分两块：Pi Durable 接管长时 agent 运行的状态持久化（消息、模型回复、工具结果、任务状态），崩溃后从断点续跑，且区分「可安全重放」与「有重复副作用」的操作；MCP 侧用工具搜索 + 渐进式披露按需加载而非全量注入，Code Mode 则让 agent 在 QuickJS 沙箱里写 JavaScript 来并行编排工具、过滤中间数据，甚至在小循环里调用 System 1 小模型做逐条判断。
解决什么痛点
agent 崩溃后要人再输一次「继续」，工具结果与流式输出丢失；MCP 全量塞进上下文导致 token 浪费与上下文污染；中间数据（比如 200 条评论）未经处理就进入前沿模型的上下文，成本和噪声都不可控。
值不值得
你正在积累 agent 编排与 skill 实践，Pi Durable 的「断点续跑 + 副作用安全重放」与 Code Mode 的「沙箱内编排、只回结果」是两个能直接借用的模式；注意 Pi 团队的自我批评仍然成立——agent 涉及设计与架构时经常只在局部堆叠代码，长时无人运行后谁来保证代码库没被改烂是它自己也没答案的问题。

3DCodeVerse：把 3D 内容变成可执行可验证的代码，harness 在人类成对评测中对 Claude Design 胜率 90%

3DCodeVerse 是一个研究生态，目标是让 coding agent 能规模化产出可编辑、可验证的 3D 内容。它先构建 3DCodeVerse-2M：从开源数据收集、把专用表示转换、再用 coding agent 生成新程序，得到大规模可独立执行的 3D 代码数据集，每个程序打包源码、运行所需资产，以及已有的描述与验证记录。再给出 3DCodeVerse Harness——一个多 agent 有向无环图框架，用执行检查、空间测量与视觉反馈在生成过程中无人类反馈地自动评估并修订程序。实验显示在该数据集上微调能显著提升开源模型的 3D 编码能力；当两者都由 Claude Opus 5.5 使用时，该 harness 在成对人工评测中对 Claude Design（3D Object）取得 90% 胜率。

解决什么痛点

四个 Gemini 4 Argon agent 打通《我的世界》：27 小时写 2783 个程序击败末影龙，死亡 605 次

论文把四个 Gemini 4 Argon agent 放进沙盒化的 Minecraft 生存世界，只给一个目标——击败末影龙。每个 agent 通过开源库 Mineflayer 操作一个玩家，队员之间用游戏内聊天与共享记忆协作；没有人分配角色、也没有人写游戏逻辑，规划、写程序、调试全部由 agent 自己完成，研究者只能在实时面板上观察、必要时暂停。团队从随机生成、Easy 难度的世界出发，共写了 2783 个程序，用 27 小时 14 分击败末影龙，期间死亡 605 次。作者称这是首个仅用标准 Mineflayer 库、无预先探图、无人类编写的游戏专用工具的端到端自主通关；任务要求团队在超过一天的时间里跨数千个相互依赖的步骤维持连贯计划，而真实世界的软件工程与企业级任务需要同样的长程编码与多 agent 协调能力。

苹果用 4 台 Mac Studio 跑 816B 的 Muse Spark Open：36+ tokens/s，靠 RDMA over Thunderbolt 组集群

CNCF 博客介绍 Nirmata Runtime for Kyverno（开源）：Kyverno 的准入控制只能回答「这份 spec 看起来对不对」，回答不了 pod 跑起来之后「它是否在做 spec 说的事」——而对自主 AI agent 与非确定性 LLM 应用，事故大多住在这个缝里（启动后再拉二段载荷、没人收紧的 sidecar 开始连未批准目标、没有任何配置策略预料到的进程被执行）。作者主张控制要跑在负载下面（内核）而不是旁边（sidecar / agent / 用户态代理），因为旁路的控制在负载自身被攻陷时可以被看见、拖慢或绕过。实现上按 pod 把 BPF-LSM 程序挂到 bprm_check_security 与 file_open、把 cgroup 范围的 eBPF 程序挂到 egress 路径，五种行为全部在内核内同步判定：被阻止的 exec 在进程运行前返回 -EPERM，被阻止的连接不会完成，决策与执行之间没有可竞态的窗口。策略语言沿用 Kyverno 的 CEL，RuntimePolicy 用同样的 podSelector / namespaceSelector 定位负载，并支持从 ConfigMap 或 HTTP 源按刷新间隔取实时值；报告沿用 OpenReports。

能做什么
把 Kyverno 的策略执行从准入控制延伸到内核运行时：按 pod 挂 BPF-LSM（bprm_check_security、file_open）与 cgroup 范围 eBPF（egress），在内核内同步允许 / 拒绝 exec 与网络连接，策略仍用 CEL、负载定位方式与 Kyverno 一致，报告沿用 OpenReports，准入与运行时可共用一套策略语言。
解决什么痛点
准入控制只能校验 spec 声明，管不住运行时行为；而 agent 的行为有一部分是模型在运行时生成的——镜像可以审、运行时的行为没法预先审，于是二段载荷、越界 egress、意料外的进程执行都落在策略盲区里。
值不值得
你做 agent 平台的多租户隔离与网络管控时，这是「把策略执行点从旁路挪到内核」的现成开源实现，和你关注的 Agent Sandbox + 网络策略方向互补（一个管执行环境，一个管运行时行为）；限制是 eBPF / LSM 要求较新内核与相应权限，且项目较年轻，需先在小集群验证稳定性。
