🔥 今日重点

Harness 才是差距：同一份权重，ARC-AGI 从 30% 到 95%

同一份模型权重，换一套 harness，ARC-AGI 成绩从 30% 拉到 95%（Nvidia AVO 到 100%），Harness 1 与 Harness 2 之间也差 18%。Seth Karten 把上下文分成 L1 权重、L2 活跃上下文加 REPL、L3 文件系统调度状态三层，认为 harness 要在这三层之间做压缩、增删改查与 refinement，缺一项就少一项模型无法用别的方式完成的能力；子 agent 应当是可唤醒、可卸载的持久子会话，且任意两个 agent 能直接发消息。QM 给 YC 全员做的类 Claw 助手的取舍更硬：agent 的大脑（记忆、会话）全部集中到 Postgres，沙箱从「家」降级成按需取用、由 agent 自己挑提供商的资源；harness 只留三个工具——远程沙箱执行、对象存储读写、发布内部应用，定时任务与记忆都算临时补丁。Jon Saad-Falcon 给出的另一条线是本地化：本地 LLM 只落后前沿 6 到 12 个月，Qwen 3.8 27B 大致相当于 2025 年 8 月的 Claude 4.6 Opus，用云端模型只做诊断与门控、推理不出网。他们还提到 LLM-as-judge 会得「主角综合症」，看得到大象的一部分，所以 human in the loop 仍不可省。

YC Paper Club 的 Harness Night 专场，四位讲者分别从表达力、硬件边界、组织落地三个角度拆 harness。核心论据：Claude Opus 在私有保留集上只有 30%，仅靠换 harness 可到 95%，Nvidia 的 AVO 到 100%；Harness 1 到 Harness 2 之间相差 18%。Seth Karten 把上下文分三层（L1 权重 / L2 活跃上下文+REPL / L3 文件系统等调度状态），认为 harness 的职责是在层间做压缩、CRUD 与 refinement，像缓存加垃圾回收。QM 团队（给 YC 员工的类 Claw 助手）的三条设计：把 agent 大脑从沙箱挪到 Postgres、沙箱降级为按需资源且由 agent 自己选提供商、harness 只保留远程沙箱执行/对象存储/发布内部应用三个工具。
🔥 今日重点

HAMi v2.11.0：K8s GPU 共享补上 Flexible-MIG 与 Cluster Autoscaler

HAMi 2.11.0 把 K8s 上做 GPU 共享最缺的几块补齐：Flexible-MIG 加上按工作负载的真实用量监控、支持 Cluster Autoscaler（不再因为 vGPU 分配让伸缩器算错账）、Remote CUDA 可以让 vLLM 直接跑在远端 GPU 上。调度侧新增 GPU/CPU NUMA 对齐、PodGroup 支持和 mutex 策略，且不同调度策略可组合；设备侧补了完整 AMD 支持与昇腾 950。一个行为变化要注意：整卡分配不再挂载 hami-core，指标改由 NVML 直出，老监控面板要跟着改。

HAMi 是 K8s 上的 GPU 虚拟化/共享层（vGPU、MIG 切分、异构卡统一调度）。2.11.0 的关键项：Flexible-MIG 与 Flexible-MIG 工作负载的真实用量监控、支持 Cluster Autoscaler、Remote CUDA（可让 vLLM 跑在远端 GPU）、GPU/CPU NUMA 对齐、PodGroup 支持与新的 mutex 调度策略、调度策略可组合、完整 AMD 支持与昇腾 950 支持、libvnpu 性能优化。行为变化：整卡分配不再挂载 hami-core，指标改由 NVML 直出。

长上下文可能不需要：后段 token 成本可达 7 倍，频繁压缩几乎不掉点

论文实测前沿开源模型生成越靠后的 token 越贵，成本差距最高到 7 倍；在长周期与长输入任务上做频繁 compaction、只维持短上下文，任务精度几乎没有损失。作者进一步发现长周期软件工程任务里每个上下文只允许一个动作，性能也不崩，并据此提出 semantic state space models（SSSM）的概念。

能做什么
用「频繁压缩 + 短上下文」替代长上下文窗口，给出跨长周期/长输入任务的精度对比，并提出 SSSM 作为语义状态建模的框架。
解决什么痛点
长上下文推理的边际成本极高：后段 token 生成成本是前段的数倍，靠堆窗口做 agent 记忆既贵又慢。
值不值得
对自建 agent 上下文管理的人，这条直接支持「压缩优先、窗口次要」的策略；但结论来自开源权重模型的测量，闭源前沿模型上的 7 倍差距未必同幅。

投机解码会改变长周期 agent 的推理：噪声在 30 步后放大

论文指出投机解码并非「只加速不改行为」：验证窗口内的数值噪声会累积，draft 接受结果在 30 步后能改变输出分布，随机地影响长周期 agent 的准确率。方法是在 agent trace 里定位关键决策点，训练 draft model 在这些点被拒绝，让 target 以噪声最低的条件重采样；只训练托管参数的 0.06%–0.28%，在 agentic coding benchmark 上提升端到端成功率且不改 target 的输出分布。

能做什么
把投机解码从纯加速器改成「上下文精度分配器」：训练 draft model 在关键推理点被拒绝，触发 verification 重启，让关键 token 由 target 在最低噪声下采样。
解决什么痛点
推理加速与长周期 agent 可靠性冲突：省下的算力可能以随机精度损失为代价，而这类损失在短 benchmark 上看不出来。
值不值得
跑自建推理栈 + 长周期 agent 的团队值得读；限制是要能改 draft model 训练流程，纯用现成投机解码权重无法直接复现收益。

谷歌 Data Agent Kit 正式 GA：37 个技能，安全边界交给 IAM

能做什么

Harbor 接入 Docker Sandboxes：每个评测任务一个独立内核的 microVM

开源 agent 评测框架 Harbor 支持 Docker Sandboxes，每个评测任务改在独立 microVM（独立内核）里跑，不再共享容器；本地或 Docker Cloud Sandboxes 都能跑，云端实测 64 个并发任务。动机是评测编码 agent 等于大规模运行 AI 写的不可信代码，且存在「奖励破解」——agent 改测试或改记录分数的文件来骗过评分。云沙箱可配网络策略：准备阶段放行拉依赖，运行阶段限制出网，从而让每个 agent 在相同网络条件下被评估，解决结果不可复现。支持 Docker Compose，多容器任务可在单个云沙箱内共享同一 microVM。已知缺口：公告没给启动开销、单任务成本或分数波动的数据；网络限制只堵了一条作弊路径，没说明如何防沙箱内改测试文件。

能做什么
Harbor 负责编排任务、收分、记日志，Docker Sandboxes 提供带独立内核的 microVM 隔离；云侧可配分阶段网络策略、Compose 多容器同沙箱；已是 Daytona/Modal/E2B/Runloop 等十多种后端之一。
解决什么痛点
评测编码 agent 就是跑成千上万次不可信代码：共享容器会互相污染，网络不隔离导致结果不可复现，agent 还会改测试来骗分。
值不值得
如果在自己搭 agent 评测或沙箱平台（尤其关心隔离粒度与并发成本），这条的后端清单与网络策略设计值得对照；但性能/成本数据缺失，选型前要自己压测。

TokenSpeed：为 agent 负载重写推理引擎，128K→1M 解码吞吐只降 16%

TokenSpeed 独立贡献者尚旭春在 AICon 深圳站拆解了这套面向 agent 的推理引擎：优化目标从「打满 batch」改成「延迟约束下的吞吐」，内部指标是每用户不低于 70 TPS。对比 TensorRT-LLM，batch=1 的端到端延迟快 9%，每用户 100 TPS 工作点上单卡吞吐高 11%；上下文从 128K 扩到 1M，解码吞吐只降 16%。架构分控制面（C++）、Runtime（Python）、Kernel（独立子包）三层，并用 Placement 系统把并行切分从模型适配代码里抽出来，编译器按相邻模块的 replicate/shard/partial 差异自动插入 all-reduce、all-gather、reduce-scatter。

能做什么
按 agent 的多轮短请求重设调度与缓存：请求状态机（submitted/prefilling/decoding/retracting/finished）以 C++ unique_ptr 传递资源所有权，Placement 类型系统自动生成通信与 fusion，Kernel 层对 Blackwell 单独优化。
解决什么痛点
chat 场景的吞吐优化在 agent 场景失效：前缀几十 K、输出几百 token，KV 复用率低、延迟敏感，传统引擎的 batch 打满策略反而拖慢跟手性。
值不值得
自建推理服务的团队值得看它的分层与自动并行编译思路（尤其多模型适配的维护成本）；但项目较新、生态与算子覆盖未经验证，短期更适合借鉴设计而非直接替换 vLLM。

哈佛基于 Jellyfish 平台数据研究 2021-01 至 2026-03、718 家企业、约 70 万员工、3 亿个工作事件：编码助手带来代码行 +12%、提交 +9%、合并请求 +5%（仅提交显著）；AI agent 带来 +30%/+20%/+23%。但工单解决量只 +12%，远低于代码行增幅。原因是下游成了瓶颈——合并请求平均评审时长 +49%、单条评论数 +53%、需要返工的 MR 占比翻倍、参与评审的人 +14%；工程师只有 30%–40% 时间在写代码。

能做什么

能做什么
用 LLM 做代码审计并直接推报告：复现程序 + 引入点二分 + 候选补丁，注册走 GitHub PR 提交构建配置，扫描在断网环境运行。
