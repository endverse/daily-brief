🔥 今日重点

Agent Sandbox v1.0.12：三个 SDK 统一支持 suspend/resume，空闲沙箱释放 Pod 但保留 claim 与持久卷

kubernetes-sigs 的 Agent Sandbox 11 月 20 日发布 v1.0.12，核心是把 suspend()/resume()/is_suspended() 补齐到 Go、Python、TypeScript 三个 SDK：通过对 Sandbox 打 spec.operatingMode 补丁（带 UID 守卫）释放 Pod，但保留 SandboxClaim 与持久卷。运行中的进程、内存与 emptyDir 不会随挂起保留，要连内存一起留住得配 pod snapshot。控制面新增 SandboxWarmPool 的 per-pool readinessGracePeriodSeconds（最小 30 秒，默认 5 分钟，可双向覆盖集群级默认）。sandbox-router 增加 Ed25519 v2 的沙箱级 scoped token，绑定 (namespace, name, uid)，在过期前授权该沙箱所有端口与方法；sandboxd 增加 ?stat=true 的单路径元数据与更细的 REST 错误码（ENOSPC/EDQUOT→507、ENAMETOOLONG→400）。示例里补了 CI runner sandbox 与 Claude Code 走集群内模型代理、跨 suspend/resume 保持会话两套。

v1.0.12 于 11 月 20 日发布；suspend/resume 覆盖 Go/Python/TypeScript 三个 SDK；readyness grace 最小 30s、默认 5m；Ed25519 v2 token 绑定 namespace+name+uid；新增 CI runner 与 Claude Code 两个示例。

27B 开源模型自己改自己的权重：无梯度、不训练，未见题目上准确率 +6.6 点

论文提出 self-rewriting：把权重、评分后的答案和「运行自己」的能力交给模型，让它诊断自己的失败并直接改写背后的权重，全程没有梯度也没有训练。在一个开放 27B 模型上，一次自编辑让未见题目的准确率提升 6.6 个点，并在连续八次会话里单调上升——每次先在练习题上验证编辑，只提交有效的。它还能修一个几乎全错的自身副本：不重训、不读原始权重，恢复到原模型 80% 以上的图像任务准确率。作者称该能力随规模涌现：同一模型家族里小模型改不动或把自己改坏，只有最大的那个能改进并自修。

能做什么
模型把自身权重当可编辑对象：自评 + 自运行定位失败，再写权重补丁；27B 单次编辑 +6.6 点，八次会话单调提升，还能把损坏副本恢复到 >80% 准确率。
解决什么痛点
常规后训练要重跑训练管线与 GPU 集群；推理期的 prompt/scaffold 收益任务一结束就消失。self-rewriting 把收益写进权重，且每次回答不额外付费。
值不值得
值得跟进但别急着上生产：目前是单模型、单任务族的结果，编辑正确性靠自评把关，退化风险与可复现性仍需第三方复现；关注持续学习方向的话，这是近期最具体的一篇。

02

System 1 agents：不生成文本、把工具调用做成选择题，1952 次请求里 97.0% 选对工具

论文针对「敏感临床数据不能出网、本地 LLM 又会编参数」的两难，提出 System 1 agents：本地 agent 调工具时不生成文本。做法是用一个确定性编译器，把每个工具的 schema 与请求变成若干选择题——选项只来自请求和 schema——再由一遍式决策模型作答。在 157 个生物医学工具、1952 次请求上，最好的 System 1 agent 选对工具或正确拒答的比例是 97.0%，高于 18 个本地 LLM agent 设置里最好的 95.2%；6056 个参数值填对 97.0%，且没有任何一次调用含编造内容，而 LLM 调用有 5.5%–19.7% 含编造值。框架已开源。

能做什么
把开放式生成换成受限多选题：工具选择与参数填充都变成从 schema/请求里枚举的选项，决策模型一遍作答，因此不可能产出 schema 之外的值。
解决什么痛点
医疗等场景不能把数据发给云端 LLM，本地小模型又会幻觉参数，而一次编造的值会污染后续每一步工具调用。
值不值得
值得读它的编译器设计——把「工具调用」降成「分类 + 填空」是可控 agent 的通用套路，可迁移到任何有清晰 schema 的内部工具集；限制是工具必须有严格 schema，开放式任务不适用。

03

Repo-Premium 基准：稠密检索的领先大半来自评测口径，用 LLM 生成标识符再 grep 就能追平

论文指出代码检索基准里「稠密向量远胜 BM25」多半是评测选出来的：查询精心构造、代码偏旧、BM25 还被削弱（把文件切块、把改过的测试算作相关）。作者自建 Repo-Premium——真实仓库的文件级排序、Python/JS/TS/Go/Rust/Java 六种语言、2022–2026 的 PR、91 个仓库的预注册测试池。结论是稠密优势可拆成两部分：偏袒稠密的评测选择，以及查询里缺少代码中的稀有标识符。用 LLM 先写出可能的标识符再 grep（generate-then-grep），在每一个 Python 测试池里都能追平稠密检索，包括模型发布之后才开的 PR。作者给出三条建议：跟公平的词法基线比、稠密与 BM25 融合、给缺词的查询补上代码里的词。

能做什么
用 91 个真实仓库、六语言、四年 PR 的基准把「稠密 vs 词法」拆开度量，并给出廉价补强：让 LLM 生成候选标识符再 grep。
解决什么痛点
团队常按论文结论直接上向量库，忽略 BM25 基线，换来很小的实际收益却付出索引与延迟成本；代码 agent 里 grep 明明够用，却说不清为什么。
值不值得
值得用来校准内部代码检索选型：先做公平 BM25 基线，再决定是否加向量；不宜据此彻底放弃稠密——论文自己也承认没有方法能预测单条查询该用哪个，融合更稳。

Frostbite：AI 从零设计出一颗通用 CPU，ISA、微架构、RTL、验证到 GDS 全由 agent 群迭代

Architect Labs 11 月 18 日发布 Frostbite：一颗指令集全新设计的通用 CPU，从编译器、ISA、微架构、RTL、验证到最终 GDS 都由 AI 系统自主迭代产出，公司称全程「零架构先验」，过程中跑的是多个 agent swarm。设计押在 interaction nets 上——程序的每一步都是局部的、依赖显式、每个值只有一个所有者——因此不必靠乱序执行在运行时重新发现依赖。作者给的例子是五皇后搜索：顺序程序一次只看一个候选，interaction net 平均每一步有约 12 个交互可并行执行，而程序本身一行没改。公司称由此拿到「免多线程」的并行（无锁、无竞争）与台阶式的性能提升。

能做什么
用 agent swarm 跑完架构探索→ISA→微架构→RTL→验证→GDS 全链路，产出一个基于 interaction nets 的新 ISA 通用 CPU 设计。
解决什么痛点
通用 CPU 架构几十年停滞，根因之一是主流语言把依赖藏在共享可变状态里，硬件只能在运行时猜；interaction nets 把并行性暴露在程序结构里，省掉乱序与一致性开销。
值不值得
值得读方法论而不是等芯片：这是「agent 群做长链路硬件工程」目前最完整的公开案例，验证与收敛怎么组织比结果更有参考价值；性能数字要打折看——来自公司自己的工作负载与仿真。

生产 DAG 半夜 OOM 没有 traceback：Managed Airflow Agent 把 worker 内存与重试对上，给出三条修法

Google Cloud 用一个具体案例讲 Managed Airflow（原 Cloud Composer）里的 agent：零售商 Cymbal 的 clickstream DAG 由 agent 生成并部署到 Airflow 2.11.1 环境（worker 2 vCPU/4GB，1–6 台自动伸缩）。10 月大促加新版 App 让一小时事件从约 350MB 涨到约 1.4GB，pandas 把整小时 concat 进内存后，10 月 23 日 14:00 UTC 那次运行三次重试全挂且任务日志无报错。控制台的 Investigate 让 agent 自己查：它把 worker 内存指标与任务重试对上，报告里每条结论都附证据，最后给出三条修法——直接写 BigQuery、分批处理、或加 worker 内存。运维先选加内存，再让 agent 分析整个环境该给多少内存。

能做什么
在控制台对失败 run 一键 Investigate：关联 worker 内存指标、任务重试与日志，输出带证据链的诊断与可执行修法；同一 agent 还能判断 DAG 是否适配新版本 Airflow。
解决什么痛点
生产管道失败的难点不是修而是定位——任务无 traceback 死掉时，线索散在 task log、scheduler log 与 worker 指标三处，人工要跨三处对时间线。
值不值得
值得看它的「证据链」设计：每条结论给依据，是把 agent 放进运维闭环的前提；但它绑定 Managed Airflow 控制台，自建 Airflow 只能借鉴「指标 + 重试」的关联诊断思路。

Grab 给 AI 生成代码上分层防御：预生产门禁 + 灰度 + 开关，崩溃自动映射到具体 PR

Grab 说 AI 编程助手普及后每版代码变更量变大，缺陷与崩溃概率随之上升，于是把稳定性防线做成四段：合并前用 Android Lint/SwiftLint（含自研规则）与单测、UI 测试拦；预生产用 Grab Early Access 把早期包发给内部用户持续监控——只有少数内部用户会碰到的崩溃，到生产规模就是崩溃率飙升与紧急热修；发布阶段用分阶段放量与功能开关，崩溃率超阈值就关开关而不发版；发布后用 Crashlytics + BigQuery 实时监控，自动分诊把崩溃元数据与堆栈映射到具体 PR，事后复盘再反哺 Lint 规则与测试覆盖。

能做什么
用左移的 lint/测试、内部灰度门禁、分阶段放量与实时崩溃监控四层接住 AI 带来的变更量增长，并形成「事故→规则」的反馈环。
解决什么痛点
AI 让提交变多、单次变更变大，崩溃更难定位——并非所有崩溃都有符号化堆栈，得交叉比对发布时间表、开关发布记录与会话元数据。
值不值得
值得抄结构而不是工具：内部灰度门禁 + 开关兜底 + 崩溃→PR 映射这套组合，对任何「AI 提效后变更量翻倍」的团队都成立；门槛是会话与版本元数据要打通。

Kueue v0.21.0-rc.1：DRA 优先级列表与可消费容量配额升 Beta，拒收受管的 LWS groupIdentity: Hash

rc.1 把两个 DRA 特性推到 Beta：KueueDRAIntegrationPrioritizedList 默认开启，调度时会把 firstAvailable 请求的 CEL 选择器与集群实际设备比对；consumable capacity 配额也升 Beta，DeviceClass 的容量维度可以用独立配额资源计费，请求取整导致多收费时会报告。另一处是准入收紧：受 Kueue 管理的 LeaderWorkerSet 用 spec.groupIdentity: Hash 会被直接拒绝——此前该模式下 leader Pod 绕过准入、worker 一直被门控。Helm 增加 managerConfig.structuredOverrides，可在不复制整份配置的前提下改 manager 设置。

02

Argo CD 的 self-heal 会跳过 Sync hook：5 个 region 里 2 个没跑迁移，36–44 分钟跑的是新代码

一篇 CNCF 博客复盘了真实现象：发布时 5 个 region 的 Application 同时上线同一 commit，3 个跑了数据库迁移、2 个没跑，新代码随后 36–44 分钟里一直报错——而 UI 上这两个 Application 显示 Synced + Healthy、「successfully synced (all tasks run)」。根因是两种刷新在抢：level-2 刷新来自约 2–3 分钟一次的 reconcile 定时器、会完整比对 Git；level-1 刷新由被管理对象变化触发、复用控制器已知状态。deny window 关闭时没有任何事件通知，先到的 level-1 被当成「修漂移」处理，而修漂移从不执行 hook。作者用最小复现（一个 Application + Sync hook Job + 四分钟 deny window）在 6 次里复现 5 次，并指出控制器日志里那次操作只列了 13 个资源、self-heal 计数为 1。

能做什么
解释「同步成功但 hook 没跑」的竞态：self-heal 走 level-1 刷新时只修漂移、不执行 Sync hook，而 UI 与 last operation 都显示成功。
解决什么痛点
把迁移放在 Sync hook 又开 self-heal 的团队会遇到「部分 region 迁移没跑、代码却已上线」，排查时被绿色状态误导，事故窗口被拉长。
值不值得
必读类：作者给了可复现的最小实验，读完能自己判断该改成 PreSync/PostSync 显式 hook、还是关掉 self-heal 或调整 deny window 策略。
